# Tech Design: Bitrix24 Logistics App + Shared Backend MVP

## 1. Цель

Вынести логистический контур подтверждения перемещений во внешний сервис с
основным интерфейсом во встроенном приложении Bitrix24. Telegram и web fallback
остаются резервными интерфейсами той же state machine, а 1С — системой учета
для документов `ПеремещениеТоваров`, РТУ, складов, остатков и учетных
справочников.

MVP должен закрыть сценарии:

- передача пакета водителю;
- приемка пакета в точке выгрузки;
- просмотр ожидаемых доставок;
- монитор текущего логистического состояния;
- аудит событий по каждой логистической единице.

AS-IS процесс транспортной службы зафиксирован в
[LogisticsTransportAsIs.md](LogisticsTransportAsIs.md).

## 2. Границы ответственности

### 2.1. 1С остается источником истины для

- документов `ПеремещениеТоваров`;
- документов `РеализацияТоваровУслуг` для потока интернет-заказов;
- складов, магазинов, центрального склада;
- учетных сотрудников/физлиц;
- печатного штрихкода/QR документа или пакета;
- бизнес-атрибутов документов: откуда, куда, номер, дата, проведение.

ОТМЕНЕНО (2026-09-12): 1С считалась источником актуального справочника
водителей. Для внутренних перемещений актуальность водителей теперь
определяется по сотрудникам Bitrix24; учетная связь с физлицом 1С может
сохраняться.

### 2.2. Внешний сервис становится источником истины для

- внутреннего логистического статуса `На складе / В пути`;
- текущей точки нахождения пакета;
- ожидаемой точки выгрузки;
- водителя в текущем рейсе;
- истории логистических событий;
- UX-слоев для сканирования и подтверждения: Bitrix24 как основной интерфейс,
  Telegram и web fallback как резервные интерфейсы.

### 2.3. Интерфейсы отвечают только за UX

Bitrix24, Telegram-бот и web fallback не хранят бизнес-состояние. Они вызывают
backend API, а вся валидация, state machine и аудит живут во внешнем сервисе.

Основной интерфейс Bitrix24 не должен быть единственной точкой выполнения
операций. При сбое камеры/WebView приложение выдаёт одноразовую ссылку на web
fallback; Telegram остаётся дополнительным резервом. Оба интерфейса принимают
тот же напечатанный QR/штрихкод и проводят те же draft/confirm операции.

### 2.4. Термины

- `Логистическая единица` - один физический пакет, который сканируют и ведут в
  state machine. В текущем коде она хранится в legacy-таблице
  `logistics_transfer`.
- `source_document_type` - тип документа-источника: `transfer` для
  `ПеремещениеТоваров`, `rtu` для `РеализацияТоваровУслуг`.
- `external_id` - стабильная ссылка на документ-источник в 1С. Уникальность
  должна проверяться в паре `(source_document_type, external_id)`.
- `source_warehouse_id` - склад, где пакет физически лежит перед первым плечом.
- `document_target_warehouse_id` - склад-получатель в документе 1С. Для
  `ПеремещениеТоваров` в пилоте это транзит Москвы.
- `target_warehouse_id` - финальный склад-получатель логистической единицы.
- `current_warehouse_id` - где пакет лежит сейчас, если он не в пути.
- `dropoff_warehouse_id` - куда водитель должен сдать пакет в текущем плече.

## 3. Бизнес-правила MVP

Раздел фиксирует целевую модель пилота. Уже реализованный foundation покрывает
передачу/приемку, ожидаемые доставки, монитор, историю и read-only sync РТУ.
Внешние статусы СДЭК/Почты остаются в действующей интеграции Bitrix24, а
пользовательский ручной допуск готовности в текущем пилоте отменен.

- Для `ПеремещениеТоваров`: `1 документ = 1 пакет`.
- Для межточечной РТУ: `1 РТУ = 1 логистическая единица`.
- Передачу водителю сканирует отправитель.
- Приемку сканирует получатель.
- Водитель не сканирует.
- Конечный получатель по документу может не совпадать с текущей точкой выгрузки.
- Если точка выгрузки не по пути, используется двухплечевая схема через центральный склад.
- В MVP документ `ПеремещениеТоваров` считается готовым к логистической передаче только по текущим признакам 1С, без доработки формы 1С.

### 3.1. Readiness gate документа 1С

Для пилота во внешний сервис попадают только документы `ПеремещениеТоваров`, где склад-получатель является транзитным складом.

Документ считается готовым к передаче водителю, если одновременно выполнены
все условия:

1. Документ не помечен на удаление.
2. Документ проведен.
3. `СкладПолучатель` документа = транзит Москвы (`_Reference80._Code = РБ0000027`).
4. Документ распечатан.
5. В истории документа есть событие сканирования / `Отсканирован`.

Правила по нижним флагам формы:

- `Отправка подтверждена` не используется как отдельный gate: по текущему процессу без подтвержденной отправки документ не проводится.
- `Проверен` в пилоте не обязателен; после появления отдельной роли сотрудников проверки этот флаг нужно добавить в readiness gate.
- `Распечатан` обязателен для пилота. Известный риск: очень редко флаг печати не проставляется, примерно один случай на несколько тысяч документов; такие случаи разбираются как исключения.
- если печать фактически была, но флаг не проставился, документ попадает в
  `manual_review` и не допускается к передаче в обход readiness gate.

Одного факта проведения документа недостаточно для запуска логистической передачи.

ОТМЕНЕНО (2026-08-28): пользовательский `manual_ready_override`, обходивший
сбой флага печати. Сохранившийся внутренний legacy endpoint не публикуется в
приложении Bitrix24, Telegram или web fallback и не является правилом пилота.

Фактический склад-получатель для backend и всех интерфейсов определяется через реквизит
`Подразделение` документа. В справочнике `Подразделения` к подразделению
привязан склад; именно этот склад становится точкой выгрузки / получателем
пакета во внешнем сервисе. `СкладПолучатель` документа при этом остается
признаком маршрутизации через транзит.

Для заказов сайта это правило временно действует как адресный fallback.
Отдельный реквизит `ЗаказПокупателя.осиТочкаСамовывоза`, принимающий
`PICKUP_POINT = XML_ID` склада, подготовлен как production-based candidate в
задаче Codex
[«Уточнить поле точки самовывоза»](codex://threads/01a0499c-af7c-78d0-8bea-64a994831eb5)
и [спецификации 1С](../../1C_Dev_Workflow/docs/specs/ut103-task-107-pickup-point-field-candidate-2026-08-28.md).
После отдельной установки и production readback он становится основным
источником точки внутреннего самовывоза; адрес остается резервом, СДЭК-ПВЗ не
смешивается с внутренней точкой.

### 3.2. Несколько плеч доставки

Один документ `ПеремещениеТоваров` в логистическом сервисе остается одним
пакетом, но пакет может ехать несколькими плечами.

Ключевые понятия:

- `target_warehouse_id` - финальный склад-получатель из
  `Подразделение.осиСклад`;
- `current_warehouse_id` - где пакет физически лежит сейчас, если он не в пути;
- `dropoff_warehouse_id` - куда водитель должен сдать пакет в текущем рейсе.

Правило маршрутизации:

- если водитель забирает перемещение из подразделения A, а подразделение B есть
  по пути текущего маршрута, то текущее плечо идет напрямую в B:
  `dropoff_warehouse_id = target_warehouse_id`;
- если B не по пути, водитель сдает пакет на центральный транзитный склад:
  `dropoff_warehouse_id = central_transit_warehouse_id`;
- после приемки на центральном транзитном складе пакет снова становится
  `at_warehouse`, но не считается доставленным, если
  `current_warehouse_id != target_warehouse_id`;
- на следующий день или в ближайший подходящий рейс центральный склад передает
  этот же пакет водителю следующим плечом до финального получателя.

Для MVP не нужен полноценный оптимизатор маршрутов. Достаточно:

- хранить стандартный маршрут первой машины как упорядоченный список
  складов/подразделений:
  `Щелковская -> Савеловская -> Митино -> Пресня -> Горбушка -> Теплый стан -> Гранд Юг -> Склад -> Люблино`;
- при передаче водителю показывать определенную backend подсказку:
  `везти напрямую` или `сдать на центральный транзит`;
- направление и точку сдачи текущего плеча определять автоматически по документу
  и маршруту; пользователь не выбирает их вручную;
- неоднозначное направление блокировать и отправлять в `manual_review` /
  `DELIVERY_REVIEW`, не разрешая обход проверки в интерфейсе;
- в аудите сохранять каждое плечо отдельными событиями `handed_to_driver` и
  `accepted_at_point`.

Завершенной логистическая единица считается только когда пакет принят на
финальном складе:
`status = at_warehouse` и `current_warehouse_id = target_warehouse_id`.

### 3.3. Передача Внешним Службам Доставки

СДЭК и Почта России уже интегрированы с Bitrix24. Активный контур
`pricing-service` отвечает только за внутреннее плечо нашего водителя до точки
сдачи и не создаёт повторные адаптеры перевозчиков.

Правила пилота:

- направление к внешней службе определяется способом доставки и документом,
  а не ручным выбором пользователя;
- внутренний сотрудник передает пакет нашему водителю обычным событием
  `handed_to_driver`;
- пока наш водитель везет пакет, физическое состояние — `in_transit`, а CRM не
  продвигается выше `FINAL_INVOICE` / `Готов к отгрузке` этим событием;
- водитель не подтверждает приемку перевозчиком вручную;
- действующая интеграция СДЭК/Почты получает сильное событие перевозчика и сама
  ведет внешние стадии сделки;
- `pricing-service` не зеркалирует внешние статусы в монитор, а пользователь
  смотрит дальнейшее движение только по стадиям сделки Bitrix24;
- при необходимости допустим только технический readback Bitrix24 для закрытия
  внутреннего плеча без пользовательского статуса и без обратной записи стадии.

`with_external_carrier`, `handed_to_external_carrier` и
`accepted_from_external_carrier` сохраняются в модели только как legacy-резерв
для иных маршрутов без действующей CRM-интеграции. Для СДЭК/Почты текущего
пилота они не используются.

### 3.4. Заказы Сайта И РТУ

Заказы интернет-магазина, которые нужно физически доставить/передать в
подразделение, не должны попадать в логистику напрямую из `ЗаказПокупателя`.

Текущий процесс 1С:

- сайт создает `ЗаказПокупателя`;
- на основании заказа создается `РеализацияТоваровУслуг` (`РТУ`);
- собирается уже `РТУ`;
- после готовности `РТУ` появляется логистическая задача.

Для этого потока действует отдельный integration contract:
[IntegrationContract.LogisticsSiteOrders1C.md](IntegrationContract.LogisticsSiteOrders1C.md).

Действующий readiness gate для РТУ:

1. РТУ не помечена на удаление.
2. РТУ проведена.
3. В истории РТУ есть событие `Распечатан`.
4. В истории РТУ есть событие `Собран`.

Служебный фильтр по пометке удаления обязателен всегда. Бизнес-готовность РТУ
для пилота дают три признака: проведена, распечатана, собрана.

Событие `Сборка через РМ закончена` для РТУ на MVP не ждем и 1С ради него не
дорабатываем: текущего события `Собран` достаточно для запуска пилота.

Склад получателя для самовывоза определяем без отдельного поля `ПВЗ`:

- из заказа берем `Способ доставки с сайта`;
- если это `Самовывоз`, берем адрес из `Дополнение` / `Адрес доставки`;
- сопоставляем адрес с карточкой подразделения;
- склад получателя берем из `Подразделение.осиСклад`;
- если адрес не сопоставился однозначно, задача попадает в `manual_review`, где
  логист вручную выбирает подразделение-получатель.

Локальная выдача не создает логистическую единицу: если найденный склад
получателя совпадает со складом РТУ либо адрес пуст при внутреннем самовывозе,
РТУ остается в ТЗП своего подразделения. Межточечная РТУ создается как
`source_document_type = rtu`, после `handed_to_driver` видна получателю в
`/expected`, а после `accepted_at_point` на конечной точке возвращается в
«Готов к выдаче» ТЗП получателя через read-only API.

Для сканирования РТУ используется уже напечатанный штрихкод/QR расходной
накладной. Backend сначала выполняет точный поиск по внутренним
`lookup_code`/`barcode`, затем нормализует поддерживаемые короткий и полный
форматы. Отдельный корпоративный lookup-код и изменение печатной формы
отложены; перепечатка документов для текущего пилота не требуется.

## 4. Архитектура решения

```text
1С
  -> read-only справочники, перемещения и готовые РТУ
  -> фоновая синхронизация РТУ каждую минуту без обращения при сканировании

External Logistics Service (FastAPI + PostgreSQL)
  -> хранение logistics state
  -> хранение audit trail
  -> пользовательский BFF для приложения Bitrix24
  -> общий backend API для Bitrix24, Telegram и web fallback
  -> API для sync с 1С
  -> отчеты и операционный монитор

Bitrix24 Logistics App
  -> OAuth/scoped session и привязка роли/склада
  -> сканирование напечатанного QR/штрихкода
  -> создание handoff / receipt draft
  -> подтверждение операций
  -> просмотр expected deliveries

Telegram Bot + Web Fallback UI
  -> резервные интерфейсы той же state machine
  -> те же draft/scan/confirm операции без отдельной бизнес-логики
```

## 5. Модель данных PostgreSQL

### 5.1. Справочники

#### `logistics_warehouse`

- `id`
- `external_id`
- `name`
- `kind` (`store`, `central`, `transit`, `external_terminal`)
- `is_active`
- `created_at`
- `updated_at`

#### `logistics_driver`

- `id`
- `external_id`
- `full_name`
- `phone`
- `is_active`
- `created_at`
- `updated_at`

#### `logistics_user`

- `id`
- `external_id`
- `bitrix_user_id` (nullable unique)
- `telegram_user_id`
- `username`
- `full_name`
- `role` (`sender`, `receiver`, `logist`, `admin`)
- `default_warehouse_id`
- `is_active`
- `created_at`
- `updated_at`

Источник пользователей для MVP — Bitrix24: `bitrix_user_id` связывается с
ролью логистики и складом/подразделением во внешнем сервисе. Опциональный
`telegram_user_id` дает тому же пользователю доступ к резервному Telegram UX.
Справочники складов и подразделений остаются из 1С. Сотрудника из Bitrix можно
дополнительно сопоставлять с сотрудником/физлицом 1С по телефону, email или
внешнему идентификатору, но это не блокирует авторизацию в Bitrix24.

На период тестирования `admin` получает все экраны и операции
`sender`/`receiver` на любом пилотном складе, мониторинг, историю, ошибки и
ручной разбор логистических конфликтов. Все действия пишутся в аудит; финальные
стадии сделки и обязательная последовательность физических событий остаются
защищенными. После пилота расширенный тестовый доступ отключается.

ОТМЕНЕНО (2026-09-12): водителей предлагалось импортировать из 1С как
актуальный справочник для выбора в рейсе.

Для внутренних перемещений список формируется только из активных сотрудников
Bitrix24 с должностью «Водитель». Должность «Курьер» не включается: она
относится к отдельному процессу курьерской доставки в Санкт-Петербурге.
Неактивный водитель исключается из новых передач, но сохраняется в истории.
Доступ к боту для водителя не обязателен: по текущей модели сканируют
отправитель и получатель.

### 5.2. Логистические Единицы

#### `logistics_transfer`

Текущий состав таблицы после выполненного расширения модели:

- `id`
- `source_document_type` (`transfer`, `rtu`)
- `external_id`
- `document_number`
- `document_date`
- `origin_order_external_id`
- `site_order_number`
- `source_warehouse_id`
- `document_target_warehouse_id` (для
  `ПеремещениеТоваров` это транзитный склад документа)
- `target_warehouse_id`
- `final_recipient_name`
- `lookup_code` (внутреннее техническое поле backend)
- `barcode`
- `onec_status`
- `onec_deleted`
- `payload` (`jsonb` с исходным payload из 1С)
- `created_at`
- `updated_at`

Индексы:

- уникальный индекс по `(source_document_type, external_id)`
- индекс по `lookup_code`; однозначность кода дополнительно проверяется сервисом;
- индекс по `barcode` для совместимости старых scan endpoints.

Текущий код уже различает `transfer` и `rtu`, ищет единицу по уникальной паре
`(source_document_type, external_id)` и сохраняет `barcode` как совместимое
legacy-поле.

Пользователь сканирует код с существующей печатной формы. Backend нормализует
его и сопоставляет с внутренними `lookup_code`/`barcode` либо стабильной ссылкой
документа. Пользователь не выбирает и не вводит корпоративный lookup-код.

ОТЛОЖЕНО (2026-08-28): отдельный корпоративный QR на печатной форме. Если этот
этап будет возобновлен отдельным решением, зарезервирован основной формат:

```text
MMLOG1|transfer|<1c_document_ref>
```

Допустимый будущий fallback, если ссылка 1С недоступна в печатном макете:

```text
MMLOG1|transfer-number|<full_document_number>|<document_date_yyyyMMdd>
```

Этот будущий формат разрешается только после проверки уникальности полного
номера и даты. Он не является условием текущего пилота и не требует перепечатки
существующих документов.

### 5.3. Текущее состояние

#### `logistics_transfer_state`

- `transfer_id`
- `status` (`at_warehouse`, `in_transit`; `with_external_carrier` — legacy для
  маршрутов без CRM-интеграции)
- `current_warehouse_id`
- `dropoff_warehouse_id`
- `driver_id`
- `last_event_type`
- `last_event_at`
- `last_user_id`
- `last_document_ref`
- `version`
- `updated_at`

Назначение:

- хранит только текущий логистический state;
- обновляется только через append-only события.
- поддерживает много плеч: `dropoff_warehouse_id` всегда относится только к
  текущему рейсу, а финальный получатель хранится в
  `logistics_transfer.target_warehouse_id`.

#### `logistics_transfer_event`

- `id`
- `transfer_id`
- `event_type`
- `event_at`
- `warehouse_id`
- `dropoff_warehouse_id`

Типы событий:

Legacy-события сохраняются в модели ради совместимости и аудита ранее

Индексы:

- уникальный индекс по `idempotency_key`, где он заполнен;
- индекс по `(transfer_id, event_at desc)`.

### 5.5. Внешние Службы Доставки

Для следующей волны пилота достаточно простого справочника:

#### `logistics_external_carrier`

- `id`
- `name`
- `is_active`
- `created_at`
- `updated_at`

Терминалы внешних служб не заводим отдельной таблицей. Их достаточно хранить как
склады с `kind = external_terminal`, чтобы существующий
`dropoff_warehouse_id` мог указывать, куда водитель должен сдать пакет.

API-интеграции с перевозчиками не входят в пилот; справочник нужен только для
нормализации названий в событиях и отчетах.

### 5.6. Manual Review И Legacy Override

Два сценария не должны ломать автоматический поток:

- документ `ПеремещениеТоваров` готов физически, но `_Fld8954` не проставился;
- РТУ самовывоза не удалось однозначно сопоставить с подразделением по адресу.

Активный административный workflow:

- документ с отсутствующим обязательным признаком печати остаётся в
  `manual_review` без допуска к передаче;
- `manual_review` по РТУ хранит исходный payload, кандидатов подразделений и
  выбранное логистом подразделение-получатель;
- все решения пишутся в audit trail, а не редактируют state напрямую.

внутренний endpoint остаётся legacy-фактом кода, но не публикуется в приложении
Bitrix24, Telegram или web fallback.

## 6. State machine

### 6.1. Состояния

- `at_warehouse`
- `in_transit`
- `with_external_carrier` — только legacy-резерв для маршрутов без действующей
  CRM-интеграции; в приложении текущего пилота не показывается.

### 6.2. Переходы

#### Передача водителю

Событие: `handed_to_driver`

Переход:

- `at_warehouse -> in_transit`

Проверки:

- логистическая единица найдена по напечатанному QR/штрихкоду, который backend
  сопоставил с внутренними полями поиска;
- если state отсутствует, считаем, что пакет находится на складе-отправителе из 1С;
- если state есть, статус должен быть `at_warehouse`;
- текущий склад должен совпадать со складом пользователя;
- нельзя повторно передать уже `in_transit` логистическую единицу.

Результат:

- `status = in_transit`
- `current_warehouse_id = null`
- `dropoff_warehouse_id = автоматически определенная точка выгрузки текущего плеча`
- `driver_id = выбранный водитель`

Примечание:

- если финальный получатель по пути, точка выгрузки текущего плеча равна
  `target_warehouse_id`;
- если финальный получатель не по пути, точка выгрузки текущего плеча равна
  центральному транзитному складу.

#### Приемка в точке

Событие: `accepted_at_point`

Переход:

- `in_transit -> at_warehouse`

Проверки:

- логистическая единица найдена;
- статус должен быть `in_transit`;
- `dropoff_warehouse_id` должен совпадать со складом приемки пользователя;
- если уже `at_warehouse`, возвращаем сообщение `уже принято ранее`.

Результат:

- `status = at_warehouse`
- `current_warehouse_id = склад приемки`
- `dropoff_warehouse_id = null`
- `driver_id = null`

Если `current_warehouse_id = target_warehouse_id`, логистическая единица
доставлена в финальную точку. Если `current_warehouse_id != target_warehouse_id`,
пакет лежит на промежуточном складе и должен попасть в очередь следующей
отгрузки.

#### Передача внешней службе доставки

Для действующего потока СДЭК/Почты этот локальный переход не используется:
внешние события и стадии уже ведет Bitrix24, а копия состояния в логистическом
мониторе не создается. Переход ниже остается legacy-возможностью модели для
других маршрутов без CRM-интеграции и не должен менять сделку.

Событие: `handed_to_external_carrier`

Переход:

- `in_transit -> with_external_carrier`

Проверки:

- логистическая единица найдена;
- текущее плечо должно быть назначено на `warehouse.kind = external_terminal`;
- источник события не относится к действующему потоку СДЭК/Почты;
- событие однозначно связано с одной РТУ/логистической единицей;
- повторный идентификатор события является идемпотентным;
- неоднозначное событие создает `manual_review` без смены состояния;
- обработчик никогда не записывает CRM-стадию.

Результат:

- `status = with_external_carrier`
- `current_warehouse_id = null`
- `dropoff_warehouse_id = null`
- `driver_id = null`
- в `event.meta` сохраняется `carrier_name`; `tracking_number`, `city` и
  `carrier_terminal` заполняются опционально.

Для списка ожидаемых приемок от внешних служб используется пара
`status = with_external_carrier` и `target_warehouse_id`; `dropoff_warehouse_id`
не перегружаем, потому что внутреннее водительское плечо уже завершено.

#### Приемка после внешней доставки

Событие: `accepted_from_external_carrier`

Переход:

- `with_external_carrier -> at_warehouse`

Проверки:

- логистическая единица найдена;
- пользователь принимает на складе финального подразделения;
- склад приемки должен совпадать с `target_warehouse_id`.

Результат:

- `status = at_warehouse`
- `current_warehouse_id = склад приемки`
- `dropoff_warehouse_id = null`
- `driver_id = null`

#### Отмена передачи

Событие: `handoff_cancelled`

Переход:

- `in_transit -> at_warehouse`

Условие:

- разрешено, если перемещение еще не принято в точке.

#### Возврат

Событие: `returned`

Переход:

- `in_transit -> at_warehouse`

Условие:

- фактический склад приемки задается явно;
- в комментарии фиксируется причина возврата.

#### Инцидент

Событие: `incident`

Переход:

- состояние не меняется.

#### Legacy: Ручной Допуск Готового Документа

ОТМЕНЕНО ДЛЯ ТЕКУЩЕГО ПИЛОТА (2026-08-28): операция ниже описывает
сохранившуюся внутреннюю возможность кода и не должна быть доступна через
пользовательские интерфейсы.

Событие: `manual_ready_override`

Переход:

- если логистическая единица еще не создана: создается state `at_warehouse`;
- если логистическая единица уже есть: state не меняется.

Проверки:

- операцию выполняет логист/админ;
- причина обязательна;
- документ не помечен на удаление;
- документ проведен;
- склад-получатель документа соответствует транзиту Москвы;
- фактический склад-получатель через `Подразделение.осиСклад` определен;
- выбранный lookup для сканирования подтвержден и уникален.

Результат:

- логистическая единица доступна для handoff;
- в `event.meta` сохраняются причина, пользователь, исходные флаги 1С и список
  условий, которые были обойдены. Для этого workflow допускается обходить только
  `printed = false`.

## 7. REST API

Все endpoints `/api/logistics/*` являются backend/internal API и защищены
внутренним токеном. Пользовательское приложение Bitrix24 получает только
короткую scoped-сессию через BFF `/api/bitrix/logistics/*`; внутренний токен не
передаётся в браузер. Telegram и web fallback вызывают ту же бизнес-логику через
свои серверные контуры. Клиентские UX-слои не хранят state и не получают прямой
доступ к БД.

### 7.1. UX-facing API

Основной пользовательский BFF приложения Bitrix24:

- `POST /api/bitrix/logistics/session` — OAuth payload в короткую scoped-сессию;
- `GET /api/bitrix/logistics/bootstrap` — профиль, склад, водители и операции;
- `/api/bitrix/logistics/handoffs/draft/*` — передача водителю;
- `/api/bitrix/logistics/receipts/draft/*` — приёмка в точке;
- `GET /api/bitrix/logistics/expected-deliveries` и `/monitor`;
- `POST /api/bitrix/logistics/fallback-link` — одноразовый переход во внешний
  браузер при проблеме камеры/WebView.

Ни один BFF endpoint не разрешает пользовательский обход readiness gate,
последовательности `передача -> приёмка` или защиты финальных CRM-стадий.

#### `POST /api/logistics/auth/telegram`

Назначение:

- связать `telegram_user_id` с пользователем сервиса;
- вернуть роль и default warehouse.

Это резервный контур Telegram, а не основной способ входа. Web fallback получает
одноразовую пятиминутную ссылку из Bitrix24 и меняет её один раз на короткую
scoped-сессию с теми же ролями и warehouse binding.

#### Поиск Логистической Единицы По Напечатанному Коду

В текущем foundation отдельного публичного `GET` endpoint для lookup нет:
поиск выполняется внутри endpoints сканирования draft:
`POST /api/logistics/handoffs/draft/{draft_id}/scan` и
`POST /api/logistics/receipts/draft/{draft_id}/scan`.

Если нужен отдельный lookup endpoint для UI/debug, legacy-compatible вариант:
`GET /api/logistics/transfers/by-barcode/{barcode}`. После добавления РТУ лучше
добавить generic alias `/api/logistics/units/lookup`.

#### `POST /api/logistics/handoffs/draft`

Назначение:

- создать черновик передачи водителю; направление определяется backend по
  документу и маршруту.

Вход:

- `warehouse_id`
- `driver_id`

`dropoff_warehouse_id` не выбирается пользователем. Если backend не может
однозначно определить точку сдачи, черновик блокируется и создаётся ошибка для
разбора.

#### `POST /api/logistics/handoffs/draft/{draft_id}/scan`

Назначение:

- добавить строку в draft по напечатанному QR/штрихкоду.

Вход:

- `barcode` / значение, возвращённое сканером

Проверки:

- код распознан и однозначно найден;
- в draft нет дубля;
- логистическая единица допустима к передаче.

#### `POST /api/logistics/handoffs/draft/{draft_id}/confirm`

Назначение:

- провести передачу водителю.

Вход:

- `comment`
- `idempotency_key`

#### `POST /api/logistics/receipts/draft`

Назначение:

- создать черновик приёмки на складе из профиля пользователя.

Вход:

- `warehouse_id`
- `driver_id` (optional)

Обычный `receiver` принимает только на своём складе. Расширенный тестовый
`admin` видит все пилотные склады, но также не обходит последовательность
событий.

#### `POST /api/logistics/receipts/draft/{draft_id}/scan`

Назначение:

- добавить логистическую единицу в draft приемки.

Вход:

- `barcode` / значение, возвращённое сканером

#### `POST /api/logistics/receipts/draft/{draft_id}/confirm`

Назначение:

- провести приемку.

Вход:

- `comment`
- `idempotency_key`

#### `GET /api/logistics/expected-deliveries`

Фильтры:

- `warehouse_id`
- `driver_id`
- `period_from`
- `period_to`

Примечание: `period_from` / `period_to` относятся к следующей волне. Текущий
foundation API поддерживает фильтры `warehouse_id` и `driver_id`.

Назначение:

- вернуть список логистических единиц, где `status = in_transit` и
  `dropoff_warehouse_id = warehouse_id`.

#### `GET /api/logistics/monitor`

Фильтры:

- `status`
- `warehouse_id`
- `driver_id`
- `final_recipient`
- `date_from`
- `date_to`

Примечание: `date_from` / `date_to` относятся к следующей волне. Текущий
foundation API поддерживает `status`, `warehouse_id`, `driver_id`,
`final_recipient`.

Назначение:

- вернуть сводный монитор текущего состояния логистических единиц.

#### `GET /api/logistics/transfers/{transfer_id}/history`

Назначение:

- вернуть историю событий и фото по логистической единице.

#### `POST /api/logistics/transfers/{transfer_id}/incident`

Назначение:

- записать событие `incident` без изменения основного state.

#### `POST /api/logistics/transfers/{transfer_id}/return`

Назначение:

- записать событие `returned`; для текущей реализации нужен `warehouse_id`,
  потому что возврат меняет фактический склад.

### 7.2. Sync API для 1С и административных справочников

#### `POST /api/logistics/sync/warehouses`

- импорт складов и магазинов из 1С

#### `POST /api/logistics/sync/drivers`

- импорт водителей из 1С

#### `POST /api/logistics/sync/users`

- импорт пользователей, Bitrix user ID, опционального Telegram ID, ролей и
  привязок к складам из Bitrix24
  либо из локальной административной таблицы на время пилота

#### `POST /api/logistics/sync/transfers`

- импорт открытых перемещений и внутреннего кода поиска для сканирования;
- API поддерживает `source_document_type`; для перемещений используется
  `source_document_type = transfer`.

#### `POST /api/logistics/sync/order-plans`

- принимает полный versioned snapshot `ORDER_TRANSFER_V1` до готовности
  документов перемещения;
- план идентифицируется `plan_key + plan_version`, обязательные части —
  уникальным `unit_key`;
- изменение незапущенного плана создаёт новую версию, изменение после handoff
  фиксируется как `order_flow_conflict`;
- production ingress выполняется минутным read-only SQL pull. HTTP endpoint
  используется сервисным слоем и тестами, но не делает backend владельцем 1С.

#### `POST /api/logistics/sync/carrier-confirmations`

- принимает сильный факт существующей Bitrix-интеграции СДЭК/Почты;
- требует однозначный заказ, активный carrier-plan, терминал, трек,
  `confirmed_at` и стабильный `source_ref`;
- отклоняет подтверждение, если последний snapshot плана старше 180 секунд;
- идемпотентно завершает все обязательные внутренние плечи заказа на терминале;
- сохраняет backend-owned `carrier_confirmation` при последующих snapshot из 1С;
- не создаёт второй CRM outbox и не заменяет внешний adapter Bitrix24.

#### `POST /api/logistics/sync/rtu`

Отдельный HTTP endpoint не является действующим способом загрузки РТУ. Текущий
production-процесс — read-only CLI/cron
`tasks/sync_logistics_rtu_from_onec.py`, запускаемый раз в минуту с `flock` и
явным apply-режимом. Ручной запуск без `--apply` остаётся dry-run.

Если push-endpoint когда-либо будет добавлен отдельно, он обязан применять те
же правила, что и текущая синхронизация:

- импорт готовых РТУ интернет-заказов;
- применяет gate `не помечена на удаление` + `Проведена` + история
  `Распечатан` + история `Собран`;
- при неоднозначном адресе самовывоза создает запись `manual_review`, а не
  логистическую единицу для автоматической отправки.

### 7.3. Операционные И Legacy Endpoints

#### Внешние статусы Bitrix24

Отдельные adapters API СДЭК/Почты и endpoint зеркалирования их статусов в
`pricing-service` не создаются. Пользователь видит внешнюю доставку только в
стадиях сделки Bitrix24. Допустим только технический readback для завершения
внутреннего водительского плеча, если без него единица останется ошибочно в
очереди «В пути»; такой readback не создает пользовательский внешний статус и
никогда не записывает обратный CRM-переход.

#### `POST /api/logistics/transfers/{transfer_id}/external-carrier/accept`

Legacy/future endpoint для маршрутов без действующей CRM-интеграции; в потоке
СДЭК/Почты текущего пилота не используется:

- фиксирует `accepted_from_external_carrier`;
- доступен получателю финального склада;
- закрывает логистическую единицу только при приемке на `target_warehouse_id`.

#### `POST /api/logistics/manual-ready-overrides`

Endpoint существует как internal/legacy возможность, но пользовательский
`manual_ready_override` отменён и не публикуется через Bitrix24, Telegram или
web fallback:

- принимает ссылку на документ 1С или номер документа;
- требует обязательную причину;
- создает/обновляет логистическую единицу и пишет `manual_ready_override`;
- не пишет изменения обратно в 1С.

#### `GET /api/logistics/manual-review`

Реализованный internal endpoint:

- показывает РТУ, которые не удалось автоматически сопоставить с подразделением
  или lookup;
- используется для контролируемого разбора неоднозначностей; пользовательское
  приложение не разрешает через него обход readiness gate или порядка событий.

### 7.4. Read-only API возврата принятой РТУ в ТЗП

#### `GET /api/logistics/rtu/ready-for-pickup`

Параметры:

- `warehouse_code` — обязательный код склада/подразделения 1С;
- `date_from` — опциональная нижняя граница даты РТУ;
- `format=json|xml` — формат ответа, по умолчанию JSON.

Назначение:

- вернуть только межточечные РТУ, принятые событием `accepted_at_point` на
  конечном складе;
- предоставить ТЗП получателя безопасный read-only список без записи логистики
  обратно в production 1С;
- XML используется старой платформой 1С 8.2, JSON — тестами и другими клиентами.

#### `GET /api/logistics/orders/ready-for-pickup`

- объединяет legacy РТУ и `ORDER_TRANSFER_V1`;
- возвращает одну строку на клиентский заказ только после приёмки всех
  обязательных частей актуальной версии на конечном складе;
- не возвращает новый поток при snapshot плана старше 180 секунд;
- промежуточная приёмка и одна часть многоскладского заказа не дают готовность;
- ТЗП сначала читает этот XML endpoint, затем временно использует RTU endpoint
  как fallback.

#### `GET /api/logistics/orders/carrier-confirmations`

- read-only feed подтверждённых передач внешнему перевозчику;
- параметры: опциональный `confirmed_from`, `format=json|xml`;
- XML предназначен для native 1С 8.2 handler, создающего одну финальную РТУ;
- feed не подтверждает событие повторно и не двигает CRM.

## 8. UX: Bitrix24, Telegram И Web Fallback

### 8.1. Основной Интерфейс Bitrix24

Приложение открывается через пункт `LEFT_MENU` «Логистика». После OAuth
backend связывает пользователя Bitrix24 с ролью и складом логистики и выдаёт
короткую scoped-сессию.

Основные экраны:

- `Передать водителю`
- `Принять в магазине`
- `Ожидаемые поступления`
- `В пути`
- `История и ошибки`

Telegram сохраняет команды `/handoff`, `/receive`, `/expected`, `/monitor` как
резервный UX той же state machine, без отдельного набора бизнес-правил.

### 8.3. Сценарий передачи

1. Пользователь выбирает водителя.
2. Backend определяет направление и точку выгрузки по документу и маршруту.
3. Приложение открывает режим сканирования с заметной кнопкой
   `Назад / Отменить`.
4. Каждый напечатанный QR/штрихкод отправляется в `handoff draft scan`.
5. Приложение показывает:
   - список принятых сканов;
   - список ошибок без модальных окон.
6. Пользователь нажимает `Провести`.

Пользователь не выбирает направление вручную. Неоднозначность блокирует
подтверждение, но не удаляет уже собранный draft.

### 8.4. Сценарий приемки

1. Пользователь открывает приемку.
2. Backend определяет склад из профиля пользователя; обычный `receiver` не
   выбирает чужой склад.
3. Пользователь сканирует тот же напечатанный QR/штрихкод.
4. Приложение выводит валидные позиции и ошибки по неверной точке выгрузки,
   отсутствующей передаче или дублям.
5. Пользователь нажимает `Подтвердить приемку`.

### 8.5. Сценарий ожидаемых доставок

Приложение показывает логистические единицы:

- номер документа;
- склад отправителя;
- конечного получателя;
- водителя;
- ожидаемую точку выгрузки;
- время последнего события.

### 8.6. Web Fallback UX

Web fallback нужен как обязательный резерв, если камера или WebView мобильного
Bitrix24 не работает. Одноразовая ссылка действует пять минут и один раз
обменивается на короткую scoped-сессию. Это не отдельная бизнес-логика, а тонкий
UX-слой над теми же backend endpoints.

Минимальный состав:

- страница `Передать водителю`;
- страница `Принять в точке`;
- ввод напечатанного QR/штрихкода через камеру браузера, ручной сканер в режиме клавиатуры
  или обычное поле ввода;
- выбор водителя; направление и точка выгрузки приходят из backend;
- список валидных сканов и ошибок перед подтверждением;
- заметная кнопка `Назад / Отменить`, не теряющая draft при ошибке камеры;
- кнопка `Провести` / `Подтвердить приемку`.

Технические правила:

- значение напечатанного кода одинаково обрабатывается в Bitrix24, Telegram и
  web fallback; корпоративный формат `MMLOG1|...` не обязателен для текущего
  пилота;
- web fallback использует те же `handoff draft`, `receipt draft`, `scan` и
  `confirm` endpoints;
- роли, склад пользователя и warehouse binding проверяет backend;
- браузер не хранит логистическое состояние, кроме текущего draft/session;
- `confirm` отправляет `idempotency_key`;
- операция считается проведенной только после успешного ответа backend; локальное
  сообщение в браузере не является фактом передачи или приемки.

## 9. Минимальный контракт обмена с 1С

Текущий расширенный payload по логистической единице:

```json
{
  "source_document_type": "transfer",
  "external_id": "uuid-from-1c",
  "document_number": "ПТ-000123",
  "document_date": "2026-03-28T10:15:00Z",
  "source_warehouse_external_id": "store-01",
  "document_target_warehouse_external_id": "moscow-transit",
  "target_warehouse_external_id": "store-05",
  "final_recipient_name": "Магазин 5",
  "barcode": "4601234567890",
  "onec_status": "posted"
}
```

Критично:

- `external_id` должен быть стабильным;
- для `ПеремещениеТоваров` `target_warehouse_external_id` должен указывать на
  фактический склад-получатель из `Подразделение.осиСклад`, а не на
  `СкладПолучатель` документа 1С;
- `document_target_warehouse_external_id` нужен для аудита маршрутизации через
  транзит и сохраняется отдельно от финального `target_warehouse`;
- значение напечатанного кода должно однозначно находить одну логистическую
  единицу: перемещение или РТУ;
- справочники складов и логистических пользователей должны синхронизироваться
  раньше логистических единиц.

API принимает `source_document_type`, `document_target_warehouse_external_id` и
внутренний `lookup_code`. Поле `barcode` сохранено как legacy-совместимость
старых scan endpoints. Сканирование не обращается напрямую в 1С: документ
должен быть заранее загружен минутной read-only синхронизацией.

Печатную форму текущего этапа не меняем. Backend поддерживает существующий
короткий QR РТУ и полный совместимый формат; отдельный корпоративный QR
`MMLOG1|...` остаётся отложенной следующей доработкой.

## 10. Нефункциональные требования

- поиск по значению напечатанного кода должен укладываться в `<= 1 сек`;
- confirm endpoints должны быть идемпотентными;
- обновление state и запись события должны происходить в одной транзакции;
- прямое редактирование текущего состояния без события запрещено;
- аудит должен сохранять пользователя, время, склад, водителя и комментарий;
- backend должен поддерживать optimistic locking по `version`;
- сбой камеры или WebView Bitrix24 не должен останавливать операцию: web
  fallback использует одноразовую короткую сессию и тот же backend API.

Примечание: текущий foundation хранит и инкрементит `version`, но настоящее
условное обновление state по версии относится к следующей волне реализации.

## 12. Основные риски

- напечатанный QR/штрихкод 1С может неоднозначно сопоставиться с документом;
  отдельный корпоративный lookup-код отложен на следующий этап, поэтому такой
  случай должен блокироваться и уходить в `manual_review`;
- если пользователи меняют документы перемещений задним числом, внешний контур может расходиться с 1С;
- если в будущем один документ начнет соответствовать нескольким пакетам, потребуется отдельная сущность `package`;
- если перепутать `СкладПолучатель` документа с фактическим получателем из
  `Подразделение.осиСклад`, backend будет вести пакеты на транзит вместо магазина;
- если авторизацию UX-слоев не привязать жестко к складу и роли, будут ошибки в
  приемке и передаче;
- если камера или WebView Bitrix24 не запускается, процесс передачи/приемки
  может остановиться; снижение риска — одноразовый web fallback на том же
  backend API.

## 13. Рекомендация по реализации в текущем репозитории

Контур реализуется внутри `pricing-service` как отдельный bounded context:

- `app/api/logistics*.py`
- `app/services/logistics/`
- `app/schemas/logistics.py`
- `app/models/logistics.py`
- `alembic/versions/*_add_logistics_tables.py`
- `docs/TechDesign.LogisticsTelegramMVP.md`

Это позволяет:

- использовать текущий FastAPI-каркас;
- использовать текущий PostgreSQL/Alembic стек;
- поддерживать Bitrix24, Telegram и web fallback над одной state machine;
- позже, если нагрузка вырастет, вынести логистику в отдельный сервис без изменения пользовательского UX.

- Telegram webhook endpoint и базовый бот;
- web fallback и Bitrix24-встраивание используют ту же state machine.

Локально реализован, но ещё не включён `ORDER_TRANSFER_V1`:

- Alembic-модели versioned order plan и plan unit;
- минутный read-only sync-кандидат с dry-run по умолчанию;

- единый `orders/ready-for-pickup` с legacy fallback;
- carrier confirmation ingress/readback и защита финальной РТУ;
- 1С source package для native-8.2 merge, feature flag выключен.

Production release и минутный cron уже активны. Внешние события и стадии
СДЭК/Почты уже ведет действующая интеграция Bitrix24; `pricing-service` не
дублирует этот контур. Не завершено связывание внутреннего водительского плеча
с существующим внешним CRM-flow. Отдельный реквизит точки самовывоза собран в
production-based candidate другой задачи, но в рабочую 1С еще не установлен.

Окружение:

- `pricing-service.service` работает на `127.0.0.1:18080`;
- nginx проксирует `price.mm.offonika.ru`;
- webhook health отвечает `200`, webhook без secret отвечает `401`;
- отдельный `pricing-logistics-bot.service` может быть disabled/inactive при
  работе через webhook;
- в локальной БД логистики на момент проверки были справочники и тестовые
  перемещения, все в состоянии `at_warehouse`.

Следующая волна кода:

- при необходимости — только техническое закрытие внутреннего водительского
  плеча по readback Bitrix24 без отображения внешнего статуса;
- установка и readback отдельного реквизита точки самовывоза выполняются в
  связанной задаче 1С, а не в `pricing-service`;
- условное обновление state по `version` для настоящего optimistic locking;
- runtime-приёмка ТЗП v3 и контроль порогов 5/10 секунд;
- отдельный корпоративный lookup-код и его печать после утверждения следующего
  этапа.

Операционный риск: старый лог `/var/log/pricing/logistics_bot.log` мог хранить
полный Telegram bot token в ошибках. Перед production-пилотом нужно
ротировать/очистить этот лог и убедиться, что логирование Telegram ошибок
маскирует token.
