# Tech Design: логистика Bitrix24, Telegram и web fallback

Актуализировано 2026-09-12. Выпуск №225 находится в реализации, факт production
публикации и device smoke подтверждаются отдельно в канонической спецификации.

## 1. Цель

Вынести логистический контур подтверждения перемещений во внешний сервис с
Telegram-ботом, оставив 1С системой учета для документов
`ПеремещениеТоваров`, РТУ, складов, остатков и учетных справочников.

MVP должен закрыть сценарии:

- передача пакета водителю;
- приемка пакета в точке выгрузки;
- просмотр ожидаемых доставок;
- монитор текущего логистического состояния;
- аудит событий по каждой логистической единице.

AS-IS процесс транспортной службы зафиксирован в
[LogisticsTransportAsIs.md](LogisticsTransportAsIs.md).

## 2. Границы ответственности

### 2.1. 1С остается источником истины для

- документов `ПеремещениеТоваров`;
- документов `РеализацияТоваровУслуг` для потока интернет-заказов;
- складов, магазинов, центрального склада;
- учетных сотрудников/физлиц (операционный список водителей — из Bitrix24);
- печатного штрихкода/QR документа или пакета;
- бизнес-атрибутов документов: откуда, куда, номер, дата, проведение.

### 2.2. Внешний сервис становится источником истины для

- логистического статуса внутреннего пилота `На складе / В пути`;
- текущей точки нахождения пакета;
- ожидаемой точки выгрузки;
- водителя в текущем рейсе;
- истории логистических событий;
- UX-слоев для сканирования и подтверждения: Bitrix24 как основной интерфейс,
  Telegram и web fallback как резерв.

### 2.3. Telegram-бот отвечает только за UX

Бот не хранит бизнес-состояние. Он вызывает backend API, а вся валидация, state machine и аудит живут во внешнем сервисе.

Telegram не должен быть единственной точкой выполнения операций. На случай
блокировок, деградации Telegram или работы только через VPN нужен web fallback
на том же backend API: браузерная страница передачи и приемки, которая принимает
тот же QR/lookup-код и проводит те же draft/confirm операции.

### 2.4. Термины

- `Логистическая единица` - один физический пакет, который сканируют и ведут в
  state machine. В текущем коде она хранится в legacy-таблице
  `logistics_transfer`.
- `source_document_type` - тип документа-источника: `transfer` для
  `ПеремещениеТоваров`, `rtu` для `РеализацияТоваровУслуг`.
- `external_id` - стабильная ссылка на документ-источник в 1С. Уникальность
  должна проверяться в паре `(source_document_type, external_id)`.
- `source_warehouse_id` - склад, где пакет физически лежит перед первым плечом.
- `document_target_warehouse_id` - склад-получатель в документе 1С. Для
  `ПеремещениеТоваров` в пилоте это транзит Москвы.
- `target_warehouse_id` - финальный склад-получатель логистической единицы.
- `current_warehouse_id` - где пакет лежит сейчас, если он не в пути.
- `dropoff_warehouse_id` - куда водитель должен сдать пакет в текущем плече.

## 3. Бизнес-правила MVP

Раздел фиксирует целевую модель пилота. Реализация покрывает передачу/приемку,
ожидаемые доставки, монитор, историю и РТУ. Внешние службы и ручной допуск не
входят в текущий внутренний пилот.

- Для `ПеремещениеТоваров`: `1 документ = 1 пакет`.
- Для РТУ пилота: `1 РТУ = 1 логистическая единица`.
- Передачу водителю сканирует отправитель.
- Приемку сканирует получатель.
- Водитель не сканирует.
- Конечный получатель по документу может не совпадать с текущей точкой выгрузки.
- Если точка выгрузки не по пути, используется двухплечевая схема через центральный склад.
- В MVP документ `ПеремещениеТоваров` считается готовым к логистической передаче только по текущим признакам 1С, без доработки формы 1С.

### 3.1. Readiness gate документа 1С

Для пилота во внешний сервис попадают только документы `ПеремещениеТоваров`, где склад-получатель является транзитным складом.

Документ считается готовым к передаче водителю, если одновременно выполнены
все условия:

1. Документ не помечен на удаление.
2. Документ проведен.
3. `СкладПолучатель` документа = транзит Москвы (`_Reference80._Code = РБ0000027`).
4. Документ распечатан.
5. В истории документа есть событие сканирования / `Отсканирован`.

Правила по нижним флагам формы:

- `Отправка подтверждена` не используется как отдельный gate: по текущему процессу без подтвержденной отправки документ не проводится.
- `Проверен` в пилоте не обязателен; после появления отдельной роли сотрудников проверки этот флаг нужно добавить в readiness gate.
- `Распечатан` обязателен для пилота. Известный риск: очень редко флаг печати не проставляется, примерно один случай на несколько тысяч документов; такие случаи разбираются как исключения.
- если печать фактически была, но флаг не проставился, документ остаётся вне
  текущего пилота; ручной допуск отложен в отдельный backlog.

Одного факта проведения документа недостаточно для запуска логистической передачи.

Существующий internal endpoint `manual_ready_override` не доступен в Bitrix24
UX текущего пилота. Если его включение будет отдельно утверждено, он сможет
обходить только сбой флага печати и не сможет обходить остальные проверки.

Фактический склад-получатель для Telegram определяется через реквизит
`Подразделение` документа. В справочнике `Подразделения` к подразделению
привязан склад; именно этот склад становится точкой выгрузки / получателем
пакета во внешнем сервисе. `СкладПолучатель` документа при этом остается
признаком маршрутизации через транзит.

### 3.2. Несколько плеч доставки

Один документ `ПеремещениеТоваров` в логистическом сервисе остается одним
пакетом, но пакет может ехать несколькими плечами.

Ключевые понятия:

- `target_warehouse_id` - финальный склад-получатель из
  `Подразделение.осиСклад`;
- `current_warehouse_id` - где пакет физически лежит сейчас, если он не в пути;
- `dropoff_warehouse_id` - куда водитель должен сдать пакет в текущем рейсе.

Правило маршрутизации:

- если водитель забирает перемещение из подразделения A, а подразделение B есть
  по пути текущего маршрута, то текущее плечо идет напрямую в B:
  `dropoff_warehouse_id = target_warehouse_id`;
- если B не по пути, водитель сдает пакет на центральный транзитный склад:
  `dropoff_warehouse_id = central_transit_warehouse_id`;
- после приемки на центральном транзитном складе пакет снова становится
  `at_warehouse`, но не считается доставленным, если
  `current_warehouse_id != target_warehouse_id`;
- на следующий день или в ближайший подходящий рейс центральный склад передает
  этот же пакет водителю следующим плечом до финального получателя.

Для MVP не нужен полноценный оптимизатор маршрутов. Достаточно:

- хранить стандартный маршрут первой машины как упорядоченный список
  складов/подразделений:
  `Щелковская -> Савеловская -> Митино -> Пресня -> Горбушка -> Теплый стан -> Гранд Юг -> Склад -> Люблино`;
- при передаче водителю показывать подсказку: `везти напрямую` или
  `сдать на центральный транзит`;
- разрешить логисту/отправителю вручную выбрать точку сдачи текущего плеча;
- в аудите сохранять каждое плечо отдельными событиями `handed_to_driver` и
  `accepted_at_point`.

Завершенной логистическая единица считается только когда пакет принят на
финальном складе:
`status = at_warehouse` и `current_warehouse_id = target_warehouse_id`.

### 3.3. Перемещения Через Внешние Службы Доставки

Отдельный поток - перемещения в другие города и подразделения, которые второй
водитель отвозит сторонним службам доставки.

Для следующей волны пилота храним простой справочник внешних служб, без
интеграции с их API:

- СДЭК;
- Почта России;
- другие транспортные компании по задаче.

Такой пакет не должен считаться доставленным в подразделение в момент передачи
СДЭК/Почте. В этот момент он выходит из контура нашего водителя, но финальная
приемка подразделением еще не выполнена.

Для следующей волны пилота правило такое:

- внутренний сотрудник передает пакет второму водителю как обычное плечо;
- точка сдачи текущего плеча - офис/терминал внешней службы доставки,
  заведенный как `logistics_warehouse.kind = external_terminal`;
- после передачи внешней службе фиксируется событие
  `handed_to_external_carrier`;
- в событии обязательно сохраняется служба доставки из справочника; номер
  накладной/трек-номер, город и комментарий можно заполнять как дополнительные
  поля, если они есть на момент передачи;
- статус пакета становится `with_external_carrier`;
- финально перемещение закрывается только после приемки получающим
  подразделением событием `accepted_from_external_carrier`.

В этой волне можно не интегрироваться с API СДЭК/Почты. Достаточно хранить факт
передачи внешней службе и название службы; трек-номер или номер накладной
остаются дополнительными полями, если они есть.

### 3.4. Заказы Сайта И РТУ

Заказы интернет-магазина, которые нужно физически доставить/передать в
подразделение, не должны попадать в логистику напрямую из `ЗаказПокупателя`.

Текущий процесс 1С:

- сайт создает `ЗаказПокупателя`;
- на основании заказа создается `РеализацияТоваровУслуг` (`РТУ`);
- собирается уже `РТУ`;
- после готовности `РТУ` появляется логистическая задача.

Для этого потока действует отдельный integration contract:
[IntegrationContract.LogisticsSiteOrders1C.md](IntegrationContract.LogisticsSiteOrders1C.md).

Readiness gate для РТУ в следующей волне пилота:

1. РТУ не помечена на удаление.
2. РТУ проведена.
3. В истории РТУ есть событие `Распечатан`.
4. В истории РТУ есть событие `Собран`.

Служебный фильтр по пометке удаления обязателен всегда. Бизнес-готовность РТУ
для пилота дают три признака: проведена, распечатана, собрана.

Событие `Сборка через РМ закончена` для РТУ на MVP не ждем и 1С ради него не
дорабатываем: текущего события `Собран` достаточно для запуска пилота.

Склад получателя для самовывоза определяем без отдельного поля `ПВЗ`:

- из заказа берем `Способ доставки с сайта`;
- если это `Самовывоз`, берем адрес из `Дополнение` / `Адрес доставки`;
- сопоставляем адрес с карточкой подразделения;
- склад получателя берем из `Подразделение.осиСклад`;
- если адрес не сопоставился однозначно, задача попадает в `manual_review`, где
  логист вручную выбирает подразделение-получатель.

Для сканирования РТУ используем печатный штрихкод/QR с расходной накладной. В
коде синхронизации нужно зафиксировать, какое значение приходит со сканера
после чтения этого кода: номер РТУ, ссылка 1С, номер заказа сайта или отдельная
строка штрихкода. После этого lookup должен однозначно находить одну РТУ.

## 4. Архитектура решения

```text
1С
  -> выгрузка справочников, перемещений и готовых РТУ
  -> опционально прием обратно логистических событий

External Logistics Service (FastAPI + PostgreSQL)
  -> хранение logistics state
  -> хранение audit trail
  -> API для Telegram-бота и web fallback
  -> API для sync с 1С
  -> отчеты foundation и печатные формы следующей волны

Telegram Bot
  -> авторизация пользователя
  -> сканирование lookup-кодов
  -> создание handoff / receipt draft
  -> подтверждение операций
  -> просмотр expected deliveries

Web Fallback UI
  -> авторизация пользователя
  -> ввод QR/lookup-кода с камеры, ручного сканера или клавиатуры
  -> создание handoff / receipt draft
  -> подтверждение операций через те же backend endpoints
```

#### `logistics_driver`

- `bitrix_user_id` (nullable, unique; не сопоставляется автоматически по ФИО)
- `work_position`
- `shift_status`, `shift_checked_at`, `synced_at`
- `external_id`
- `full_name`
- `phone`
- `is_active`
- `created_at`
- `updated_at`

#### `logistics_user`

- `id`
- `external_id`
- `telegram_user_id`
- `username`
- `full_name`
- `role` (`sender`, `receiver`, `logist`, `returns`, `admin`); роль `returns`
  использует ту же Bitrix24 session-auth схему для входящих клиентских возвратов,
  не требует склада и не даёт доступ к операциям внутренних перемещений;
- `default_warehouse_id`
- `is_active`
- `created_at`
- `updated_at`

Рекомендованный источник пользователей для MVP - Bitrix24: там удобно завести
`telegram_user_id`, роль логистики и привязку к складу/подразделению как
административные поля без доработки 1С. Справочники складов и подразделений
остаются из 1С. Сотрудника из Bitrix можно дополнительно сопоставлять с
сотрудником/физлицом 1С по телефону, email или внешнему идентификатору, но это
не должно блокировать авторизацию в Telegram на старте.

ОТМЕНЕНО 2026-09-12: импорт водителей из 1С как источник новых передач после
переключения. `user.get` Bitrix24 отбирает ACTIVE и точную нормализованную
должность «Водитель», без фильтра подразделений. Курьер — другая должность.
`timeman.status` даёт предупреждение о смене, не запрет. Полная выгрузка
атомарно обновляет справочник и DB marker; неполная не применяется.
Водитель не сканирует: это делают отправитель и получатель.

### 5.2. Логистические Единицы

#### `logistics_transfer`

Целевой состав таблицы после следующей миграции:

- `id`
- `source_document_type` (`transfer`, `rtu`)
- `external_id`
- `document_number`
- `document_date`
- `origin_order_external_id`
- `site_order_number`
- `source_warehouse_id`
- `document_target_warehouse_id` (следующая миграция; для
  `ПеремещениеТоваров` это транзитный склад документа)
- `target_warehouse_id`
- `final_recipient_name`
- `barcode`
- `onec_status`
- `onec_deleted`
- `payload` (`jsonb` с исходным payload из 1С)
- `created_at`
- `updated_at`

Индексы:

- уникальный индекс по `(source_document_type, external_id)`
- уникальный индекс по `barcode`, если поле заполнено и выбранный lookup
  действительно уникален в окне пилота

Текущий foundation в коде уже использует таблицу `logistics_transfer` и
одиночный `external_id`; перед добавлением РТУ нужна миграция, которая
безопасно расширит модель до `source_document_type` и сохранит совместимость с
существующими перемещениями.

Пока lookup со сканера не подтвержден, `barcode` нельзя считать обязательным
источником поиска для всех типов документов. Для следующей миграции нужно
разрешить хранить выбранный lookup в одном из вариантов:

- `barcode` / QR-строка;
- номер документа;
- ссылка 1С;
- номер заказа сайта.

Для нового QR на печатной форме `ПеремещениеТоваров` основной формат lookup:

```text
MMLOG1|transfer|<1c_document_ref>
```

Это версионированный payload, который не конфликтует со старым линейным
штрихкодом на форме. В foundation его можно хранить в существующем поле
`barcode`; после миграции лучше вынести в отдельное поле `lookup_code`.

Временный fallback, если ссылка 1С недоступна в печатном макете:

```text
MMLOG1|transfer-number|<full_document_number>|<document_date_yyyyMMdd>
```

Fallback разрешен только после проверки уникальности полного номера и даты в
окне пилота. Короткий номер с формы, например `34486`, как самостоятельный
lookup не подходит.

### 5.3. Текущее состояние

#### `logistics_transfer_state`

- `transfer_id`
- `status` (`at_warehouse`, `in_transit`, `with_external_carrier`)
- `current_warehouse_id`
- `dropoff_warehouse_id`
- `driver_id`
- `last_event_type`
- `last_event_at`
- `last_user_id`
- `last_document_ref`
- `version`
- `updated_at`

Назначение:

- хранит только текущий логистический state;
- обновляется только через append-only события.
- поддерживает много плеч: `dropoff_warehouse_id` всегда относится только к
  текущему рейсу, а финальный получатель хранится в
  `logistics_transfer.target_warehouse_id`.

- `dropoff_warehouse_id`

- `idempotency_key`

Типы событий:

Для события `handed_to_external_carrier` в `meta` обязательно поле

пользователя-логиста.

Индексы:

- уникальный индекс по `idempotency_key`, где он заполнен;
- индекс по `(transfer_id, event_at desc)`.

### 5.5. Внешние Службы Доставки

Для следующей волны пилота достаточно простого справочника:

#### `logistics_external_carrier`

- `id`
- `name`
- `is_active`
- `created_at`
- `updated_at`

Терминалы внешних служб не заводим отдельной таблицей. Их достаточно хранить как
склады с `kind = external_terminal`, чтобы существующий
`dropoff_warehouse_id` мог указывать, куда водитель должен сдать пакет.

API-интеграции с перевозчиками не входят в пилот; справочник нужен только для
нормализации названий в событиях и отчетах.

### 5.6. Manual Review / Override

Два сценария не должны ломать автоматический поток:

- документ `ПеремещениеТоваров` готов физически, но `_Fld8954` не проставился;
- РТУ самовывоза не удалось однозначно сопоставить с подразделением по адресу.

Для этого нужен административный workflow:

- `manual_ready_override` допускает документ к логистике только с обязательной
  причиной и пользователем-логистом;
- ручной допуск создает/обновляет логистическую единицу из документа 1С и
  пишет событие `manual_ready_override`; прямое редактирование state без события
  запрещено;
- `manual_review` по РТУ хранит исходный payload, кандидатов подразделений и
  выбранное логистом подразделение-получатель;
- все решения пишутся в audit trail, а не редактируют state напрямую.

## 6. State machine

### 6.1. Состояния

- `at_warehouse`
- `in_transit`
- `with_external_carrier`

### 6.2. Переходы

#### Передача водителю

Событие: `handed_to_driver`

Переход:

- `at_warehouse -> in_transit`

Проверки:

- логистическая единица найдена по lookup-коду;
- если state отсутствует, считаем, что пакет находится на складе-отправителе из 1С;
- если state есть, статус должен быть `at_warehouse`;
- текущий склад должен совпадать со складом пользователя;
- нельзя повторно передать уже `in_transit` логистическую единицу.

Результат:

- `status = in_transit`
- `current_warehouse_id = null`
- `dropoff_warehouse_id = выбранная точка выгрузки текущего плеча`
- `driver_id = выбранный водитель`

Примечание:

- если финальный получатель по пути, точка выгрузки текущего плеча равна
  `target_warehouse_id`;
- если финальный получатель не по пути, точка выгрузки текущего плеча равна
  центральному транзитному складу.

#### Приемка в точке

Событие: `accepted_at_point`

Переход:

- `in_transit -> at_warehouse`

Проверки:

- логистическая единица найдена;
- статус должен быть `in_transit`;
- `dropoff_warehouse_id` должен совпадать со складом приемки пользователя;
- если уже `at_warehouse`, возвращаем сообщение `уже принято ранее`.

Результат:

- `status = at_warehouse`
- `current_warehouse_id = склад приемки`
- `dropoff_warehouse_id = null`
- `driver_id = null`

Если `current_warehouse_id = target_warehouse_id`, логистическая единица
доставлена в финальную точку. Если `current_warehouse_id != target_warehouse_id`,
пакет лежит на промежуточном складе и должен попасть в очередь следующей
отгрузки.

#### Передача внешней службе доставки

Событие: `handed_to_external_carrier`

Переход:

- `in_transit -> with_external_carrier`

Проверки:

- логистическая единица найдена;
- текущее плечо должно быть назначено на `warehouse.kind = external_terminal`;
- операцию выполняет логист/админ или уполномоченный пользователь;
- должна быть указана служба доставки; номер накладной/трек-номер, город и
  терминал заполняются, если они уже есть.

Результат:

- `status = with_external_carrier`
- `current_warehouse_id = null`
- `dropoff_warehouse_id = null`
- `driver_id = null`
- в `event.meta` сохраняется `carrier_name`; `tracking_number`, `city` и
  `carrier_terminal` заполняются опционально.

Для списка ожидаемых приемок от внешних служб используется пара
`status = with_external_carrier` и `target_warehouse_id`; `dropoff_warehouse_id`
не перегружаем, потому что внутреннее водительское плечо уже завершено.

#### Приемка после внешней доставки

Событие: `accepted_from_external_carrier`

Переход:

- `with_external_carrier -> at_warehouse`

Проверки:

- логистическая единица найдена;
- пользователь принимает на складе финального подразделения;
- склад приемки должен совпадать с `target_warehouse_id`.

Результат:

- `status = at_warehouse`
- `current_warehouse_id = склад приемки`
- `dropoff_warehouse_id = null`
- `driver_id = null`

#### Отмена передачи

Событие: `handoff_cancelled`

Переход:

- `in_transit -> at_warehouse`

Условие:

- разрешено, если перемещение еще не принято в точке.

#### Возврат

Событие: `returned`

Переход:

- `in_transit -> at_warehouse`

Условие:

- фактический склад приемки задается явно;
- в комментарии фиксируется причина возврата.

#### Инцидент

Событие: `incident`

Переход:

- состояние не меняется.

#### Ручной допуск готового документа

Событие: `manual_ready_override`

Переход:

- если логистическая единица еще не создана: создается state `at_warehouse`;
- если логистическая единица уже есть: state не меняется.

Проверки:

- операцию выполняет логист/админ;
- причина обязательна;
- документ не помечен на удаление;
- документ проведен;
- склад-получатель документа соответствует транзиту Москвы;
- фактический склад-получатель через `Подразделение.осиСклад` определен;
- выбранный lookup для сканирования подтвержден и уникален.

Результат:

- логистическая единица доступна для handoff;
- в `event.meta` сохраняются причина, пользователь, исходные флаги 1С и список
  условий, которые были обойдены. Для этого workflow допускается обходить только
  `printed = false`.

## 7. REST API

Все endpoints `/api/logistics/*` в текущем сервисе являются backend/internal API
и защищены внутренним токеном. Telegram-бот и web fallback вызывают их через
backend; клиентские UX-слои не хранят state и не получают прямой доступ к БД.

### 7.1. UX-facing API

#### `POST /api/logistics/auth/telegram`

Назначение:

- связать `telegram_user_id` с пользователем сервиса;
- вернуть роль и default warehouse.

Для web fallback нужен отдельный backend-auth слой: существующая авторизация
`pricing-service`, внутренняя учетная запись или другой корпоративный способ
входа. После входа backend обязан применять те же роли и warehouse binding, что
и для Telegram.

#### Lookup логистической единицы по сканируемому коду

Отдельного публичного `GET` endpoint для lookup нет:
поиск выполняется внутри endpoints сканирования draft:
`POST /api/logistics/handoffs/draft/{draft_id}/scan` и
`POST /api/logistics/receipts/draft/{draft_id}/scan`.

Если нужен отдельный lookup endpoint для UI/debug, legacy-compatible вариант:
`GET /api/logistics/transfers/by-barcode/{barcode}`. После добавления РТУ лучше
добавить generic alias `/api/logistics/units/lookup`.

#### `POST /api/logistics/handoffs/draft`

Назначение:

- создать черновик передачи водителю.

Вход:

- `warehouse_id`
- `driver_id`
- `default_dropoff_warehouse_id`

#### `POST /api/logistics/handoffs/draft/{draft_id}/scan`

Назначение:

- добавить строку в draft по lookup-коду.

Вход:

- `barcode` / текущий lookup-код

Проверки:

- lookup-код найден;
- в draft нет дубля;
- логистическая единица допустима к передаче.

#### `POST /api/logistics/handoffs/draft/{draft_id}/confirm`

Назначение:

- провести передачу водителю.

Вход:

- `comment`
- `idempotency_key`

#### `POST /api/logistics/receipts/draft`

Назначение:

- создать черновик приемки.

Вход:

- `warehouse_id`
- `driver_id` (optional)

#### `POST /api/logistics/receipts/draft/{draft_id}/scan`

Назначение:

- добавить логистическую единицу в draft приемки.

Вход:

- `barcode` / текущий lookup-код

#### `POST /api/logistics/receipts/draft/{draft_id}/confirm`

Назначение:

- провести приемку.

Вход:

- `comment`
- `idempotency_key`

#### `GET /api/logistics/expected-deliveries`

Фильтры:

- `warehouse_id`
- `driver_id`
- `period_from`
- `period_to`

Примечание: `period_from` / `period_to` относятся к следующей волне. Текущий
foundation API поддерживает фильтры `warehouse_id` и `driver_id`.

Назначение:

- вернуть список логистических единиц, где `status = in_transit` и
  `dropoff_warehouse_id = warehouse_id`.

#### `GET /api/logistics/monitor`

Фильтры:

- `status`
- `warehouse_id`
- `driver_id`
- `final_recipient`
- `date_from`
- `date_to`

Примечание: `date_from` / `date_to` относятся к следующей волне. Текущий
foundation API поддерживает `status`, `warehouse_id`, `driver_id`,
`final_recipient`.

Назначение:

- вернуть сводный монитор текущего состояния логистических единиц.

#### `GET /api/logistics/transfers/{transfer_id}/history`

Назначение:

- вернуть историю событий и фото по логистической единице.

#### `POST /api/logistics/transfers/{transfer_id}/incident`

Назначение:

- записать событие `incident` без изменения основного state.

#### `POST /api/logistics/transfers/{transfer_id}/return`

Назначение:

- записать событие `returned`; для текущей реализации нужен `warehouse_id`,
  потому что возврат меняет фактический склад.

### 7.2. Sync API для 1С и административных справочников

#### `POST /api/logistics/sync/warehouses`

- импорт складов и магазинов из 1С

#### `POST /api/logistics/sync/drivers`

- legacy импорт до переключения на Bitrix24; после первого подтверждённого
  snapshot возвращает 409, в том числе при остановленном новом cron.

#### Дополнения №225

- `PATCH /api/bitrix/logistics/handoffs/draft/{id}/driver` — `driver_id`;
  только открытая собственная передача, действующий водитель, аудит в
  `logistics_draft_audit`. Сканированные документы сохраняются.
- `GET /api/bitrix/logistics/pending-documents` — `operation`, `warehouse_id`,
  необязательные `draft_id`, `driver_id`, `offset`, `limit` (1–200).
  Документы/счётчики/свежесть РТУ и перемещений; один SQL snapshot для страницы
  и счётчиков, без событий/разборов. Готовность общая со scan/confirm.
- Те же сервисы доступны web fallback; Telegram использует `/drivers`,
  `/driver <id>` и `/pending [страница]`. Нового интерфейса водителя нет.
- Существующие scan/confirm URL и тела сохранены. Ответ скана дополняется
  `scan_result=added/already_scanned`; совпадение проверяется по единице,
  короткий и полный QR одного документа не дублируют позиции.
- Подтверждение заново проверяет активность водителя под блокировкой строки;
  повтор ранее подтверждённой передачи — no-op. Приёмка доставок бывшего
  водителя разрешена. Свежесть смены более 180 секунд означает «Неизвестно».

#### `POST /api/logistics/sync/users`

- импорт пользователей, Telegram ID, ролей и привязок к складам из Bitrix24
  либо из локальной административной таблицы на время пилота

#### `POST /api/logistics/sync/transfers`

- импорт открытых перемещений и выбранного lookup-кода для сканирования;
- legacy alias выставляет `source_document_type = transfer`.

#### `POST /api/logistics/sync/units`

Generic internal endpoint принимает перемещения и РТУ. Штатный production flow
РТУ не вызывает браузерный endpoint, а запускает фоновую задачу
`tasks/sync_logistics_rtu_from_onec.py`, которая:

- импорт готовых РТУ интернет-заказов;
- применяет gate `не помечена на удаление` + `Проведена` + история
  `Распечатан` + история `Собран`;
- при неоднозначном адресе самовывоза создает запись `manual_review`, а не
  логистическую единицу для автоматической отправки.

### 7.3. Internal endpoints вне текущего пользовательского пилота

#### `POST /api/logistics/transfers/{transfer_id}/external-carrier/handoff`

Endpoint реализован под internal token, но не включён в Bitrix24 UX пилота:

- опционально принимает `tracking_number`, `city`, `carrier_terminal`,

- переводит state в `with_external_carrier`.

#### `POST /api/logistics/transfers/{transfer_id}/external-carrier/accept`

Endpoint реализован под internal token, но не включён в Bitrix24 UX пилота:

- фиксирует `accepted_from_external_carrier`;
- доступен получателю финального склада;
- закрывает логистическую единицу только при приемке на `target_warehouse_id`.

#### `POST /api/logistics/manual-ready-overrides`

Endpoint реализован под internal token, но ручной допуск запрещён правилами
текущего пилота:

- принимает ссылку на документ 1С или номер документа;
- требует обязательную причину;
- создает/обновляет логистическую единицу и пишет `manual_ready_override`;
- не пишет изменения обратно в 1С.

#### `GET /api/logistics/manual-review`

Read-only endpoint реализован под internal token; Bitrix24 использует отдельный

- показывает РТУ, которые не удалось автоматически сопоставить с подразделением
  или lookup;
- позволяет логисту выбрать подразделение-получатель и продолжить sync.

## 8. UX: Telegram и Web Fallback

### 8.1. Команды

- `/start`
- `/handoff`
- `/receive`
- `/expected`
- `/monitor`
- `/help`

### 8.2. Основное меню

- `Передать водителю`
- `Принять от водителя`
- `Ожидаемые доставки`
- `Монитор`
- `Инцидент`

### 8.3. Сценарий передачи

1. Пользователь выбирает водителя.
2. Пользователь выбирает текущую точку выгрузки.
3. Бот открывает режим сканирования.
4. Каждый lookup-код отправляется в `handoff draft scan`.
5. Бот показывает:
   - список принятых сканов;
   - список ошибок без модальных окон.
6. Пользователь нажимает `Провести`.

### 8.4. Сценарий приемки

1. Пользователь открывает приемку.
2. Бот определяет склад из профиля пользователя или предлагает выбрать его.
3. Пользователь сканирует lookup-код.
4. Бот выводит валидные позиции и ошибки по неверной точке выгрузки или дублям.
5. Пользователь нажимает `Подтвердить приемку`.

### 8.5. Сценарий ожидаемых доставок

Бот показывает логистические единицы:

- номер документа;
- склад отправителя;
- конечного получателя;
- водителя;
- ожидаемую точку выгрузки;
- время последнего события.

### 8.6. Web Fallback UX

Web fallback нужен как обязательный резерв на случай, если Telegram недоступен,
тормозит или работает только через VPN. Это не отдельная бизнес-логика, а второй
тонкий UX-слой над теми же backend endpoints.

Минимальный состав:

- страница `Передать водителю`;
- страница `Принять в точке`;
- ввод QR/lookup-кода через камеру браузера, ручной сканер в режиме клавиатуры
  или обычное поле ввода;
- выбор водителя; направление автоматически из документа, без ручной подмены;
- список валидных сканов и ошибок перед подтверждением;
- кнопка `Провести` / `Подтвердить приемку`.

Технические правила:

- QR payload не должен быть Telegram-specific: строка `MMLOG1|...` одинаково
  работает в Telegram и в web fallback;
- web fallback использует те же `handoff draft`, `receipt draft`, `scan` и
  `confirm` endpoints;
- роли, склад пользователя и warehouse binding проверяет backend;
- браузер не хранит логистическое состояние, кроме текущего draft/session;
- `confirm` отправляет `idempotency_key`;
- операция считается проведенной только после успешного ответа backend; локальное
  сообщение в браузере не является фактом передачи или приемки.

## 9. Минимальный контракт обмена с 1С

Целевой payload следующей волны по логистической единице:

```json
{
  "source_document_type": "transfer",
  "external_id": "uuid-from-1c",
  "document_number": "ПТ-000123",
  "document_date": "2026-03-28T10:15:00Z",
  "source_warehouse_external_id": "store-01",
  "document_target_warehouse_external_id": "moscow-transit",
  "target_warehouse_external_id": "store-05",
  "final_recipient_name": "Магазин 5",
  "barcode": "4601234567890",
  "onec_status": "posted"
}
```

Критично:

- `external_id` должен быть стабильным;
- для `ПеремещениеТоваров` `target_warehouse_external_id` должен указывать на
  фактический склад-получатель из `Подразделение.осиСклад`, а не на
  `СкладПолучатель` документа 1С;
- `document_target_warehouse_external_id` хранится отдельной колонкой и нужен
  для аудита маршрутизации через транзит;
- выбранный lookup со сканера должен однозначно находить одну логистическую
  единицу: перемещение или РТУ;
- справочники складов и логистических пользователей должны синхронизироваться
  раньше логистических единиц.

Generic `/sync/units` принимает `source_document_type` и
`document_target_warehouse_external_id`; legacy `/sync/transfers` сохраняет
совместимость и выставляет тип `transfer`. `target_warehouse_external_id`
указывает фактического получателя, а отдельное document target поле сохраняет
учётный транзит.

Поле `barcode` в текущем API - legacy-название. До отдельной миграции оно может
содержать выбранный lookup-код, если сканер читает не `_Document178._Fld9256`, а
номер документа, ссылку 1С или QR-строку с печатной формы.

Перед кодом синхронизации нужно сканером снять фактическое значение с печатной
формы `ПеремещениеТоваров` и расходной накладной РТУ: это может быть номер
документа, ссылка 1С, номер заказа сайта или отдельная строка QR/штрихкода.
Для новой QR-доработки ожидаем значение с префиксом `MMLOG1|...`; старый
линейный штрихкод с формы не трогаем, пока не подтверждено, что он не нужен
существующему 1С-процессу.

## 10. Нефункциональные требования

- поиск по выбранному lookup-коду должен укладываться в `<= 1 сек`;
- confirm endpoints должны быть идемпотентными;
- обновление state и запись события должны происходить в одной транзакции;
- прямое редактирование текущего состояния без события запрещено;
- аудит должен сохранять пользователя, время, склад, водителя и комментарий;
- backend должен поддерживать optimistic locking по `version`;
- Telegram не должен быть единственной точкой отказа: для production-пилота
  нужен web fallback на `price.mm.offonika.ru` или другом внутреннем домене,
  использующий тот же backend API.

`version` участвует в условном ORM update. Если между чтением и commit состояние
изменилось, backend откатывает транзакцию и возвращает `409` с предложением
обновить данные.

## 12. Основные риски

- в 1С может не оказаться стабильного и уникального lookup-кода на уровне
  `1 логистическая единица = 1 пакет`;
- если пользователи меняют документы перемещений задним числом, внешний контур может расходиться с 1С;
- если в будущем один документ начнет соответствовать нескольким пакетам, потребуется отдельная сущность `package`;
- если перепутать `СкладПолучатель` документа с фактическим получателем из
  `Подразделение.осиСклад`, бот будет вести пакеты на транзит вместо магазина;
- если авторизацию UX-слоев не привязать жестко к складу и роли, будут ошибки в
  приемке и передаче;
- если Telegram недоступен, тормозит или работает только через VPN, процесс
  передачи/приемки может остановиться; снижение риска - web fallback на том же
  backend API, где QR lookup и confirm не завязаны на Telegram.

- `app/api/logistics*.py`
- `app/services/logistics/`
- `app/schemas/logistics.py`
- `app/models/logistics.py`
- `alembic/versions/*_add_logistics_tables.py`

Это позволяет:

- позже, если нагрузка вырастет, вынести логистику в отдельный сервис без изменения пользовательского UX.

## 14. Текущее Состояние Реализации На 2026-08-28

Production release из commit `28480e7` уже содержит модели и state machine,
Bitrix24 BFF и мобильный UI, Telegram/web fallback, короткий и полный QR,
фоновой постраничный RTU sync и транзакционный stage outbox.

Пилот ограничен маршрутом «Электроника на Пресне → Савёловский»:

- `LOGISTICS_BITRIX_APP_ENABLED=true`;
- `LOGISTICS_STAGE_AUTOMATION_ENABLED=true`;
- `PICKUP_READY_SMS_ENABLED=false`;
- список складов Bitrix/web fallback и создание черновиков ограничены тем же
  pilot allowlist; `admin` имеет обе операции только внутри пилотных складов;
- Арсений Кештов, Андрей Платонов и Максим Арустамов работают как `admin` на
  время пилота: им доступны все логистические операции на pilot allowlist без
  обхода финальных стадий и иных бизнес-проверок;
- RTU sync запускается каждую минуту с `flock`, 14-дневным окном и marker
  свежести 180 секунд;
- повторный RTU sync считает `updated` только для реально изменившихся единиц;
  неизменившийся документ обрабатывается как идемпотентный no-op;
- основной список ошибок фильтруется по pilot allowlist и скрывает legacy
  `rtu_external_carrier_unmapped` без удаления аудита;
- если QR относится к уже распознанной внешней доставке, `unknown_qr`
  автоматически закрывается, а сканер сообщает, что документ пока не входит во
  внутренний пилот, не включая внешний carrier flow;
- `logistics_transfer_state.version` используется как настоящий optimistic
  lock; stale update возвращает `409`;
- изменение маршрута в 1С после начала физического движения не перезаписывает
  активную логистическую единицу: один конфликт и одно событие аудита остаются
  открытыми для разбора без дублей от минутного sync;
- stage watchdog сообщает о `retry`/ручных конфликтах и падает при задержке
  пилотной строки более 30 секунд.
- строка stage outbox в `manual_review` блокирует все более поздние переходы
  того же заказа до разбора, поэтому приёмка не может обогнать конфликт передачи.

Ручной допуск готовности, ручное подтверждение СДЭК/Почты и обязательные
печатные формы исключены из ближайшей волны. После внутреннего пилота внешний
flow должен фиксировать внутреннее плечо водителя и получать приемку терминалом
из уже действующей интеграции Bitrix24, не создавая второй carrier adapter.

Операционный риск старого `/var/log/pricing/logistics_bot.log` закрывается
ротацией без чтения или публикации потенциального токена.

В production release `logistics-stability-20260829-c3505d7` опубликованы
fail-closed границы pilot allowlist для Bitrix24 и web fallback, блокировка
продолжения старого черновика вне пилота при сохранении возможности отмены,
выбор склада монитора для `admin`/`logist` и русские сообщения ошибок
сканирования.
