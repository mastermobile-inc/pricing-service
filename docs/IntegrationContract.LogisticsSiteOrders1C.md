финальные РТУ не создают дублирующих логистических единиц.

## Контракт scan-led-v1 (локальная реализация, ещё не установлена)

- План передаёт `payload.accounting_protocol = scan-led-v1`; каждая часть —
  `payload.lines`: `line_key`, `product_external_id`, `name`, `barcode`,
  `quantity`, опциональные `characteristic_external_id`, `series_external_id`.
- Подтверждение существующего черновика принимает `receipts`: `transfer_id`,
  `damaged`, `lines[{line_key, quantity}]`. Для конечной точки обязательна каждая
  ожидаемая строка, включая явный ноль. Скан пакета не подтверждает состав.
- `GET /api/logistics/accounting/events?limit=100` возвращает ожидающие события
  `event_id`, `operation` (`dispatch` / `final_receipt`), `status`, `payload`.
  Конечная приёмка выдаётся обработчику только после ACK отправки.
- `POST /api/logistics/accounting/events/{event_id}/ack` принимает
  `{status: applied, documents: [ссылка_1С]}` либо `{status: error, error: причина}`.
  Применённый результат неизменяем; повтор идентичного ACK безопасен.
  Оба адреса требуют существующий внутренний Bearer-токен логистики и не доступны
  через сотрудническую Bitrix/web-сессию.
- Ответ подтверждения содержит `accounting` по каждой новой упаковке: отдельно
  `receipt_status` и `accounting_status`. `discrepancy` блокирует выдачу независимо
  от физического положения и ACK отправки.
- `LOGISTICS_SCAN_ACCOUNTING_ENABLED=false` по умолчанию. Отключение запрещает
  новые физические команды и получение очереди для исполнения; завершённые
  подтверждения и ACK уже выполненных операций сохраняются. Миграция не допускает
  удаления журнала через downgrade. Не включать до native-проверки 1С.

Сервис не проводит документы сам. Потребитель очереди на стороне 1С и durable
защита повторного проведения в 1С ещё требуют реализации и native-приёмки.
Уникальность события в backend не является доказательством идемпотентности 1С.

## 1. Почему Это Отдельный Поток

Для заказов сайта нельзя считать готовность к логистике только по
`ЗаказПокупателя`.

В текущем процессе:

- сайт создает `Заказ покупателя`;
- на основании заказа создается `Реализация товаров и услуг` (`РТУ`);
- собирается уже `РТУ`, а не исходный заказ;
- физическое перемещение/выдача должно стартовать только после готовности `РТУ`.

Это совпадает с уже зафиксированным архитектурным решением: не двигать внешние
статусы по "сырым" документам 1С, а считать derived operational status во
внешнем backend.

## 5. Как Определять Склад Получателя

### 5.1. Контракт доставки v1

После rollout связанной задачи 1С №3484 заказ сайта передает снимок доставки:

| Поле | Назначение |
| --- | --- |
| `contract_version` | Версия контракта, для первого rollout — `1` |
| `delivery_code` | Стабильный код способа доставки |
| `execution_class` | Класс исполнения Wave 1 `01–06` |
| `region_xml_id` | Стабильный XML_ID региона |
| `source_warehouse_xml_id` | UUID/XML_ID склада исполнения |
| `payment_mode` | `included`, `carrier_direct`, `by_agreement` или `free` |
| `delivery_price` | Стоимость в валюте заказа |
| `tracking_policy` | `required`, `provider_order_id` или `none` |
| `provider_order_id` | Опциональный идентификатор заказа перевозчика |

`pricing-service` классифицирует способ прежде всего по `delivery_code`.
Строковое поле `site_delivery_method` используется только как fallback для
старых заказов, в которых код отсутствует. Если непустой код неизвестен либо
равен `OTHER`, строковое название не может его переопределить: РТУ направляется
в `manual_review`.

Поддерживаемые коды первого справочника:

- локальный: `PICKUP`;
- СДЭК/Почта: `CDEK_PVZ`, `CDEK_COURIER`, `RUSSIAN_POST`;
- курьерские и такси: `MM_COURIER`, `DOSTAVISTA`, `YANDEX_TAXI`;
- маршрутка Пятигорска: `MARSHRUTKA_PTG`;
- ручной разбор: `OTHER` и любой неизвестный код.

Существующие роботы Bitrix24 остаются владельцами внешних статусов СДЭК и
Почты России. `pricing-service` не создает повторные API-adapters, треки или
зеркальные внешние статусы. `MARSHRUTKA_PTG` классифицируется как внутреннее
плечо/передача без API перевозчика и без трека; legacy-флаг автоматической
передачи внешнему перевозчику для него запрещен. До настройки однозначной точки
передачи маршрутка остается в `manual_review`, а не получает фиктивный статус.

В первом релизе распознавание `DOSTAVISTA` и `YANDEX_TAXI` не означает включение
этих способов на сайте или создание интеграции с провайдером.

Для потока заказов сайта в MVP не нужна отдельная доработка поля `ПВЗ / пункт
выдачи`: склад получателя определяем через способ доставки и адрес самовывоза.

Правило для `Самовывоз`:

1. Берем `Способ доставки с сайта` из `_Document132._Fld9266`.
2. Если значение = `Самовывоз`, берем адрес из:
   - `_Document132._Fld2422` (`Дополнение к адресу`), приоритетно;
   - `_Document132._Fld2395` (`Адрес доставки`), fallback;
   - `_Document203._Fld4965` / `_Document203._Fld4952`, если в заказе пусто.
3. Ищем ровно один активный склад/точку в `logistics_warehouse`, где адрес
   совпадает с `payload.address_aliases`, `payload.aliases`, `payload.addresses`,
   `payload.address`, `payload.pickup_address`, названием или `external_id`.
   `payload.address_aliases` заполняется повторяемым read-only sync из
   `_Reference68._Fld9249 -> _Reference80`, а matching допускает не только
   полное вхождение строки, но и уверенное совпадение адресных токенов
   `улица/шоссе + дом + павильон`. Город, бренд и часы работы не считаются
   достаточным совпадением; если павильон указан в обеих строках и различается,
   документ уходит в `manual_review`.
4. Фактический склад-получатель берем из найденной записи
   `logistics_warehouse`.

Если адрес не сопоставился однозначно, документ должен попадать в
`manual_review`, а не в автоматическую логистическую очередь.

Подтвержденное бизнес-правило для локальной выдачи: если способ доставки -
внутренний `Самовывоз`, но все адресные поля пустые, либо однозначно найденный
склад получателя совпадает со складом РТУ, отдельная логистическая единица не
создается. РТУ остается в ТЗП исходного подразделения. Sync увеличивает счетчик
`local_pickup_skipped`, закрывает ставший неактуальным открытый `manual_review`
этой РТУ и не создаёт `logistics_transfer`.

ОТМЕНЕНО (2026-08-28): массовое исключение РТУ со способами доставки `СДЭК`,
`Почта России`, `Доставка курьером` в `rtu_external_carrier_unmapped`, а также
автоматический перевод таких РТУ в `with_external_carrier` системным событием
`handed_to_external_carrier` с `source = 1c_sync`. Причина: до внешнего
перевозчика заказ проходит физическое плечо нашего водителя, которое должно
подтверждаться сканированием, а не read-only синхронизацией.

Решение 2026-08-28: РТУ со способами доставки `СДЭК`, `Почта России` и
`Доставка курьером` после прохождения readiness gate создаются как
логистические единицы на исходном складе в состоянии `at_warehouse`.
Передача нашему водителю подтверждается только сканированием и событием
`handed_to_driver`.

ОТМЕНЕНО (2026-08-28): передачу внешнему перевозчику вручную подтверждает
водитель, логист либо сотрудник точки сдачи. Причина: сильный факт приемки
должен приходить от самой внешней службы доставки по API.

ОТМЕНЕНО (2026-08-28): `pricing-service` напрямую принимает API-события
перевозчика, создает `handed_to_external_carrier` с `source = carrier_api` и
сам переводит сделку в `IN_DELIVERY`. Причина: адаптеры СДЭК/Почты уже
подключены к Bitrix24 и действующие роботы CRM двигают сделки по их событиям.

Пока наш водитель везет заказ до СДЭК/Почты, логистическая единица находится в
`in_transit`, а CRM-сделка остается в `FINAL_INVOICE` / `Готов к отгрузке`.
После приемки внешней службой существующая интеграция Bitrix24 самостоятельно
ведет внешние стадии сделки. `pricing-service` не подключается к API
перевозчиков повторно и не создает дублирующий outbox. Внешние статусы не
зеркалируются в логистический монитор: пользователь видит их только по стадиям
сделки Bitrix24. Технический readback, если он потребуется для закрытия
внутреннего водительского плеча, не создает внешний пользовательский статус и
ничего не записывает обратно в CRM. Read-only синхронизация `1С` не создает ни
одно из этих физических событий.

Способ доставки однозначно определяет тип внешнего перевозчика. Если точка
сдачи/терминал для этого перевозчика еще не настроены, РТУ остается доступной
для распознавания QR, но ее отправка блокируется через `manual_review` до
настройки точки. Такой случай не считается неизвестным QR.

В internal `manual_review` логист разбирает неоднозначность и при необходимости
подтверждает склад/точку с обязательным аудитом исходной строки, выбранной
точки и пользователя. Это не ручной выбор направления в сценарии сканирования
и не обход readiness gate.

Дополнительный подтверждающий источник для aliases точек выдачи - публичная
страница `https://master-mobile.ru/contacts/`. Адреса с сайта можно применять
как `logistics_warehouse.payload.address_aliases` через
`tasks/apply_logistics_warehouse_alias_overrides.py`, сохраняя причину
`official master-mobile.ru contacts page`.

## 6. Readiness Gate РТУ Для Логистики

Действующее бизнес-правило пилота для готовности `РТУ` к логистической передаче:

1. РТУ не помечена на удаление.
2. РТУ проведена.
3. В истории РТУ есть событие `Распечатан`.
4. В истории РТУ есть событие `Собран`.

Пометка удаления - технический фильтр безопасности. Три бизнес-признака
готовности для пилота: РТУ проведена, распечатана и собрана. На текущей базе
признак печати для РТУ берем из истории `_InfoRg9448` по действию
`Распечатан`, пока отдельный флаг печати РТУ не подтвержден.

Это правило отличается от `ПеремещениеТоваров`, где раньше обсуждалось событие
`Отсканирован`.

Техническое наблюдение по текущей живой базе:

- для `_Document203` сейчас найдены события `Начата сборка`, `Выставлен сборщик`,
  `Собран`, `Распечатан`;
- событие `Сборка через РМ закончена` по `_Document203` сейчас не найдено;
- в выгрузке конфигурации событие `Сборка через РМ закончена` найдено в форме
  проверки `ПеремещениеТоваров`.

Практическое решение для пилота: 1С ради события `Сборка через РМ закончена` не
дорабатываем, используем текущее событие `Собран` как source of truth для РТУ.

## 7. Черновой SQL Для Текущей Базы

SQL ниже использует согласованное для этой волны событие `Собран`.
Перед production-кодом нужно подтвердить `_Fld9449_RTRef` для
`Документ.РеализацияТоваровУслуг` и добавить его в оба `EXISTS`, как это
сделано для `ПеремещениеТоваров`.

```sql
SELECT
    CONVERT(varchar(34), rtu._IDRRef, 1) AS rtu_external_id,
    rtu._Number AS rtu_number,
    rtu._Date_Time AS rtu_date,
    CONVERT(varchar(34), ord._IDRRef, 1) AS site_order_external_id,
    ord._Number AS onec_order_number,
    ord._Date_Time AS site_order_date,
    ord._Fld2425 AS site_order_number,
    ord._Fld9266 AS site_delivery_method,
    CAST(ord._Fld2422 AS nvarchar(max)) AS site_delivery_addition,
    CAST(ord._Fld2395 AS nvarchar(max)) AS site_delivery_address,
    CAST(rtu._Fld4965 AS nvarchar(max)) AS rtu_delivery_addition,
    CAST(rtu._Fld4952 AS nvarchar(max)) AS rtu_delivery_address,
    CONVERT(varchar(34), rtu._Fld4940RRef, 1) AS source_warehouse_external_id,
    wh._Code AS rtu_warehouse_code,
    wh._Description AS rtu_warehouse_name
FROM dbo._Document203 AS rtu WITH (NOLOCK)
JOIN dbo._Document132 AS ord WITH (NOLOCK)
    ON ord._IDRRef = rtu._Fld4939_RRRef
LEFT JOIN dbo._Reference80 AS wh WITH (NOLOCK)
    ON wh._IDRRef = rtu._Fld4940RRef
WHERE rtu._Marked = 0x00
  AND rtu._Posted = 0x01
  AND EXISTS (
      SELECT 1
      FROM dbo._InfoRg9448 AS print_event WITH (NOLOCK)
      WHERE print_event._Fld9449_RRRef = rtu._IDRRef
        AND print_event._Fld9454 = N'Распечатан'
  )
  AND EXISTS (
      SELECT 1
      FROM dbo._InfoRg9448 AS assembled_event WITH (NOLOCK)
      WHERE assembled_event._Fld9449_RRRef = rtu._IDRRef
        AND assembled_event._Fld9454 = N'Собран'
  );
```

## 8. Как Это Ложится В Логистику

Для внешнего сервиса это не `transfer` из документа `ПеремещениеТоваров`, а
отдельный тип логистической единицы:

- `source_document_type = rtu`;
- `external_id = _Document203._IDRRef`;
- `origin_order_external_id = _Document132._IDRRef`;
- `site_order_number = _Document132._Fld2425`;
- `lookup_code = MMLOG1|rtu|<rtu_external_id>|<site_order_number>` как
  внутреннее нормализованное значение backend;
- `barcode = lookup_code` для совместимости старых scan endpoints;
- `source_warehouse_id` берется из склада РТУ
  `_Document203._Fld4940RRef -> _Reference80`;
- до production-развертывания отдельного реквизита точки
  `target_warehouse_id` определяется прежде всего по точному реквизиту
  `ЗаказПокупателя.осиТочкаСамовывоза` (`_Document132._Fld10203RRef`), который
  сопоставляется с `payload.onec_departments[].external_id/code` карточки
  `logistics_warehouse`; адресное сопоставление применяется только для старых
  заказов с пустым реквизитом;
- production-реквизит `ЗаказПокупателя.осиТочкаСамовывоза` принимает
  `PICKUP_POINT = XML_ID` склада и описан в связанной задаче Codex
  [«Уточнить поле точки самовывоза»](codex://threads/01a0499c-af7c-78d0-8bea-64a994831eb5)
  и [спецификации 1С](../../1C_Dev_Workflow/docs/specs/ut103-task-107-pickup-point-field-candidate-2026-08-28.md);
  candidate пока не установлен в рабочую 1С, поэтому текущий адресный fallback
  сохраняется до отдельного разрешения, установки и readback;
- сканирование выполняется по печатному штрихкоду/QR на форме РТУ; backend
  принимает как текущий короткий формат без номера сайта, так и полный формат,
  хранимый в `lookup_code`, и должен однозначно находить одну РТУ;
- для внутреннего самовывоза движение идет через передачу водителю и приемку в
  подразделении; внешние стадии СДЭК/Почты ведет существующая интеграция
  Bitrix24 и в логистический monitor не копирует.

РТУ не должна двигать CRM/заказ как "выдано клиенту" только по факту создания
или проведения. Для клиента и Bitrix24 нужен derived status, например
`ready_for_dispatch`, пока физическая логистика не завершена.

Сервисный слой:

- extractor находится в `app/services/logistics_onec.py`;
- запуск из cron/ручной проверки: `tasks/sync_logistics_rtu_from_onec.py`;
- production cron установлен из immutable release, запускается раз в минуту
  через `infra/cron/logistics_rtu_sync.sh`, использует `flock` и явный
  `LOGISTICS_RTU_SYNC_APPLY=true`; ручной запуск CLI без `--apply` остается
  безопасным dry-run;
- адресные aliases точек из `1С` подтягиваются командой
  `tasks/sync_logistics_warehouse_aliases_from_onec.py`;
- без `--apply` команда делает dry-run и возвращает отчет `fetched`,
  `synced_planned`, `manual_review_planned`, `skipped`;
- с `--apply` команда пишет изменения и возвращает `synced_created`,
  `synced_updated`, `manual_review_created`, `manual_review_resolved`,
  `skipped`;
- ОТМЕНЕНО (2026-08-28): флаг `--external-carriers`, который сразу переводит
  РТУ в `with_external_carrier`, не разрешен для production. До доработки sync
  он считается legacy-механизмом, потому что пропускает внутреннее плечо
  водителя и создает неподтвержденное физическое событие;
- с `--apply` сервис вызывает общий `logistics.sync_units`, поэтому повторный
  sync обновляет существующую РТУ, а не создает дубль.
- открытый ручной разбор, который стал неактуальным после успешного sync той же
  РТУ, закрывается автоматически со статусом `resolved`;
- отчет для логистов:
  `tasks/report_logistics_rtu_manual_review.py --review-type rtu_target_warehouse_unresolved`.
- подтвержденные aliases применяются только явным JSON-файлом через
  `tasks/apply_logistics_warehouse_alias_overrides.py`; без `--apply` команда
  показывает dry-run, с `--apply` пишет `address_aliases` и историю
  подтверждения в `payload.alias_override_history`.

Возврат принятой межточечной РТУ в ТЗП выполняется read-only endpoint:

- `GET /api/logistics/rtu/ready-for-pickup`;
- обязательный фильтр `warehouse_code`, опциональные `date_from` и
  `format=json|xml`;
- код склада сопоставляется с `logistics_warehouse.external_id`,
  `payload.code` и `payload.onec_departments[].code`;
- возвращаются только РТУ, у которых исходный и целевой склады различаются,
  state находится на конечном складе, а последнее событие равно
  `accepted_at_point`;
- ТЗП использует XML-ответ и добавляет найденную РТУ в «Готов к выдаче»
  получателя; endpoint ничего не записывает в 1С.

Для legacy-потока подтверждения физической логистики не записываются обратно в
production `1С`:

- `handed_to_driver` для внутренней РТУ создает сильное событие
  `pickup_moving_to_point` и DB-outbox стадии `PICKUP_TRANSIT`;
- `accepted_at_point` на однозначно ожидаемом складе создает сильное событие
  `pickup_stored_at_point` и DB-outbox стадии `PICKUP_WAITING`;
- outbox применяется только для pilot allowlist, строго по порядку событий
  заказа, с повторным чтением и readback сделки Bitrix24;
- повторный scan/confirm является идемпотентным и не создает второй переход;
- внешний carrier flow не использует эту внутреннюю цепочку стадий.

### 8.1. Новый поток `ORDER_TRANSFER_V1`

Новый поток включается только для заказов после контрольной даты и не меняет
заказы, уже начатые как `LEGACY_RTU`. Backend получает read-only snapshot view
`dbo.MM_LogisticsOrderTransferV1` раз в минуту и хранит:

- один активный versioned plan на клиентский заказ;
- одну обязательную unit/упаковку на пару `склад-источник -> конечный склад`;
- `origin_order_external_id`, номер сайта, `plan_key`, `plan_version`,
  `unit_key`, внутренний заказ и перемещение;
- readiness как конъюнкцию `проведено + распечатано + собрано + не удалено`.

План поступает до создания готовых перемещений. Поэтому backend знает полное
число обязательных частей заранее. Если snapshot старше 180 секунд, блокируются
scan/handoff, carrier-confirmation и выдача нового потока в единый endpoint
готовности; readiness также обязателен для каждой сканируемой части. Повторный
snapshot обновляет существующие plan/unit по стабильным ключам.

API нового потока:

- `POST /api/logistics/sync/order-plans` — внутренний нормализованный контракт
  snapshot; штатный путь — read-only SQL sync, а не прямой push из 1С;
- `GET /api/logistics/orders/ready-for-pickup` — объединяет `LEGACY_RTU` и
  `ORDER_TRANSFER_V1`, возвращая одну строку на клиентский заказ;
- старый `GET /api/logistics/rtu/ready-for-pickup` сохранён как fallback ТЗП;
- `POST /api/logistics/sync/carrier-confirmations` принимает только сильный факт
  существующей Bitrix-интеграции перевозчика;
- `GET /api/logistics/orders/carrier-confirmations?format=json|xml` отдаёт 1С
  подтверждённые `plan_key/version`, терминал, дату, трек и `source_ref`.

Для СДЭК/Почты внутреннее плечо до виртуального терминала не создаёт второй
CRM-outbox. Ручная приёмка такой упаковки в приложении запрещена. После сильного
Bitrix-факта backend идемпотентно завершает внутреннее плечо, а 1С использует XML
feed для одной финальной РТУ с терминального склада. Повторный факт с тем же
`source_ref` не создаёт событие или РТУ; другой терминал, трек либо сторонняя РТУ
блокируют автоматику. Следующий минутный snapshot плана не затирает сохранённый
backend-факт `carrier_confirmation`, поэтому XML feed не зависит от гонки двух sync.

Финальная РТУ нового потока не является логистической единицей. Новый RTU sync
пропускает её по `flow_mode/final_sale`; legacy SQL-пуллер дополнительно
классифицирует РТУ как финальную продажу, если все обязательные unit активного
плана уже приняты на конечном складе. Если план не завершён, сочетание РТУ и
активного `ORDER_TRANSFER_V1` создаёт `order_flow_conflict`.

В текущем checkout backend и 1С source package реализованы локально. Новый SQL
view, apply-cron, metadata 1С и регламентное задание не активированы; до native
8.2 merge/readback и отдельного разрешения test/production остаются без изменений.

### 8.2. Предварительный расчёт многоскладского заказа — 13.09.2026

`POST /api/order-fulfillment/quote` — внутренний endpoint с существующей
проверкой bearer token. Это **предложение, не план обеспечения 1С**: вызов не
пишет в БД, не создаёт резерв, заказ, накладную и не открывает оплату.
Статус первого адаптера — только `synthetic_fixture`. В обычной конфигурации
`ORDER_FULFILLMENT_QUOTE_MODE=disabled` (503). Единственный включаемый сейчас
режим — `test_fixture`, только при `ENVIRONMENT=test|development`;
production environment и любой другой режим дают 503.

Вход: `delivery_method` (`pickup`, `cdek`, `russian_post`, `yandex_delivery`),
`pickup_point_id` только для самовывоза, `lines[]` со стабильным `line_id`,
`product_id`, `characteristic_id`, `series_id`, `unit_id`, десятичным `quantity`.
`sources=null` означает рекомендацию. Явный `sources[]` содержит
`warehouse_id/quantity`; сумма должна точно совпадать с количеством строки.
Повтор склада, неверный шаг единицы, дефицит либо недопустимый маршрут дают
409 без подмены источников. Разные строки одного складского ключа используют
общий доступный остаток внутри расчёта. Это не защита от конкурирующих покупок:
её обязан обеспечить последующий транзакционный резерв в 1С.

Выход: `quote_id`, `quoted_at`, `payment_condition_until`, полный состав,
допустимые источники, все внутренние плечи, физическая точка комплектования,
`ready_at`, отдельно `carrier_handoff_at` и `carrier_delivery_at`, предупреждения.
`quote_id` — fingerprint конкретного расчёта, не `plan_key/plan_version`, не
токен оплаты и не документ 1С. Всегда `test_only=true`,
`inventory_provenance=synthetic_fixture`, `reservation_created=false`,
`payment_allowed=false`, `production_eligible=false`.

Техническое окно демонстрационного расчёта — 5 минут, настраивается в профиле.
Это не 72-часовой таймер оплаты. ETA рассчитывается консервативно от конца
окна («при оплате до…»), затем сборка, ближайший рейс с cutoff, перевозка,
приёмка каждого плеча, самая поздняя часть и упаковка. Склад на месте также
участвует в полном комплекте. Расписание перевозчика независимо от внутренних
рейсов; неизвестное расписание возвращает null, не обещанную дату отправки.
Дата доставки до клиента без carrier quote остаётся null.

В тестовой конфигурации сервер читает два явных пути:
`ORDER_FULFILLMENT_QUOTE_PROFILE_PATH` и `ORDER_FULFILLMENT_QUOTE_INVENTORY_PATH`.
Они не принимаются из запроса. Файлы валидируются и перечитываются при каждом
расчёте; смена длительности не требует перезапуска/переустановки 1С.
Snapshot старше 180 секунд или из будущего блокирует расчёт. Некорректный
профиль/snapshot возвращает 503 без содержимого файлов в ошибке.

Канонический искусственный профиль:
`/opt/MM/1C_Dev_Workflow/migration/ut103/tests/task-46-fulfillment-timing-test-profile.json`.
Архив сборки backend должен явно включать согласованную копию профиля либо
указывать конфигурационный путь; поиск соседнего repository в production не
предполагается. В default mode файл не читается.

Изолированная демонстрация, не подключённая к `app.main`, БД или интеграциям:

```bash
cd /opt/MM/pricing-service
./.venv/bin/python scripts/run_order_fulfillment_demo.py --port 18946
```

Открыть `http://127.0.0.1:18946/` на машине запуска (для другой машины нужен
отдельно настроенный безопасный туннель). Сервер отдаёт только три явно
разрешённых файла интерфейса из копии сайта, bootstrap и quote. Изменение
корзины и подтверждение выбора живут только в памяти страницы. Нет кнопки
оформления/оплаты и сохранения заказа. Host/Origin ограничены, сторонние
запросы запрещены CSP, ответы no-store. Для завершения — Ctrl+C.
Bootstrap генерирует искусственные остатки заново, явно маркируя происхождение;
он не переименовывает старый снимок 1С в свежий.

Демонстрационные пять точек — не сверенный список всех активных магазинов.
Следующий адаптер потребует актуального соответствия XML_ID/точка/город/роль,
без технических складов, реальных свободных остатков, серверной корзины и цены.
Ни CommerceML, ни обычная корзина/checkout/оплата существующих заказов здесь
не изменены. Потребители не должны трактовать quote как подтверждённый резерв.

## 9. Решения Пилота И Остаточные Проверки

- `ПВЗ / пункт выдачи` в 1С для MVP не дорабатываем.
- Отдельный реквизит внутреннего самовывоза
  `ЗаказПокупателя.осиТочкаСамовывоза` установлен в production. Логистический
  sync использует его как первичный точный источник; адрес остаётся fallback
  только для старых заказов с пустым полем. СДЭК-ПВЗ с внутренней точкой
  самовывоза не смешивается.
- Source of truth по готовности РТУ: `не помечена на удаление` + `Проведена` +
  событие `Распечатан` + событие `Собран`.
- Адреса, которые не сопоставились с одним подразделением, отправляются в
  internal `manual_review`; такой разбор не является выбором направления в
  пользовательском сканере.
- Отдельный barcode для РТУ-пакета на старте не создаем, используем печатный
  штрихкод/QR с расходной накладной.
- Внутренний полный `lookup_code` backend хранится как
  `MMLOG1|rtu|<rtu_external_id>|<site_order_number>`; сканер также принимает
  существующий короткий QR без номера сайта и нормализует decimal UUID/
  `_IDRRef` без перепечатки документа.
- Если generated lookup не уникален, документ отправляется в `manual_review`.
- Локальная РТУ не создает логистическую единицу и остается в ТЗП своего склада.
- Межточечная РТУ возвращается в ТЗП получателя только после
  `accepted_at_point` на конечном складе.
- Для `_InfoRg9448` по РТУ нужно подтвердить и зафиксировать RTRef документа,
  чтобы события других типов документов не попадали в gate по совпавшей ссылке.
