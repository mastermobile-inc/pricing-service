# Integration Contract: Logistics 1C -> External Service

Документ фиксирует рабочую карту технических имен 1С/MSSQL для пилота
`Логистика перемещений через Telegram-бота`.

Источник истины для документов остается 1С. Внешний сервис читает данные из 1С
read-only и хранит только логистический state, события Telegram и аудит.

Актуализация 2026-09-14: события приходят также из Bitrix24 и web fallback.
Выпуск №225 опубликован 2026-09-14 из commit `fd10958`; минутная загрузка
перемещений включена. Аппаратная приёмка командой подтверждается отдельно.

## Операционный справочник водителей (решение №225)

Bitrix24 — источник списка для новых передач: `user.get`, `ACTIVE=true`,
точное `WORK_POSITION=Водитель` после нормализации пробелов и регистра.
Курьеры исключены; фильтра по подразделениям нет. Уникальная связь — ID
Bitrix24; ФИО не используется для автоматического объединения.
Учетные сотрудники 1С и прежние идентификаторы истории сохраняются.
ОТМЕНЕНО 2026-09-12: обновление активного списка старым `sync/drivers` после
первого успешного snapshot Bitrix24. Остановка нового job не отменяет это правило.

Полная минутная выгрузка применяется атомарно; ошибка, меняющийся total или
неполная пагинация не деактивируют сотрудников. Последний успешный snapshot
старше 180 секунд показывается как устаревший. `timeman.status` используется
только для подсказки смены; без доступа или при устаревании — «Неизвестно».
Сканирование и подтверждение не запрашивают Bitrix24/1С напрямую.

Остатки отправления используют локальную готовность, физическое положение и
следующее плечо. RTU sync сохраняет `payload.ready_for_handoff`; при утрате
готовности ранее загруженная РТУ исключается из новых передач без изменения
истории/физического состояния. Legacy импорт перемещений обязан соблюдать gate
ниже; явный `ready_for_handoff=false` исключает документ. Свежесть обоих типов
проверяется раздельно, неизвестная свежесть означает потенциально неполный список.

Полный [план и приёмка №225](specs/logistics-control-contour.md#выпуск-по-задаче-225-водители-сканер-и-остатки-2026-09-12).

## 1. Статус проверки

Проверено на живой MSSQL-базе 1С через локальный `ONEC_DATABASE_URL` и по
выгрузке конфигурации `ВыгрузкаКонфиг10.3`.

Подтверждено:

- документ 1С `ПеремещениеТоваров` физически хранится в `_Document178`;
- табличные части документа: `_Document178_VT3822`, `_Document178_VT3839`;
- справочник складов физически хранится в `_Reference80`;
- история событий документа для сканирования хранится в регистре сведений
  `осиОтветственныеЗаДокументы`, физическая таблица `_InfoRg9448`;
- склад-получатель `Транзит  для Москвы` имеет код `РБ0000027`;
- фактический склад-получатель для логистики определяется через реквизит
  `Подразделение` документа: у подразделения есть реквизит `осиСклад`.

## 2. Readiness Gate Для Пилота

Во внешний логистический контур попадают документы `ПеремещениеТоваров`, где
склад-получатель является транзитным складом.

Документ считается готовым к логистической передаче, если одновременно:

1. документ не помечен на удаление;
2. документ проведен;
3. склад-получатель = `Транзит  для Москвы` / код склада `РБ0000027`;
4. документ распечатан;
5. в истории документа есть событие `Отсканирован`.

Флаг `Проверен` в пилоте не обязателен. После появления отдельной роли
сотрудников проверки его нужно добавить в gate.

Флаг `Отправка подтверждена` отдельно в gate не добавляем: по текущей логике
1С документ с требованием подтверждения не проводится без этого флага.

Если документ фактически был распечатан, но `_Fld8954` не проставился, он не
попадает в автоматическую выгрузку. В следующей волне пилота допуск возможен
только вручную логистом с обязательной причиной и событием
`manual_ready_override` во внешнем сервисе.
Ручной допуск в следующей волне пилота обходит только сбой флага печати:
пометка удаления, проведение, склад-получатель `РБ0000027`, фактический
склад-получатель через `Подразделение.осиСклад` и подтвержденный lookup для
сканирования все равно обязательны.

## 7. Черновой SQL Для Выгрузки Готовых Документов

```sql
SELECT
    CONVERT(varchar(34), d._IDRRef, 1) AS transfer_external_id,
    d._Number AS document_number,
    d._Date_Time AS document_date,
    d._Fld9256 AS barcode,
    CONVERT(varchar(34), src._IDRRef, 1) AS source_warehouse_external_id,
    src._Code AS source_warehouse_code,
    src._Description AS source_warehouse_name,
    CONVERT(varchar(34), dst._IDRRef, 1) AS document_target_warehouse_external_id,
    dst._Code AS document_target_warehouse_code,
    dst._Description AS document_target_warehouse_name,
    CONVERT(varchar(34), dep._IDRRef, 1) AS department_external_id,
    dep._Code AS department_code,
    dep._Description AS department_name,
    CONVERT(varchar(34), dep_wh._IDRRef, 1) AS logistics_target_warehouse_external_id,
    dep_wh._Code AS logistics_target_warehouse_code,
    dep_wh._Description AS logistics_target_warehouse_name,
    d._Posted AS posted,
    d._Fld8805 AS send_confirmed,
    d._Fld8954 AS printed,
    d._Fld8955 AS checked,
    d._Fld8957 AS osi_color
FROM dbo._Document178 AS d WITH (NOLOCK)
JOIN dbo._Reference80 AS src WITH (NOLOCK)
    ON src._IDRRef = d._Fld3819RRef
JOIN dbo._Reference80 AS dst WITH (NOLOCK)
    ON dst._IDRRef = d._Fld3820RRef
LEFT JOIN dbo._Reference68 AS dep WITH (NOLOCK)
    ON dep._IDRRef = d._Fld3818RRef
LEFT JOIN dbo._Reference80 AS dep_wh WITH (NOLOCK)
    ON dep_wh._IDRRef = dep._Fld8919RRef
WHERE d._Marked = 0x00
  AND d._Posted = 0x01
  AND dst._Code = N'РБ0000027'
  AND dep_wh._IDRRef IS NOT NULL
  AND d._Fld8954 = 0x01
  AND EXISTS (
      SELECT 1
      FROM dbo._InfoRg9448 AS scan WITH (NOLOCK)
      WHERE scan._Fld9449_RRRef = d._IDRRef
        AND scan._Fld9449_RTRef = 0x000000B2
        AND scan._Fld9454 = N'Отсканирован'
  );
```

Важно: `СкладПолучатель` документа и `target_warehouse` внешнего сервиса - не
одно и то же поле. В документе `СкладПолучатель` может быть транзитным складом,
а фактическая точка доставки для Telegram берется из связанного склада
подразделения.

В живой выборке есть документы, которые проходят readiness gate, но имеют
пустой `_Document178._Fld9256`. Это не блокирует пилот, если печатная форма
содержит другой штрихкод/QR. До реализации lookup нужно сканером снять
фактическое значение с формы и закрепить источник поиска: номер документа,
ссылка 1С, номер заказа или отдельная строка кода.

Если выбран не `_Document178._Fld9256`, уникальность нужно проверять уже для
выбранного lookup-поля. Нельзя оставлять уникальный индекс только по `_Fld9256`,
если фактически бот сканирует другое значение.

## 9. QR Lookup Для Печатной Формы

На текущей печатной форме `ПеремещениеТоваров` уже есть линейный штрихкод, но
его значение не напечатано текстом рядом с кодом. По снимку формы нельзя
надежно определить, что именно он кодирует. Для логистического Telegram-flow
добавляем отдельный QR с явным версионированным payload и не завязываемся на
старый barcode.

Рекомендуемый payload QR:

```text
MMLOG1|transfer|<1c_document_ref>
```

Где:

- `MMLOG1` - версия формата;
- `transfer` - тип источника, совместимый с будущим `source_document_type`;
- `<1c_document_ref>` - стабильная ссылка 1С на документ
  `Документ.ПеремещениеТоваров`.

Предпочтительно использовать внутреннюю ссылку документа, а не короткий номер с
печатной формы. На форме номер может отображаться как `34486`, тогда как в SQL
номер документа может содержать полный префикс. Короткий номер без типа и ссылки
нельзя считать надежным lookup.

Если быстро получить ссылку 1С в QR технически сложно, допустимый временный
payload для пилота:

```text
MMLOG1|transfer-number|<full_document_number>|<document_date_yyyyMMdd>
```

Например:

```text
MMLOG1|transfer-number|РБГУ0034486|20260428
```

Такой fallback можно использовать только после проверки уникальности пары
`(_Document178._Number, _Document178._Date_Time)` в окне пилота. Значение
`34486` с печатной формы без префикса и даты использовать нельзя.

Артефакты по 1С:

- добавить QR в макет
  `Документ.ПеремещениеТоваров.Макет.Накладная`;
- рядом с QR вывести короткую подпись `MMLOG1 transfer`, чтобы отличать его от
  старого штрихкода;
- оставить существующий линейный штрихкод на форме, если он используется текущим
  складским процессом;
- в функции печати `ПечатьПеремещениеТоваров()` передавать в макет параметр
  QR lookup;
- на одном документе сравнить значение, которое печатает 1С в QR, с тем
  значением, которое backend получает из MSSQL sync.

Артефакты по backend:

- текущий API еще принимает поле `barcode`; для QR в foundation его можно
  заполнять строкой `MMLOG1|...` как legacy lookup;
- при следующей миграции лучше выделить поле `lookup_code` и оставить
  `barcode` только как старое имя;
- lookup должен распознавать префикс `MMLOG1|transfer|...` и находить ровно одну
  логистическую единицу;
- если найдено несколько документов или ни одного, операция должна уходить в
  ошибку скана, а не создавать движение.

`tasks.sync_logistics_transfers_from_onec`: по умолчанию dry-run, запись только
с `--apply` и `LOGISTICS_TRANSFER_SYNC_ENABLED=true`. Параметры:
`--date-from YYYY-MM-DD`, `--limit 500` (размер страницы, не предел выгрузки),
`--transfer-external-id` (hex `_IDRRef` или decimal UUID), `--document-number`
(полный номер документа). Без адресного фильтра — окно 14 дней.

SQL читает `_Document178`, назначение через `_Reference68._Fld8919RRef`,
готовность: проведён, не удалён, распечатан `_Fld8954`, существует запись
`_InfoRg9448` «Отсканирован», учётный получатель `РБ0000027`, склады сопоставлены.
Пагинация по возрастающему `_IDRRef` с курсором последней строки, без OFFSET
и без постоянного предела TOP 500 на весь запуск. Фильтры готовности применяются
после чтения: это позволяет отзывать готовность ранее загруженного документа.

Идентичность — `(source_document_type=transfer, external_id)`. Короткий decimal
и hex QR, полный QR продолжают распознаваться общим lookup. Новый canonical
код — `MMLOG1|transfer|<0x-IDRRef>`. Пакетный `_Fld9256` не гарантирует уникальность;
новые единицы не получают его как идентификатор. Старые lookup/barcode и связи
с историей сохраняются. Разборы `unknown_qr` закрываются после сопоставления.

Новый sync не расширяет доступы и не создаёт handoff/receipt, CRM-связь или SMS.
Отсутствующие склады импортируются по ссылке и названию 1С как неактивные
справочные записи; pilot allowlist и назначения сотрудников не меняются.
Это позволяет распознать документ и назвать правильный склад отправления,
не открывая сотрудникам новые точки. Уже существующие склады не деактивируются.
При изменении уже двигавшегося документа маршрут и физическое состояние
сохраняются, создаётся один открытый разбор. До движения потеря готовности
запрещает новую передачу.

Cron из immutable release: `infra/cron/logistics_transfer_sync.cron`, `flock`,
тайм-аут 49 секунд; отдельный marker `logistics_transfer_sync.last_success`.
Только полный успешный **apply**, не dry-run, обновляет marker. Журнал содержит
время, длительность, read/created/updated/skipped/conflicts. Старше 180 секунд —
операционное предупреждение. Свежесть РТУ не заменяет свежесть перемещений.
Сканирование никогда не читает 1С. При устаревшем marker не обещается повтор
через минуту. Перед включением обязательны адресный и 14-дневный dry-run,
после включения — три последовательных успешных минутных запуска.

## 11. Что Еще Проверить Перед Кодом Синхронизации

ОТМЕНЕНО (2026-09-14) для выпуска №225: необходимость менять тип QR `transfer`
на `rtu`, использовать пакетный `_Fld9256` как уникальный идентификатор или

Пункты ниже — исторические вопросы исходного обследования, не блокеры новой
перепечатки и не разрешение обходить признаки готовности.

- подтвердить на одном известном документе из UI 1С, что `_Fld8954` точно
  соответствует нижнему флагу `Распечатан`;

  но флаг `ОсиРаспечатан` не проставился: ручной допуск логистом с записью
  причины и аудиторского события;
- подтвердить источник штрихкода для сканирования в Telegram: в живой выборке
