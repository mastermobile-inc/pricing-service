# Integration Contract: pricing-service -> УТ 10.3, закрытие заказов

## Владельцы факта

- `pricing-service` хранит черновик, dry-run, подтверждение, очередь и аудит.
- УТ 10.3 является единственным владельцем учётного состояния и создаёт
  `ЗакрытиеЗаказовПокупателей`.
- Bitrix24 предоставляет пользовательскую сессию; он не является источником
  состояния заказа.

Прямая запись из сервиса в SQL/COM 1С запрещена.

## Пользовательский процесс

1. Сотрудник создаёт пакет из Excel (`номер + дата/год`, до 200 строк) либо по
   ограниченному фильтру одного года.
2. Сервис публикует команду `diagnose`. УТ 10.3 возвращает точный заказ и факты
   закрытия, РТУ, оплат, долга, остатка исполнения, резерва и размещения.
3. Каждая подтверждаемая строка должна однозначно разрешиться до заказа с полной
   датой. Сотрудник выбирает допустимые строки и вручную назначает им
   `Исполнение заказа` или `Отмена заказа`. Причина не выбирается автоматически.
4. Роль `order_closure_operator` подтверждает неизменившийся снимок.
5. УТ 10.3 забирает `apply`, повторяет проверку и проводит весь пакет одной
   транзакцией. Любое расхождение возвращает `stale`; частичное применение
   запрещено.

## HTTP API УТ 10.3

```http
GET /api/order-closures/internal/commands?limit=1
Authorization: Bearer <dedicated-token>
Accept: application/xml
```

Ответ содержит корень `order_closure_commands`, одну или несколько команд с
`id`, `kind`, `lease_token`, `lease_until`, `diagnosis_hash` и строки `order`.
Для фильтра в `source/filters` передаются год, подразделение, категория и
состояние. Для `apply` передаются только выбранные строки с точными ссылками
заказа и причины.

Основное подтверждение результата:

```http
POST /api/order-closures/internal/commands/{batch_id}/ack
Authorization: Bearer <dedicated-token>
Content-Type: application/json
```

Для совместимого с 8.2 XML-клиента доступна та же операция по адресу
`.../ack.xml` с `Content-Type: application/xml`. Корень
`order_closure_ack` содержит `lease_token`, итог `diagnosed|applied|stale|failed`
обязательный `receipt_hash`, для диагностики — `diagnosis_hash`, и строки с
фактами либо ссылками созданных документов.

## Идемпотентность и ошибки

- Lease истекает через 30 минут; просроченная команда может быть выдана повторно.
- В УТ 10.3 ID пакета и строки записываются в отдельный регистр в той же
  транзакции, что и документы. Повтор возвращает прежнюю квитанцию.
- `stale` означает бизнес-расхождение без записи данных; `failed` — техническую
  ошибку с полным rollback.
- `applied` принимается только с результатом для каждой выбранной строки.
- Неизвестная причина, неоднозначный заказ, оплата/РТУ для отмены, отсутствие РТУ
  для исполнения, действующее закрытие или незавершённые обязательства блокируют
  весь пакет.

URL и токен читаются в УТ 10.3 из `MM_ORDER_CLOSURE_QUEUE_URL` и
`MM_ORDER_CLOSURE_QUEUE_TOKEN`. Регламентное задание поставляется выключенным.
Подтверждение в сервисе и аренда команд `apply` дополнительно закрыты флагом
`ORDER_CLOSURE_APPLY_ENABLED=false`; на стороне УТ применяется независимый
`MM_ORDER_CLOSURE_APPLY_ENABLED=1`.

## Rollout

Сначала `diagnose` в `Ekama_Test_Integration`, затем контрольный `apply` на 1–3
заказах. Production требует свежий backup, native-8.2 candidate, exact diff,
startup/readback и отдельное включение регламентного задания.

## Автоматическая предоплата: web_prepay_72h_v2

Решение 13.09.2026 заменило отсчёт от создания заказа накопленным временем
фактической доступности оплаты. Версия v1 ниже — историческая, её заявки не
переводятся в v2 и не выдаются на применение даже при включении всех флагов.
Кандидат v2 подготовлен 19.09.2026; это не утверждение о его установке.

Сайт — владелец событий доступности. В отдельной таблице
`mm_order_prepay72_clock` он регистрирует только событие создания **нового**
заказа (`OnSaleOrderSaved`, `IS_NEW=true`) с одной разрешённой онлайн-предоплатой,
RUB и действующим общим payment guard. Старый или не охваченный этим guard путь
не получает вымышленное начало отсчёта. `MM_PREPAY72_V2_RECORD_ENABLED=1`
разрешает регистрацию; по умолчанию она выключена. DDL применяется отдельно до
включения флага. Рабочий backend не создаёт таблицы в БД сайта.

Результат того же guard, который управляет оплатой, сохраняет переход
«доступна/заблокирована». Новый заказ начинает с закрытой оплатой; регистрация
сама по себе не является открытием. Обычный повтор проверки не добавляет
событие и не обнуляет время. Возврат из блокировки продолжает накопление.
Любая замеченная оплата завершает автоматический таймер; возврат оплаты его
не запускает заново. Повреждённая/переполненная история остаётся на разборе.
Обработчик сохранения и периодический worker обновляют факты для новых заказов,
не дожидаясь посещения страницы покупателем. Требуется проверка всех реальных
путей изменения доступности и задержки обновления в тестовом сайте перед
боевым включением. Технический лог старых проверок не служит backfill событий.

Снимок `SitePrepaySnapshot.payment_clock` содержит:

- `policy=web_prepay_72h_v2`, постоянный `enrollment_id` UUID и `enrolled_at`;
- полный массив `events` (1–512): уникальный UUID `event_id`, непрерывный
  `sequence` с 1, timezone-aware `occurred_at`, строгий boolean `available`;
- первое событие — открытие. Время событий не убывает, переходы чередуются,
  ни одно событие не позже `observed_at`.

Backend повторно рассчитывает сумму открытых интервалов только до
`observed_at`. Транспортное время после наблюдения не прибавляется. Сумма должна
быть **строго больше 259200 секунд**, а оплата сейчас должна быть открыта.
Свежесть снимка — максимум 120 секунд. В следующем снимке допускается только
добавление событий: замена начальной регистрации, переписывание префикса,
пропуски, дубли и позднее событие задним числом блокируют автоматизацию.
Все прежние ограничения на оплаты (включая возвраты), отгрузки, идентичность,
сумму, валюту, отмену и способ оплаты сохраняются.

Актор — `automation:prepay72:v2`, UUID пакета использует отдельное пространство
`mm:ut103:prepay72:v2:<site_order_id>`. Отрицательное наблюдение после диагностики
сохраняется: прежнее подтверждение нельзя оставить активным после паузы/оплаты.
Пауза отзывает ещё не выданную команду; возобновление требует свежей диагностики
с новым номером ревизии событий. Конфликт во время уже выданной команды
помечает пакет для ручного разбора и запрещает автоматическую отмену на сайте.
Свежесть и ограничения проверяются повторно непосредственно при выдаче `apply`.

К прежним XML полям добавлены `payment_clock_id`, `payment_clock_revision`,
`payment_available`, `payment_elapsed_seconds`, `payment_first_opened_msk`.
УТ 8.2 принимает только v2, открытое состояние, целое число секунд >259200,
целую положительную ревизию, корректный UUID по длине и свежий снимок.
Накопленное время не может превышать время от первого открытия до наблюдения.
`site_created_msk` остаётся идентичностью; подменять его датой открытия нельзя.
Хеш диагностики связывает заказ с постоянным clock ID и ревизией истории;
текущее растущее число секунд в хеш не входит.

`PrepayWorkItem.expected_clock_id` связывает отмену на сайте с тем же журналом.
Отмена требует подтверждённого закрытия 1С, повторной проверки фактов под
блокировкой и достаточного накопленного времени. Повтор отмены допустим только
для уже подтверждённого результата; произвольная отмена на сайте не создаёт
подтверждение 1С. Старые заявки остаются отдельно, повторной массовой чистки нет.

Порядок подключения: схема/код сайта с флагом off, backend с apply off,
точечный проверенный модуль 1С, проверка контракта, затем регистрация новых
событий и отдельно контролируемое включение применения. Откат сначала выключает
применение и отмену; журнал сохраняется. Удалять историю при откате нельзя.

## Архив: автоматическая предоплата web_prepay_72h_v1


Отдельный источник `auto_prepay72`, актор `automation:prepay72:v1` и одна строка
на пакет. Публичный ID детерминирован по политике и WEB-ID, уникальность уже
обеспечивает существующий индекс public_id; новые таблицы и прямой writer в 1С
не требуются. Общая ручная оценка положительных обязательств сохраняется.

Сайт через отдельный токен передаёт типизированный снимок
`POST /api/order-closures/prepay72/tick`. Сервис проверяет строго более 259200
секунд от создания, свежесть до 120 секунд, явную онлайн-предоплату, совпадение
строки платежа и суммы, отсутствие любой оплаты/возврата/отгрузки, признаков
разбора и разрешённой доставки. Ровно 72 часа ещё не дают допуска. Неизвестный
способ оплаты и отсутствующие факты не заменяются безопасными значениями.

1С отвечает обычной `diagnose`; специализированная оценка разрешает штатное
снятие резерва и плановых обязательств только для этой политики. Непроведённый,
удалённый, неоднозначный заказ, любое стороннее движение расчётов/исполнения,
РТУ, возврат, размещение либо отрицательный резерв блокируют автоотмену.
Перед `apply` сервис требует свежий снимок сайта, а 1С повторяет диагностику
в транзакции, сравнивает состояние строк и остатков и проверяет результат.

Дополнительные поля XML строки: prepay_policy, site_order_id, site_created_msk,
site_observed_msk (14 цифр YYYYMMDDhhmmss, Europe/Moscow), site_amount_minor
(копейки целым числом), site_prepayment_system. Время наблюдения обновляется
без изменения учётного state_hash; время создания, сумма, платёжная система,
состав и остатки входят в проверяемое состояние.

Автоприменение требует независимые `ORDER_PREPAY72_ENABLED=true`,
`ORDER_PREPAY72_APPLY_ENABLED=true` на сервисе и
`MM_ORDER_PREPAY72_APPLY_ENABLED=1` в 1С. Poll дополнительно заявляет
`allow_auto_apply=1`; старый клиент этого параметра не передаёт и автоматический
apply не получает. Ручной apply по-прежнему имеет собственные флаги.
Сайт использует `ORDER_PREPAY72_SITE_TOKEN`, отличный от токена 1С. По умолчанию
все новые переключатели выключены, недостаток настройки закрывает доступ.

`GET /prepay72/work` возвращает до 20 незавершённых заявок. Только квитанция
`applied` с документом закрытия открывает действие `cancel_site`. Адаптер сайта
блокирует строки заказа, платежей и отгрузок, сверяет первоначальную дату/сумму/
платёжную систему, повторяет защитные проверки и вызывает штатный Sale API.
Потерянный ответ сайта повторяется безопасно; факт CANCELED=Y/STATUS_ID=D
подтверждается новым снимком. Сбой сайта не пересоздаёт закрытие в 1С.
`stale` и `failed` не переприменяются вслепую, остаются в аудите для разбора.

Адаптер запускается раз в минуту, новые кандидаты отбирает раз в 15 минут,
не более 20 за цикл, начиная с ближайших к границе 72 часов. Список уже
обработанных WEB-ID получает постранично из `/prepay72/known`.
Нативный poll 1С при включении должен работать не реже раза в 30 секунд.
Все часы должны соответствовать Europe/Moscow/UTC согласно контракту.

До включения: негативная и положительная матрица в native 8.2, проверки повторов
и потерянных квитанций, новый native-кандидат поверх фактического production,
контролируемый пилот и отдельная активация. Локальные тесты не означают, что
автоматизация уже включена.
