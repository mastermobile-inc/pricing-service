# Назначение

Перевести работу с покупательской дебиторкой из Excel и Bitrix-задач в единое
рабочее место менеджера. Основной ежедневный интерфейс - веб-форма
`pricing-service`, где менеджер за несколько секунд видит клиентов для обзвона,
критичную просрочку и статус работы. `Bitrix24` smart-process остается карточкой
истории, эскалации и синхронизации, но не является основной массовой таблицей.

Цель первой волны:

- долг и документы считаются из `1С`;
- менеджер работает в веб-форме по клиентам, а не по отдельным накладным;
- комментарии, обещанные даты оплаты, статусы контакта и SMS-история не живут в
  Excel;
- накладные раскрываются вторым уровнем внутри строки клиента;
- еженедельный Excel остается отчетом, а не местом ручного ведения процесса.

# Decision 2026-06-24 / Ответ Максима

Утверждено по задаче Bitrix `#43`:

- основной вход в рабочее место - embedded Bitrix local app
  `/bitrix/receivables`, а прямой `/receivables/workplace` остается
  техническим fallback для локальной проверки;
- менеджер не вводит внутренний токен: фронт получает `BX24.getAuth()`,
  backend проверяет `user.current` и выдает короткую receivables session;
- основной интерфейс - веб-форма, smart-process - история/эскалация;
- первый уровень - клиенты с дебиторкой, второй уровень - накладные клиента;
- MVP показывает актуальных клиентов с долгом старше расчетного срока 7 дней;
- основные колонки: №, код 1С, клиент, ответственный по долгообразующей
  накладной, телефон, общий долг, просрочка, самая старая просрочка, обещанная
  дата оплаты, последний контакт, кто общался сегодня, статус, следующий контакт,
  перенос оплаты, комментарий/причина неоплаты;
- сводка рядом или сверху: общая дебиторка, общая просрочка, просрочка более 30
  дней, просрочка более 90 дней, сумма для звонка сегодня;
- статусы менеджера: `Не берет трубку`, `Ждем оплату`, `Перезвонить`,
  `Требуется вмешательство`, `Напомнить`, `Оплачено`; для Пятигорска
  дополнительно `Перемещение`, `На карте/в маршрутке`;
- менеджер и старший подразделения видят свое подразделение; Арсен, Арсений и
  владелец видят всю картину;
- выпадающий список сотрудников должен быть привязан к подразделению строки;
- клиентов без телефона показывать в общем списке с красной пометкой;
- риск невозврата в MVP не считать отдельной моделью: достаточно суммы, дней
  просрочки и отсутствия движения;
- задача `#756` включается отдельной вкладкой веб-формы как контроль папок и
  поиск источника долга;
- клиентам с дебиторкой и пустой глубиной кредита нужно установить 7 дней, но
  реализация записи в `1С` идет отдельным dry-run/apply шагом через утвержденный
  механизм обмена.

# Decision 2026-06-26 / QA-замечания Максима

После проверки рабочего места в Bitrix `#43` зафиксированы уточнения:

- основной вход остается embedded Bitrix local app `/bitrix/receivables/`, без
  ручного внутреннего токена для менеджера;
- `403` для обычного пользователя должен быть диагностируемым: backend сначала
  ищет refs подразделения в последнем `telephony_user_line_snapshot`, затем
  добирает refs по совпадению названия подразделения/магазина со staff и
  последней витриной дебиторки;
- refs доступа дополнительно расширяются через whitelist бизнес-эквивалентов
  подразделений. Зафиксировано: `04.Теплый Стан` в дебиторке 1С,
  `Радиорынок «Электромир»` в штате и `Теплый стан Радиорынок "Электромир"
  пав. 652` в телефонии считаются одним подразделением для доступа и подбора
  сотрудников;
- если подразделение не найдено, API возвращает текст:
  `Не найдено подразделение для доступа: проверьте привязку пользователя к подразделению`;
- дни просрочки, `oldest_overdue_date`, `effective_due_date`, ответственный и
  второй уровень накладных в рабочем месте считаются от выбранных открытых
  документов долга тем же service-layer алгоритмом, который использует вкладка
  `Контроль папок`;
- если срок оплаты у клиента отсутствует, правило `+7 дней` применяется к дате
  выбранного открытого документа долга, а не к старому `origin_document_date`;
- поле `Перенес` в веб-форме является действием: при сохранении галочка
  увеличивает счетчик `payment_postponed_count` на `+1`, backend сразу
  возвращает `payment_postponed=false`;
- счетчик переносов хранится в `ReceivableWorkItem.payload`, без отдельной
  миграции БД;
- `Последний контакт` остается датой последнего сохранения результата контакта
  (`last_manager_update_at`) и в UI отображается только датой без времени;
- таблица в Bitrix iframe должна быть компактной, с sticky header и
  закрепленными первыми колонками `№ / Код 1С / Клиент`.

# Decision 2026-06-27 / V2 стабилизация пилота

После первой проверки рабочего места принято решение стабилизировать пилот перед
SMS и любыми write-back действиями в `1С`:

- тяжелая логика выбора открытых документов долга и вкладки `Контроль папок`
  сохраняется в локальный кеш `pricing-service`;
- ежедневный `infra/cron/receivable_ledger_sync.sh` после пересборки read-model
  пересчитывает кеш рабочего места и вкладки `Контроль папок` для той же даты;
- штатный Bitrix endpoint рабочего места сначала читает кеш, а при его
  отсутствии использует старый fallback и возвращает `source_status=fallback_live`;
- сводка рабочего места считается по всей доступной пользователю выборке, а не
  только по строкам, которые показаны на первой странице;
- API возвращает `total_count`, `visible_count`, `summary_scope`,
  `department_options` и `cache_status`;
- добавлен `GET /api/receivables/workplace/meta`, чтобы UI открывался на
  последней доступной дате снимка и показывал свежесть расчета;
- полный/подразделенческий доступ может задаваться таблицей
  `receivable_bitrix_user_access`; env allowlist остается fallback;
- `PATCH /api/receivables/workplace/{counterparty_ref}` принимает `action_id`,
  чтобы повторный запрос не увеличивал счетчик `payment_postponed_count` второй
  раз;
- `last_contact_at` отделен от `last_manager_update_at`: любое сохранение
  обновляет техническую дату изменения, а дата контакта меняется только при
  реальном результате контакта.

# Decision 2026-06-27 / V3 доверие к долгу

Следующий пакет правок по замечаниям Максима не расширяет контур, а повышает
доверие к данным в пилоте:

- `Последний контакт` в таблице стал ручным `date`-полем; PATCH принимает
  `last_contact_at` и сохраняет его как пользовательскую дату контакта, а не как
  техническое изменение;
- сохранение только `next_action_date` или другой технической правки не меняет
  `last_contact_at`;
- колонка `Код 1С` показывает код карточки клиента из локального слоя
  дебиторки (`counterparty_code`) и не делает live-запрос в 1С при открытии;
- ежедневный read-model сохраняет `counterparty_code` в
  `receivable_balance_snapshot` и `receivable_case`, а для старых строк UI/API
  может использовать fallback из кеша `Контроль папок`;
- выпадающий список `Кто общался` строится по активным сотрудникам
  подразделения/магазина клиента с учетом whitelist-эквивалентов подразделений;
  в список попадают только менеджеры, товароведы и руководители подразделения,
  курьеры и прочие роли исключаются по `role_code` / `role_name`;
- второй уровень накладных показывает объяснение выбора открытого долга:
  правило выбора, исходную сумму, закрытия, возвраты, расчетный остаток и статус
  структурной проверки 1С;
- главным документом просрочки считается самый ранний реально открытый документ
  после resolver-а, с явной сортировкой по `document_date`, затем
  `document_ref`;
- после PATCH рабочее место берет документы открытого долга только из
  `ReceivableOpenDebtCache`; тяжелая ведомостная/1С-логика не запускается в
  пользовательском сохранении;
- спорные названия папок и подразделений нормализуются только через локальный
  whitelist алиасов для отображения, сравнения и расширения доступа; исходные
  refs из 1С не меняются;
- доступ тестовых пользователей не определяется по слову `Тестер`: доступ
  выдается только по точному Bitrix user id, таблице доступа, env allowlist или
  найденной привязке подразделения.

# Decision 2026-08-04 / Непрерывное окно канонического остатка

Канонический текущий остаток строится только по непрерывному интервалу
`фактический итог регистра -> все движения -> конец выбранного дня`:

- отдельный read-only запрос получает фактический `MAX(_Period)`, не позднее
  первого числа месяца, из `_AccumRgT7009`;
- этот период одновременно используется для выбора начального остатка,
  включительной нижней границы движений `_AccumRg7002` и
  `opening_balance_date` enrichment-а;
- верхняя граница движений исключительная: `snapshot_date + 1 день`;
- допустимое отставание фактического итога от первого числа месяца задаётся
  внутренней настройкой `RECEIVABLE_CANONICAL_OPENING_MAX_LAG_DAYS`, по
  умолчанию `45` дней;
- отсутствующий или будущий период, отставание более лимита, пустые начальные
  строки, пустая итоговая выборка и ошибка SQL останавливают rebuild до замены
  снимка, кеша и Bitrix-карточек; последний проверенный снимок сохраняется;
- техническая диагностика содержит запрошенный и фактический периоды,
  отставание, границы движений, признак непрерывности и агрегированные количества
  строк без данных клиентов;
- отрицательный остаток сохраняется в reconciliation, но не создаёт
  покупательский кейс, просрочку, звонок или строку рабочего списка.

# Decision 2026-08-05 / Заметки руководителя

Для задачи Bitrix `#43` менеджерский `comment` и существующий PATCH-контракт
остаются без изменений. Рядом добавлен отдельный контур заметок руководителя:

- `personal` видит только автор, включая ограничение от других пользователей с
  полным доступом;
- `shared` видят все сотрудники, которым доступен клиент;
- писать и удалять заметки могут только Bitrix-пользователи с текущим
  `full access`; internal token и подразделенческий доступ остаются read-only;
- каждый руководитель имеет не более одной личной и одной общей заметки на
  клиента; пользователь не может перезаписать заметку другого автора;
- удаление выполняется через `deleted_at`, повторный `action_id` идемпотентен;
- каждое сохранение и удаление создаёт append-only событие. Текст личной заметки
  не помещается в `ReceivableWorkEvent.comment` или общий audit payload;
- миграция аддитивная: при rollback приложения таблица сохраняется и не мешает
  предыдущему релизу.

# Decision 2026-08-05 / Цветные статусы и чистый цикл нового долга

По следующей обратной связи в задаче Bitrix `#43` принято:

- цветом выделяется только плашка выбранного статуса, текст статуса сохраняется;
- переход менеджера в `paid` очищает активный менеджерский комментарий только
  после успешного PATCH, при этом прежний или переданный текст остаётся в аудите;
- заметки руководителя и карточка Bitrix при оплате и новом долге сохраняются;
- новый рабочий цикл начинается при положительном долге после `closed` либо при
  новом `current_debt_key` после `paid`;
- новый цикл сбрасывает статус, рабочий комментарий, даты контакта и обещания,
  выбранного сотрудника, переносы, эскалацию и служебные timestamps прошлого
  цикла, но не удаляет append-only события;
- `paid` с прежним debt key не открывается повторно, пока 1С не покажет новый
  цикл; техническая смена debt key в нетерминальном статусе не сбрасывает работу;
- legacy-строки `paid` с активным комментарием нормализуются отдельной
  versioned-командой с обязательным `--dry-run` перед `--apply`.

# Decision 2026-08-27 / Поиск и предпросмотр комментариев

- поиск рабочего списка выполняется на backend по названию контрагента и коду
  `1С`, без учета регистра и повторных пробелов, до сортировки и `limit`;
- поиск действует только внутри доступного пользователю контура и сочетается с
  фильтрами подразделения, статуса, суммы долга и сортировкой;
- сводка и счетчики соответствуют полному найденному набору, а не первым 100
  строкам frontend;
- в свернутом поле комментария показываются менеджерский комментарий и все
  доступные текущему пользователю заметки руководителя с видом и автором;
- поиск по телефону и текстам комментариев в этот контракт не входит.

# Decision 2026-07-16 / Безопасная синхронизация карточек и проверяемые накладные

Ночной запуск карточек выполняется командой
`tasks.sync_receivable_workflow --force --bitrix-only --all-departments --batch-size 25`.
Для этого контура зафиксированы следующие ограничения:

- `--plan` читает Bitrix и показывает действия `create`, `update`, `conflict`,
  `close`, но не пишет в Bitrix и откатывает локальную транзакцию;
- `--bitrix-only` полностью отключает планирование и отправку SMS;
- `--batch-size` допустим только вместе с `--bitrix-only`; каждый успешный пакет
  фиксируется отдельно, а первая ошибка Bitrix останавливает job с ненулевым
  кодом;
- `crm.item.update` при HTTP `429`, `500`, `502`, `503` или `504` выполняет до
  трёх попыток с паузами `1` и `2` секунды; `crm.item.add` автоматически не
  повторяется, чтобы потерянный ответ Bitrix не привёл к созданию дубликата;
- закрытие карточек выполняется только после всех успешных пакетов, только для
  полного снимка и только после отсутствия долга в двух последовательных полных
  снимках; `--no-close` запрещает закрытие;
- stable key карточки сохраняется между повторами, поэтому повтор после сбоя не
  создаёт дубль;
- кеш открытого долга показывает накладные только при точном совпадении суммы до
  копейки и подтверждённой структуре документа в 1С; иначе долг остаётся виден,
  документы и рекомендация папки скрываются, а строка получает конкретный
  `needs_review`;
- свежий `document_mismatch` не подтверждает просрочку: рабочее место не использует
  старый `origin_document_date`, не включает долг в очередь звонков и сводку
  просрочки; существующая карточка smart-process сохраняется как
  `data_quality_error` без срока, дней просрочки и признака звонка, а новая карточка
  не создаётся;
- `source_stale` остаётся отдельным режимом и продолжает использовать прежний
  fallback до восстановления источника;
- пересборка кеша возвращает диагностические счётчики совпадений, превышений,
  недоборов, отсутствующей ведомости, неподтверждённой структуры и лишних строк.

# Decision 2026-07-03 / Коммуникации И Портрет Должника

Следующая волна должна превратить строку должника из таблицы ручных отметок в
рабочий пульт переговорщика и доказательную историю контактов. Основная цель -
собрать вокруг карточки контрагента полный портрет работы с долгом: кто
работал, как пытались связаться, что сказал клиент, какие договоренности
зафиксированы, какие звонки/SMS были сделаны и насколько качественно менеджер
ведет переговоры.

Зафиксированные требования:

- В строке должника должны быть действия связи: исходящий звонок через
  корпоративную АТС, отправка SMS, фиксация попытки связи, ручной результат
  контакта, обещанная дата оплаты, следующий контакт и комментарий.
- Исходящий звонок должен запускаться из строки должника или карточки, вести на
  корпоративную АТС и создавать событие контакта с привязкой к
  `counterparty_ref`, карточке долга, сотруднику, телефону, времени и
  результату.
- Если АТС возвращает call id, запись разговора, длительность, статус
  дозвона или ссылку на запись, эти данные должны сохраняться в событии
  должника и отображаться в истории карточки.
- Каждая попытка связи должна иметь ответственного исполнителя: Bitrix user id,
  staff ref/name, подразделение, источник идентификации и время действия.
- SMS не должна быть отдельной "черной коробкой": отправка, неотправка,
  ошибка, текст/шаблон, телефон, dedupe key и результат доставки фиксируются
  как события должника.
- События должны раскладываться по типам: звонок, неуспешный дозвон, SMS,
  комментарий, обещание оплаты, перенос оплаты, спор, эскалация, закрытие
  долга, изменение суммы из `1С`.
- Событийная история должна быть пригодна не только для просмотра, но и для
  будущего KPI: количество попыток связи, доля успешных контактов, скорость
  первого контакта, соблюдение следующего действия, качество комментария,
  выполнение обещанных оплат и доля закрытых долгов после контакта.
- KPI переговорщика не должен считаться только по факту "деньги пришли":
  нужно отделять качество работы с коммуникацией от внешних факторов, суммы
  долга, спорности долга, отсутствия телефона и уже закрытых в `1С` случаев.
- Будущая связь с оплатой труда должна идти через отдельный KPI/payroll
  контур после утверждения формул, весов, исключений и права сотрудника видеть
  свою оценку; текущий receivables MVP только собирает доказательные события.
- Нельзя превращать работу менеджера в "мартышкин труд": ручные поля нужны
  только там, где автоматический источник недоступен. Если звонок, SMS,
  запись, длительность или факт дозвона можно получить из АТС/провайдера,
  это должно подтягиваться автоматически.

Минимальный целевой принцип: строка должника показывает не только долг, а
следующее лучшее действие и всю коммуникационную историю по этому долгу. Из
нее должно быть понятно, кто реально работал с клиентом, что уже делали, где
провал связи, какая договоренность актуальна и нужен ли руководитель.

# Decision 2026-07-04 / `Дебиторка Решение`

После read-only сравнения текущего smart-process Bitrix24 по ссылке
`/page/otdel_prodazh/debitorka_pokupateley/type/1132/details/5/` и целевого
контура принято:

- Ничего не публиковать, не создавать и не менять в `Bitrix24` без личного
  присутствия владельца процесса и явной команды на live-действие.
- Текущий `type/1132` - это существующий smart-process `Дебиторка покупателей`
  с кодом `receivable_buyers`, категорией `Работа с дебиторкой` и пилотными
  карточками. Его нельзя молча переименовывать или ломать под новую концепцию.
- `Дебиторка Решение` проектируется как следующий управленческий контур, а не
  как простая копия текущей карточки долга.
- `Bitrix24` остается рабочим слоем карточки, статусов, событий, связи,
  ответственных и истории переговоров.
- `pricing-service` остается расчетным слоем: взаиморасчеты, продажи, валовая
  прибыль, маржа, рентабельность, платежная дисциплина, риск и рекомендация по
  должнику считаются вне `Bitrix24`.
- `1С` остается источником истины по сумме долга, документам, оплатам,
  возвратам, себестоимости, договорам и факту закрытия.
- В целевой карточке нужен блок решения: `Работать мягко`, `Жесткий контроль`,
  `Стоп отгрузка`, `Проверить сумму`, `Эскалация`, `Закрыть`.
- `Рабочий список` должен быть очередью на сегодня, а не обязательным статусом
  воронки: клиент попадает туда по просрочке, следующему действию, обещанной
  оплате, неудачной связи, сумме, риску и управленческой важности.
- Публикационный путь всегда начинается с read-only preflight, dry-run и
  отдельного подтверждения, что именно создается: новый process
  `Дебиторка Решение` или изменение текущего `Дебиторка покупателей`.

# Decision 2026-07-04 / Портрет, Оплата И Советник

Утверждено для целевого контура `Дебиторка Решение`:

- Создаем новый smart-process `Дебиторка Решение`. Текущий
  `Дебиторка покупателей` остается пилотом/историей до отдельного решения о
  миграции.
- В v1 берем только дебиторку контрагентов из папки `Покупатели` в `1С`.
  Дебиторка из других папок не попадает в рабочий контур без отдельного
  разрешения владельца процесса.
- Продажи, валовая прибыль и рентабельность считаются по окнам `30 / 60 / 90`
  дней. В расчет продаж включается только согласованный статус/тип `Товары`;
  возвраты учитываются только если причина возврата относится к качеству или
  браку.
- Для каждого клиента считаем коэффициент тенденции продаж:
  `avg_sales_30 = net_goods_revenue_30 / 30`,
  `avg_sales_60 = net_goods_revenue_60 / 60`,
  `avg_sales_90 = net_goods_revenue_90 / 90`.
  Базовый `trend_coefficient` строится как сравнение свежей динамики с
  90-дневной базой. Если продажи снижаются, коэффициент меньше `1.0`; если
  растут, коэффициент может быть выше `1.0`, например `1.2`. В первой версии
  коэффициент ограничивается правилами, а не используется как единственная
  причина решения.
- Фактический график оплат строится по всем покупателям: частота заказов,
  частота оплат, средний/медианный лаг оплаты, доля закрытия долга оплатами,
  размер платежа относительно долга, недельная/месячная цикличность, срывы
  обещаний и динамика остатка.
- Клиентов группируем по фактическому характеру оплаты:
  `weekly_batch_payer` - заказывает часто, гасит долг пачкой примерно раз в
  неделю;
  `regular_term_payer` - стабильно платит вблизи срока;
  `partial_but_alive` - платит частями, долг не разгоняется;
  `growing_debt_second_week` - раньше платил нормально, но долг растет вторую
  неделю;
  `chronic_non_payer` - за 3 месяца покупает на меньшую сумму, чем текущий долг,
  и долг не гасит;
  `promise_breaker` - регулярно срывает обещанные даты оплаты;
  `silent_no_contact` - нет связи или системно не отвечает;
  `dispute_quality` - есть спор, брак, возврат или вероятная ошибка суммы;
  `no_current_debt` - активный покупатель без текущего долга, которому нужен
  расчетный лимит и контроль условий до следующей отгрузки;
  `new_no_history` - мало истории для устойчивой оценки.
- Рекомендация по рассрочке/графику оплаты строится от группы оплаты,
  коэффициента тенденции, прибыльности, просрочки, формы оплаты и истории
  обещаний. Базовая рамка: расчетный кредитный лимит от средней месячной продажи
  за 90 дней, умноженный на коэффициент кредитной дисциплины. Первый платеж
  должен вернуть клиента внутрь лимита; для не-стоп групп он ограничивается
  `30%` средней месячной продажи. При ухудшении тенденции, росте долга вторую
  неделю или срывах обещаний система ужесточает рекомендацию: меньший лимит,
  меньший срок, эскалация или `Стоп отгрузка`.
- `Советник переговорщика` становится отдельным блоком перед звонком/SMS. Он
  показывает портрет клиента, тип оплаты, риск, цель разговора, рекомендуемый
  тон, допустимые уступки, запретные обещания, короткий скрипт разговора и
  условие эскалации.
- Советник не должен быть только свободным ИИ-текстом. Сначала работают
  детерминированные правила по цифрам и истории, а LLM можно подключать позже
  для аккуратной формулировки текста переговорщика.
- Сигналы злостного неплательщика включают: текущий долг выше покупок за 90
  дней и не снижается; нет оплат при продолжающихся заказах; два и более срыва
  обещаний; оплаты появляются только после давления/стопа; просрочка стареет
  при положительной динамике отгрузок; контакт отсутствует, но новые заказы
  продолжаются.
- Все действия связи делаем через CRM/Bitrix24 и подключенные к нему каналы:
  телефония, звонки, SMS и история карточки.
- Менеджер по продажам по умолчанию работает только со своими клиентами из
  папки `Покупатели`, если это не мешает выполнению задачи. Руководители видят
  всю картину. Старший магазина должен иметь возможность решить конфликт на
  месте: согласовать частичный платеж, график или компенсационное предложение в
  рамках утвержденного лимита. Любое снижение/списание суммы фиксируется как
  `settlement_request` и не меняет долг в `1С` без финансового подтверждения.
- На первый период нужен выделенный координатор дебиторки. Назначенный
  координатор пилота - Арсен Сагиян: он каждый день ведет рабочий список,
  проверяет телефоны, готовит переговоры, дожимает обещания, чистит причины
  споров и доводит процесс до управляемого состояния.
- Пилот запускается в подразделении, где будет базироваться Арсен Сагиян. Перед
  запуском нужно read-only проверить его актуальную привязку в Bitrix/staff/1С;
  в локальном контексте он проходит как руководитель сети торговых точек, но
  подразделение пилота должно браться из текущей оргструктуры.
- Операционный куратор запуска и коммуникационного контура - Платонов Андрей,
  операционный директор.
- Старые карточки - это существующие пилотные элементы в smart-process
  `Дебиторка покупателей`. Они не являются полным реестром должников и не
  мигрируются автоматически в `Дебиторка Решение` без отдельного решения.

# Decision 2026-07-05 / Кредитный Профиль Всех Покупателей

Для кредитной политики недостаточно смотреть только текущих должников. В
отдельном dry-run контуре строится профиль всех активных покупателей из папки
`Покупатели` в `1С`:

- активный покупатель - контрагент из папки `Покупатели`, у которого за
  последние `365` дней были продажи, оплаты, возвраты или взаиморасчеты, либо
  есть текущий долг на дату снимка;
- рабочий список должников остается отдельной очередью переговоров и фильтрует
  только клиентов с `current_balance > 0`;
- кредитный профиль включает клиентов без долга, чтобы заранее видеть
  рекомендуемый лимит, форму оплаты, дисциплину, тенденцию продаж и риск
  будущего долга;
- базовый лимит считается от средней месячной продажи за 90 дней:
  `avg_monthly_sales_90 * 30% * credit_discipline_coefficient`;
- для клиентов без текущего долга первый платеж равен `0`, но лимит и класс
  дисциплины сохраняются в профиле и должны использоваться перед новой
  отгрузкой;
- баланс `current_balance <= 0` означает отсутствие текущего долга: для такого
  профиля запрещены классы `D/E`, просрочка, первый платеж и решение
  `Стоп / предоплата`, даже если в старом снимке сохранилась некорректная дата;
- плановую дату оплаты и глубину кредита нельзя применять к нулевому или
  отрицательному балансу. Даты без документа долга не должны превращать сдачу,
  аванс или переплату в просроченную дебиторку;
- форма оплаты `нал / безнал / смешанная` берется из 1С read-only и влияет на
  осторожность решения: преимущественная наличная оплата не должна автоматически
  повышать клиента в лучший класс без подтвержденной дисциплины;
- профиль обновляется как расчетная витрина `pricing-service` без записи в
  `Bitrix24`. Публикация в smart-process возможна только после отдельного
  утверждения live-режима.

Предлагаемый график обновления:

- ежедневно утром после ночной синхронизации 1С - полный кредитный профиль всех
  активных покупателей из `Покупатели`;
- каждые 2 часа в рабочее время - короткое обновление рабочего списка должников
  и событий переговоров;
- раз в неделю - сверка дрейфа классов дисциплины, групп оплат и ручная выборка
  спорных клиентов;
- раз в месяц - ревизия правил кредитования и коэффициентов перед изменением
  политики лимитов.

- недельный Excel по подразделениям с первым листом для руководителя;
- выключение receivables-кейсов как самостоятельных Bitrix-задач.

Следующая волна `Дебиторка Решение`:

- новый smart-process `Дебиторка Решение`;
- расчетный портрет клиента: 30/60/90 продажи, валовая прибыль, маржа,
  рентабельность, тренд, платежная дисциплина и тип оплаты;

- блок управленческого решения: мягкая работа, жесткий контроль,

- embedded-инструменты связи в строке должника: звонок через корпоративную АТС,

- единый журнал событий должника для звонков, SMS, комментариев, обещаний
  оплаты, переносов, споров, эскалаций и автоматических изменений из `1С`;
- привязка каждого события к контрагенту, долгу, сотруднику, Bitrix user,
  телефону, источнику события, времени и исходу;
- сохранение ссылок на записи разговоров и технических call/SMS identifiers,
  если их предоставляет корпоративная АТС или SMS-провайдер;
- подготовка агрегатов качества переговоров для будущего KPI: скорость,
  регулярность, результативность, соблюдение следующего действия и качество
  фиксации договоренностей.

Не входит в текущий запуск:

- изменение формулы суммы долга в `1С`;
- ручная корректировка суммы долга из `Bitrix24`;
- полный зарплатный контур удержаний и начислений по KPI;
- BI-дашборд вместо smart-process;
- прямые изменения глубины кредита в `1С` из веб-формы;
- live-телефония, запись разговоров и автоматическая оценка переговоров в
  текущем MVP без отдельного утвержденного контракта АТС, миграции событий и
  rollout-плана.
- автоматическое списание, скидка или изменение суммы долга в `1С` из решения
  старшего магазина без утвержденного финансового процесса.
- списание, скидка или компенсация более `50%` от суммы продажи без отдельного
  согласования владельца процесса и финансового подтверждения.

- `chain_documents` - список документов роста долга по контрагенту;
- `/api/receivables/*` - private read-only API для кейсов;
- `/api/bi/receivables-*` - BI-витрины для Power BI/сверок;
- `/api/management/task-payloads` - текущий rules output для служебных задач,
  где receivables надо заменить на smart-process sync;
- `new_daily` уже не создает Bitrix-задачи, а доставляется как утренний
  Telegram/XLSX через `infra/cron/new_daily_receivables_from_a.py`.

Соседние проекты не содержат готовой замены:

- `mm-compensation` использует Bitrix/задачи для KPI и содержит контекст по
  дебиторке, но не является system of record по покупательской дебиторке;
- `mastermobile` содержит смежные процессы доставки/долга клиента, но не
  текущий receivables ledger.

# Source of Truth

- `1С` - источник истины по сумме долга, документам, сроку оплаты и закрытию
  долга.
- Каноническая сумма долга использует фактический итог `_AccumRgT7009` и все
  движения `_AccumRg7002` на непрерывном полуоткрытом интервале
  `[actual_opening_period, snapshot_date + 1 день)`.
- Справочник контрагента `1С` - первичный источник телефона клиента; дальше
  телефон синхронизируется с `Bitrix24`.
- `pricing-service` - источник истины по derived state, дедупликации SMS,
  technical history, sync status и правилам эскалации.
- `Bitrix24 smart-process` - операционная карточка и пользовательская история
  работы менеджера.
- Excel/Telegram - только канал доставки отчета или уведомления.

# Data Flow

Целевой поток:

```text
1С -> pricing-service DB -> receivables snapshots/cases -> workflow rules
   -> web workplace -> manager actions / comments
   -> Bitrix24 smart-process
   -> pricing-service sync/readback -> weekly Excel / Telegram / BI
```

Целевой поток коммуникаций следующей волны:

```text
строка должника -> call/SMS action -> корпоративная АТС/SMS provider
   -> communication event -> карточка должника / timeline
   -> KPI evidence / payroll-ready aggregates
```

Целевой поток советника переговорщика:

```text
1С продажи/оплаты/возвраты/себестоимость -> pricing-service портрет клиента
   -> payment behavior group + trend_coefficient + risk signals
   -> advisor recommendation -> Bitrix карточка / строка рабочего списка
```

Daily sync:

1. `pricing-service` пересчитывает receivables snapshots.
2. Для каждого покупательского долга строится рабочий кейс.
3. Интеграционный адаптер ищет карточку smart-process по стабильному ключу.
4. Если карточки нет, создает ее.
5. Если карточка есть, обновляет read-only поля из `1С`.
6. Если долг закрыт в `1С`, переводит карточку в `Закрыто`.
7. Если сумма изменилась, пишет событие в историю и technical log.

# Smart Process Model

Одна активная карточка smart-process = один контрагент с открытой покупательской
дебиторкой в рабочем контуре.

Карточка создается, когда долг стал просроченным.

SMS считается от срока оплаты: за один календарный день до `due_date`.
Карточка smart-process создается или обновляется на следующий календарный день
после `due_date`, если долг не закрыт. Если SMS уходит до появления карточки,
факт SMS сначала хранится в `pricing-service`, а после создания карточки
переносится или отображается в smart-process.

Минимальные группы полей:

- идентификация: stable key, `counterparty_ref`, `counterparty_name`, source,
  sync time;
- `1С` read-only: сумма, дата возникновения, срок оплаты, дни просрочки,
  подразделение, менеджер из `1С`, документы, телефон из справочника
  контрагента;
- контакт: телефон, статус телефона, SMS status/date/error/dedupe key;
- работа: рабочий ответственный, статус, результат контакта/комментарий,
  обещанная дата оплаты, следующее действие, дата последнего обновления;
- контроль: days without update, escalation level/date, dispute flag/reason.

Следующая волна добавляет к модели карточки блок коммуникаций:

- быстрые действия: позвонить, SMS, зафиксировать попытку связи, открыть запись
  разговора, добавить договоренность;
- последняя успешная коммуникация и последняя попытка связи;
- счетчики попыток связи, успешных контактов, SMS, переносов оплаты и
  пропущенных следующих действий;
- список последних событий с фильтрами по звонкам, SMS, обещаниям, спорам и
  эскалациям;
- KPI-evidence: кто работал, сколько попыток сделал, были ли записи, соблюдал
  ли следующий контакт, что произошло после переговоров.

Типы полей в `Bitrix24`:

- `Сумма просрочки` - числовое поле;
- `Статус телефона`, `Статус SMS`, `Результат контакта` и
  `Уровень эскалации` - списки выбора;
- `Комментарий по контакту` - свободный текст;
- технические поля `stable_key`, `counterparty_ref`, `status`, `source`
  не выводятся в операторский layout.

# State Machine

Минимальная воронка:

- `Новый долг`
- `Ожидаем оплату`
- `SMS отправлено`
- `Нет телефона`
- `Менеджер прозванивает`
- `Клиент обещал оплатить`
- `Спор / проверка суммы`
- `На эскалации`
- `Закрыто`

`На корректировку` не использовать как пользовательский статус первой волны.
Если сумма спорная, карточка идет в `Спор / проверка суммы`, а корректировка
делается в `1С` или отдельном финансовом процессе.

# SMS

Шаблон первой версии:

```text
{Имя}, добрый день!
Завтра истекает срок оплаты по заказу №{номер}.
Сумма к оплате: {сумма} руб.
Напоминаем, что при наличии просрочки платежа отгрузки будут приостановлены и не возобновляются до отдельного распоряжения руководства.
Благодарим за сотрудничество компания Master Mobile.
```

Правила:

- отправлять за один календарный день до срока оплаты;
- создавать рабочую карточку на следующий календарный день после срока оплаты,
  если долг не закрыт;
- не отправлять без телефона;
- при отсутствии телефона фиксировать `нет телефона` в карточке;
- запрещать повторную SMS по тому же долгу в пределах одного календарного дня;
- факт отправки писать в карточку, timeline и technical log.

# Эскалация И Спор

Эскалация включается через 15 дней просрочки.

Правило первой версии:

- уведомление уходит руководителю розничной сети;
- руководитель розничной сети становится контролером/наблюдателем эскалации;
- рабочий ответственный в карточке переводится на руководителя розничной сети;
- исходный менеджер остается видимым в карточке как менеджер из `1С` / участник
  работы.

Переход спорного долга к проверке/корректировке подтверждает руководитель
розничной сети. Сумма исправляется только в `1С`, не в `Bitrix24`.

# Отчеты

Еженедельный Excel формируется по подразделениям.

Получатели: Арсений и Арсен. Точные `Bitrix24`/Telegram identifiers нужно
подтянуть перед rollout.

Первый лист:

- клиент;
- сумма, ушедшая в просрочку;
- сколько дней просрочки;
- ответственный.

Дополнительные листы могут содержать документы, комментарии, SMS, статус,
обещанную дату оплаты, дату следующего действия и days without update.

# Invariants

- Сумма долга не редактируется в `Bitrix24`.
- Закрытие долга происходит только после закрытия долга в `1С`.
- У одного контрагента не должно быть нескольких активных карточек по одному
  покупательскому receivables-контуру.
- Комментарии и обещанные даты оплаты не должны вводиться вручную в Excel.
- Bitrix-задача не является источником истории работы с долгом.
- SMS должна иметь idempotency key.
- Ошибки интеграции не должны терять долг: если `Bitrix24` недоступен, backend
  сохраняет retryable sync error.
- Коммуникации не должны храниться только в АТС, Bitrix timeline или SMS
  провайдере: после действия в строке должника service-side event обязателен.
- KPI переговорщика должен строиться только из событий с идентифицированным
  исполнителем; анонимные или системные события не должны попадать в персональную
  оценку без ручного подтверждения.
- Записи разговоров и ссылки на них нельзя раскрывать пользователям вне их
  роли/подразделения и нельзя использовать в зарплатных расчетах без
  утвержденного регламента.

# Errors / Edge Cases

- Ссылка на карточку должна одинаково работать при прямом входе, переходе из
  управленческой витрины и обновлении страницы. Наличие launch-domain в iframe
  не гарантируется: API формирует полный URL из настроек своего контура.
  При известном ID или сохранённой ссылке, которую UI не может открыть,
  показывается `Ссылка на карточку недоступна`, а не
  `Карточка Bitrix не создана`. Пересоздание карточек, изменение долга и прав
  доступа для этого исправления не требуются;
- Нет телефона: карточка помечается `Нет телефона`, SMS не отправляется.
- Менеджер уволен или не найден: карточка назначается руководителю
  подразделения.
- Нет руководителя подразделения: fallback на согласованный финансовый/сетевой
  пул.
- Долг закрыт между SMS и обзвоном: карточка закрывается daily sync-ом.
- Сумма изменилась: запись в history и technical log.
- Клиент спорит с суммой: статус `Спор / проверка суммы`, сумма не меняется в
  карточке, проверку подтверждает руководитель розничной сети.
- Bitrix sync упал: retry, technical log, health degradation.
- SMS provider упал: карточка получает SMS error, повтор разрешен после снятия
  same-day dedupe или отдельного ручного решения.
- АТС не вернула call id: в карточке фиксируется попытка запуска звонка и
  техническая ошибка, но менеджер не должен терять строку из работы.
- Звонок создан, но запись разговора появилась позже: событие обновляется по
  provider event id, а не создается дубль.
- Пользователь нажал звонок/SMS повторно: action id / idempotency key должен
  защищать от дублей.
- Номер телефона отсутствует или требует проверки: действие звонка/SMS
  блокируется, а строка получает понятную причину и задачу на уточнение
  телефона.
- АТС/SMS событие пришло без уверенной привязки к сотруднику: событие хранится
  как unassigned и не идет в персональный KPI до разрешения.

# Rollout

# Decision 2026-09-10 / Погашение старейших документов и единый счетчик

- Пользователь подтвердил: оплаты закрывают документы по возрастанию даты.
  Сначала полностью погашается самый старый открытый документ, остаток оплаты
  направляется на следующий. Частичное погашение сохраняет документ в очереди
  с прежней датой и уменьшенным остатком.
- В таблице остаются только документы с положительным непогашенным остатком,
  от старых к новым. При одинаковой дате и времени порядок стабилизируется
  ссылкой документа. Общая сумма долга не изменяется и остается фактом 1С.
- Канонический непрерывный баланс и защита неполной истории сохраняются.
  Внутри подтвержденного текущего цикла сумма погашений равна сумме реализаций
  минус текущий остаток; она последовательно расходуется на старые документы.
  Это эквивалент последовательного распределения оплат, а не обратное
  заполнение старых документов текущим долгом. Переходящий аванс также
  уменьшает первые документы нового цикла.
- Отдельные возвраты и взаимозачеты не переименовываются в банковские оплаты:
  используемый полный регистр дает суммарное уменьшение задолженности.
  Этот выпуск не добавляет документальную привязку каждой квитанции или возврата
  к РТУ и не меняет учетные документы, назначения платежей либо данные 1С.
- Поле `age_days / UF_CRM_35_AGEDAYS` называется
  `Дней с самого старого неоплаченного документа`.
  Формула: календарная дата отчета минус дата старейшего документа с
  `open_amount > 0`, минимум ноль. Время суток не добавляет еще один день.
  Это возраст документа, не количество дней просрочки платежа.
- Таблица и счетчик используют один и тот же кеш открытых документов.
  Частичная оплата не меняет дату отсчета, полное закрытие переводит отсчет
  на следующий документ. Нет открытых документов, кеша либо достоверной даты —
  значение неизвестно; историческая цепочка и `origin_document_date` не
  подставляются как якобы открытый долг. Обновление из рабочего места не должно
  возвращать прежний расчет возраста.
- Внутренний `origin_document_date` снимка, ключ долгового цикла, договорные
  сроки, очереди SMS и пользовательские статусы этим решением не переписываются.
  Изменение их собственной семантики не требуется для новой таблицы и счетчика.
- Новая версия распределения: `onec_canonical_fifo_settlements_v1`.
  Кеш с прежним `onec_canonical_continuous_balance_origin` непригоден для
  новой подписи: документы скрываются как требующие пересчета, без отката
  к приблизительной цепочке. Статус `cache_outdated` отделен от реального
  расхождения сумм: синхронизация пропускает такие карточки и защищает от
  закрытия, не стирает поля и не меняет менеджерский статус на ошибку данных.
  Перед синхронизацией Bitrix нужен rebuild кеша.
- Установка выполняется только после проверок и штатной подготовки релиза.
  До записи в Bitrix сохранить исходные значения полей, выполнить план без SMS
  и закрытия карточек, сверить суммы документов с 1С, затем проверить readback
  таблицы, числа дней и новой подписи. Само изменение подписи без нового
  расчета запрещено. Одобрение реализации не заменяет отдельного разрешения
  на Git-публикацию, если она требуется контроллером релиза.
