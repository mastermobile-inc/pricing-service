# Назначение

Создать управляемый контур исполнения интернет-заказов `MASTER-MOBILE.RU` после
создания сделки в `Bitrix24 Box` и документов в `1С УТ 10.3`.

Контур нужен для трех операционных потоков:

- самовывоз: сборка на центральном складе `Склад Сдэк`, перемещение в розничный
  магазин, хранение на точке самовывоза, выдача клиенту или расформирование;
- курьерская доставка по Санкт-Петербургу: передача курьеру, факт доставки,
  неуспешная попытка или возврат;
- внешние перевозчики (`СДЭК`, `Почта России`): ожидание оплаты, создание
  накладной, передача в доставку, вручение, отмена/возврат.

Главная цель: не считать раннюю `РТУ` и технические документы `1С` фактом
вручения клиенту. Успех сделки должен фиксироваться только по сильному
операционному доказательству.

# Scope / Out of Scope

Входит:

- append-only история событий исполнения заказа из `1С`, сайта, логистического
  сервиса, Bitrix-чатов и Bitrix24;
- интерактивный бот самовывоза в `chat8729` и в строго отфильтрованных
  сообщениях внутреннего самовывоза из `chat733` / `Сайт MASTER-MOBILE.RU`;
- отдельный read-only парсинг `chat727` / `Отчет доставок СПб` для курьера;
- OCR изображений из `chat727` через существующий OpenAI OCR-подход сервиса;
- derived status заказа и правила перевода сделки в стадии `Bitrix24`;
- новые CRM-стадии для хранения самовывоза на точке и расформирования/отмены;
- SLA текущего самовывоза после подтвержденного уведомления клиента: задача на
  звонок через `72 часа`, возможность начать подтвержденное расформирование
  после `96 часов`;
- правила ручного разбора при слабых или конфликтующих сигналах;
- dry-run, outbox и idempotency для любых изменений в `Bitrix24`.

Не входит:

- запись в БД `1С`;
- замена учетного процесса `РТУ`, возвратов, оплат и остатков внутри `1С`;
- хранение бизнес-состояния в Bitrix-чатах;
- автоматический SLA и автоматическое расформирование исторических заказов без
  надежных дат поступления и уведомления клиента;
- автоматическое закрытие в успех по отсутствию заказа в очередном чат-отчете;
- массовые, исторические и production SMS готовности: в текущем пилоте они
  выключены. Будущий робот Bitrix24 допускается только после успешного readback
  `PICKUP_WAITING`, shadow-проверки и отдельного разрешения на одну реальную
  пилотную SMS.

# Source of Truth

Системы и их роль:

| Источник | Роль |
| --- | --- |
| `1С УТ 10.3` | source of truth по заказам, РТУ, оплатам, возвратам, остаткам, складам и подразделениям |
| `master-mobile.ru` | source of truth по заказу сайта, исходному способу доставки и платежному состоянию сайта |
| `pricing-service` | source of truth по derived status, истории событий исполнения, дедупликации, SLA и outbox |
| `Bitrix24 Box` | рабочий слой: стадии сделки, карточки/задачи, timeline, операционный контроль |
| Bitrix-чаты | источник операционных событий и evidence, но не база состояния |

Инвариант: `Bitrix24` не должен становиться единственной аналитической БД, а
Bitrix-чат не должен становиться системой хранения состояния. Любой вывод из чата
сохраняется как событие в backend и только затем влияет на CRM.

## Несколько РТУ и физических отправлений

`РТУ` является учётным документом `1С`, а не физической посылкой. Несколько РТУ
одного заказа могут быть собраны и переданы клиенту одной отгрузкой с одним
треком. Дополнительная отгрузка Bitrix создаётся только при подтверждённом
физическом разделении заказа.

Состав заказа и сборка сравниваются по товару и количеству. Наличие одной
собранной РТУ недостаточно для `FINAL_INVOICE`, если её строки не покрывают весь
состав заказа. Недостающее количество оставляет сделку в `EXECUTING`, избыток,
возврат части или несовместимое распределение создают ручную проверку.

Для разделённого заказа `pricing-service` хранит независимо:

- РТУ и их строки;
- физические отправления и распределение строк РТУ по ним;
- `shipment_id` Bitrix, трек, перевозчика и ревизию каждой части;
- отдельную дедупликацию email/SMS по отправлению, ревизии и каналу.

После передачи первой части используется `PARTIALLY_SHIPPED`, после передачи
всех количеств — `IN_DELIVERY`. Каждая фактически переданная часть получает своё
уведомление. Для единственной отгрузки продолжают действовать существующие
CRM-роботы: новый контур не отправляет второе письмо или SMS.

Первая production-версия агрегирует полный снимок заказа read-only poller-ом в
`pricing-service`: состав и РТУ читаются из `1С`, живая сделка и физические
отгрузки — из `Bitrix24`. Publisher расширенного события из `УТ 10.3` остаётся
следующим этапом и до отдельного cutover не является обязательным источником.
Снимок имеет стабильный content-based `snapshot_id`, не зависящий от времени
наблюдения и текущей стадии CRM.

Полный снимок содержит `delivery_kind` (`carrier`, `internal_pickup`, `unknown`),
время наблюдения и ревизии обоих источников, весь состав заказа, все актуальные
РТУ и все несистемные физические отгрузки. `snapshot_id` считается только по
нормализованному бизнес-содержимому: изменение времени, стадии CRM или внутренней
ревизии источника без изменения состава не создаёт нового события. Исчезнувшие
из следующего полного снимка РТУ и отправления становятся неактуальными, но их
предыдущие ревизии и append-only события сохраняются.

Маршрут определяется явно: полностью отправленная доставка переходит в
`IN_DELIVERY`, внутренний самовывоз — в `PICKUP_TRANSIT`; неизвестный вид
доставки не меняет CRM и создаёт ручную проверку. Внедрение выполняется
поэтапным production-пилотом: shadow ingest, CRM-поля, стадии, gateway и только
затем отдельные уведомления частей.

Bitrix Shipment gateway принимает только Bearer-authenticated POST JSON,
создаёт дополнительную отгрузку идемпотентно по `shipment_key`, проверяет состав
после записи и меняет трек только по точному `shipment_id`. Старый мост единого
поля `UF_CRM_OT_TRACKING` запрещено применять к заказу с несколькими физическими
отгрузками: один трек нельзя размножать на все части.
Обычный read-only snapshot не ставит gateway-мутацию в outbox: создание части
требует `explicit_split_confirmed=true`, а изменение трека — отдельного
`tracking_update_confirmed=true` и совпадающей живой ревизии Bitrix Sale.

# Текущий Контекст

На `2026-05-21` в CRM уже восстановлен базовый порядок для большинства старых
интернет-заказов:

- поля доставки и оплаты сделки заполняются;
- по СДЭК/Почте массово разнесены доставленные, переданные в доставку,
  отмененные и сделки с треками;
- `289` неоплаченных самовывозов с `РТУ` и проведенным возвратом на основании
  `РТУ` переведены в `Сделка провалена`;
- `697` неоплаченных самовывозов из `В работе` переведены в `Проверка заказа`;
- `283` неоплаченных онлайн-заказа `СДЭК`/`Почта` с неоплаченным
  `CloudPayments` переведены в `Ожидает оплаты`.

Оставшаяся проблема не в массовом backfill, а в постоянной модели управления:

- `РТУ + F` для самовывоза означает, что товар собран/готов к выдаче, но не
  означает, что клиент забрал заказ;
- факт хранения на точке самовывоза должен быть виден отдельно;
- факт расформирования должен быть виден отдельно от обычной сборки;
- факт вручения самовывоза и курьерской доставки сейчас часто есть только в
  операционных Bitrix-чатах.

Read-only срез Bitrix-чата на `2026-05-21` показал:

- `chat733` / `Сайт MASTER-MOBILE.RU`: последние `50` сообщений, `130`
  уникальных номеров заказов, `19` сообщений типа `не забрали`;
- `chat727` / `Отчет доставок СПб`: последние `100` сообщений, текстовых
  номеров заказов почти нет, найдено `55` изображений, поэтому нужен OCR.

Read-only срез production `1С` за `2026` по raw-доставке `_Document132._Fld9266`:

- `Самовывоз`;
- `СДЭК (Самовывоз)`;
- `Доставка курьером`;
- `Почта России (Доставка в отделение)`;
- один пустой raw-случай.

В тестовой Wave 1 встречались `Такси` и `Достависта`; если они, `Boxberry` или
`EMS` появятся в production/сайте, контур должен вынести их в отдельный
ежедневный dry-run отчет, а не молча применить старые правила.

Поля `1С` `_Document132._Fld9939RRef` (курьер) и `_Fld9940` (стоимость доставки)
считаются optional enrichment: в production они почти не заполнены, поэтому v1
не должен требовать их для определения стадии.

# Целевая CRM-Модель

Текущая воронка:

| Код | Название |
| --- | --- |
| `NEW` | `В работе` |
| `PREPARATION` | `Проверка заказа` |
| `PREPAYMENT_INVOICE` | `Ожидает оплаты` |
| `EXECUTING` | `Сборка / обеспечение` |
| `FINAL_INVOICE` | `Готов к отгрузке` |
| `PARTIALLY_SHIPPED` | `Частично отправлен` |
| `IN_DELIVERY` | `Передан в доставку` |
| `DELIVERY_REVIEW` | `Проблема доставки / проверка` |
| `WON` | `Сделка успешна` |
| `LOSE` | `Сделка провалена` |

Read-only проверка REST на `2026-05-21` показала: категории сделок не
используются (`crm.dealcategory.list` вернул пустой список), стадии живут в
`ENTITY_ID = DEAL_STAGE`. В CRM также есть финальная failure-стадия `APOLOGY`
`Анализ причины провала` с `SORT = 110`; она не меняет основную модель заказа,
но ее нужно учитывать при скриптах, чтобы не считать `LOSE` единственной
failure-стадией.

Нужны две новые процессные стадии:

| Семантический код | Название | Где в воронке | Назначение |
| --- | --- | --- | --- |
| `PICKUP_WAITING` | `Ожидает самовывоза` | после `Собран` для внутреннего самовывоза, до `WON`/`LOSE` | заказ готов к выдаче в магазине и ждет клиента |
| `PICKUP_TRANSIT` | `В пути в магазин` | после `FINAL_INVOICE`, до `PICKUP_WAITING` | заказ передан нашему водителю и едет в целевой магазин |
| `PICKUP_STORAGE` | `Хранение в ПВЗ / отделении` | после `IN_DELIVERY`, до `WON`/`LOSE` | отправление хранится во внешнем ПВЗ/постамате/отделении |
| `DISMANTLING` | `Расформирование / отмена` | после `PICKUP_WAITING`/`PICKUP_STORAGE`, до `WON`/`LOSE` | истек срок ожидания/хранения или начат возврат/разбор заказа |

Точный `STATUS_ID` нужно проверить через REST перед применением, потому что
Bitrix24 может хранить стадии default/category pipeline с внутренними префиксами.
В спецификации используются семантические коды.

Для default pipeline стадия `PICKUP_TRANSIT` использует `SORT = 55`. Это
визуальный порядок между `FINAL_INVOICE` и `IN_DELIVERY`; автоматические
переходы по `STATUS_ID` от значения `SORT` не зависят.

Отдельная стадия `Спорные` в v1 не создается. Для конфликтных или неполных
сигналов используется существующая стадия `PREPARATION` / `Проверка заказа`.
Это дает простой принцип пилота: чистые cases вытаскиваются из проверки в
процессные стадии, а спорные остаются в текущем рабочем карантине.

Правило для `LOSE`: финальная стадия `Сделка провалена` ставится только после
устойчивого признака отмены, например проведенного `Возврата от покупателя` на
основании `РТУ` при отсутствии оплаты. Стадия `DISMANTLING` нужна для процесса
разбора до финального закрытия.

Стадия `DELIVERY_REVIEW` считается карантином, а не рабочей очередью хранения.
30-минутный quick-проход обязан разбирать ее по безопасным признакам:

- `CANCELED=Y`: если заказ уже собран, `DISMANTLING`; если не собран, `LOSE`;
- ОТМЕНЕНО (2026-08-23): один `STATUS_ID=F` больше не переводит сделку в `WON`;
  нужен подтверждённый факт выдачи/доставки и отсутствие долга;
- `STATUS_ID=P` и `PAYED=Y`: несобранные возвращаются в `EXECUTING`, собранные
  самовывозы и доставки переходят в `FINAL_INVOICE`;
- `STATUS_ID=N`, `PAYED=N`, самовывоз и `Собран`: `FINAL_INVOICE`; переход в
  `PICKUP_WAITING` требует отдельного сильного факта прибытия в точку;
- `STATUS_ID=N`, `PAYED=N`, ожидание оплаты больше 7 дней: `LOSE`;
- свежие неоплаченные СДЭК/Почта: `PREPAYMENT_INVOICE`;
- свежий курьер с оплатой при получении: `EXECUTING`;
- все остальные комбинации остаются в ручном разборе.

# Derived Status

Backend хранит более детальный `derived_status`, чем CRM-стадия:

| Derived status | CRM stage | Комментарий |
| --- | --- | --- |
| `awaiting_order_check` | `PREPARATION` | самовывоз/курьер без оплаты, заказ требует проверки |
| `awaiting_online_payment` | `PREPAYMENT_INVOICE` | онлайн-оплата выбрана, платеж не подтвержден |
| `assembling` | `EXECUTING` | заказ обеспечивается или собирается |
| `ready_for_dispatch` | `FINAL_INVOICE` | `1С`/сборка говорят, что заказ готов к передаче, но еще не у клиента/логистики |
| `pickup_moving_to_point` | `PICKUP_TRANSIT` | самовывоз передан водителю и едет с исходного склада в магазин |
| `pickup_stored_at_point` | `PICKUP_WAITING` | магазин принял заказ, заказ ждет самовывоза |
| `pickup_dismantle_candidate` | `PICKUP_WAITING` | прошло `96 часов`; требуется ручная проверка и подтверждение, стадия сама не меняется |
| `pickup_dismantling_started` | `DISMANTLING` | магазин/сайт сообщил о разборе, или создан возврат-кандидат |
| `pickup_dismantled` | `LOSE` | проведен возврат на основании РТУ, оплаты нет |
| `courier_spb_handed_to_courier` | `IN_DELIVERY` | пакет физически передан курьеру СПб |
| `courier_spb_delivered_payment_pending` | `IN_DELIVERY` | доставка подтверждена, но оплата еще не подтверждена |
| `courier_spb_delivered_paid` | `WON` | доставка подтверждена и заказ оплачен или OCR/`1С` подтвердили сбор оплаты |
| `carrier_ready_for_label` | `FINAL_INVOICE` | СДЭК/Почта готовы к накладной |
| `carrier_in_delivery` | `IN_DELIVERY` | есть трек/статус передачи в доставку |
| `delivered` | `WON` | сильный факт вручения/получения |
| `cancelled` | `LOSE` | сильный факт отмены |
| `manual_review` | `PREPARATION` | конфликт или слабые доказательства, без авто-закрытия |

CRM-стадия меняется только из `derived_status` с достаточной уверенностью.
Кастомные поля сделки должны хранить сам `derived_status`, дату расчета и
последний evidence, чтобы стадия не была единственным объяснением.

## `bitrix_chat_action_candidate`

Карточка-кандидат, созданная из свободного текста. Она не является фактом
исполнения и сама по себе не меняет CRM и не отправляет SMS. Карточка хранит
источник, номер заказа, найденную сделку, действие, точку, срок действия,
одноразовый nonce, ID сообщения бота, признак `dry_run`, закреплённое действие,
сотрудника-владельца нажатия, время claim и audit payload. Callback принимается
только после атомарной фиксации успешной публикации карточки в outbox.

Append-only журнал нажатий и решений: кандидат, действие, сотрудник,
предыдущее/целевое состояние, результат проверки, причина и idempotency key.

## Инвентаризация точек

`pickup_inventory_run`, `pickup_inventory_submission` и
`pickup_inventory_item` хранят цикл, ревизии состояния конкретной точки и
состав заказа. Нераспознанная точка допускается только у ревизии со статусом
`manual_review`; подтверждённая ревизия всегда содержит `warehouse_id`.
Уточнение кнопками не переписывает исходную строку: выбор точки и подтверждение
режима создают следующие ревизии с `supersedes_submission_id`, а действие
обрабатывается через durable outbox. Позднее изменение исходного сообщения
блокирует подтверждение и требует нового исправленного списка.

## `site_order_fulfillment_outbox`

Durable outbox для стадий CRM, полей, задач, сообщений бота и запуска
бизнес-процесса SMS. Каждая операция имеет уникальный idempotency key,
зависимость от предыдущей операции, число попыток и время следующего повтора.
CRM-стадия, локальный execution event, SMS/задача и финальное закрытие карточки
связаны последовательными зависимостями. При ошибке зависимости карточка
закрывается без кнопок и переводится в ручную проверку.

Worker забирает строки через `FOR UPDATE SKIP LOCKED`. Неидемпотентные внешние
операции (`publish_card`, запуск SMS workflow, создание задачи) не повторяются
после неоднозначного результата. Зависшая SMS через 15 минут сверяется по
`UF_CRM_MM_PICKUP_READY_SMS_AT`: наличие marker завершает outbox, отсутствие
marker переводит карточку в ручную проверку без второй отправки. Любая
зарезервированная попытка SMS, включая неоднозначно завершившуюся, сохраняется
как отдельный проверяемый факт и не отправляется повторно.
Успешный ответ запуска бизнес-процесса не считается подтверждением SMS:
отдельная read-only операция ожидает marker до 15 минут и только после него
разрешает финально закрыть карточку. SMS резервируется единым idempotency key
сделки, поэтому две карточки одного заказа не могут запустить две рассылки.

# Bitrix Chat Ingest

Чаты:

- `pickup_ready` - `chat8729`, основной рабочий чат готовности к выдаче;
- `site_master_mobile` - `chat733` / `Сайт MASTER-MOBILE.RU`, только строгие
  сообщения внутреннего самовывоза;
- `pickup_inventory` - `chat8961` / `Невыданные заказы`, фактически присланные
  точками свободные списки текущих остатков;
- `pickup_movement` - `chat729`, перемещения и смена точки;
- `pickup_exception` - `chat739`, исключения и поиск потерянных заказов;
- `courier_spb` - `chat727` / `Отчет доставок СПб`.

Источник сообщений: Bitrix REST `im.dialog.messages.get`.

Для `chat733` v1 парсит текст сообщений:

- списки номеров заказов;
- фразы `не забрали`, `забрали`, `выдали`, `разобрали`, `расформирование`,
  `возврат`.

Для `chat8961` сохраняется фактически присланное состояние каждой точки без
изменения текущего свободного формата работы сотрудников:

- полный список заказов точки;
- `всё актуально` как перенос предыдущего подтвержденного списка;
- явное сообщение об отсутствии незабранных заказов как нулевой список;
- более позднее исправление как новая ревизия состояния точки.

Отсутствие ответа точки не считается нулевым остатком. Сравнение выполняется по
двум подтвержденным состояниям одной точки; текущий список другой точки и более
позднее перемещение имеют приоритет над выводом об исчезновении заказа.

Рабочий контур задаётся явным allowlist
`ORDER_FULFILLMENT_PICKUP_WAREHOUSE_EXTERNAL_IDS`. На production в него входят
11 магазинов, связанные с подразделениями Bitrix `3270-3280`. Тестовый
`store-1 / Магазин 1` и неиспользуемый `Люблино 1-2` не удаляются из общего
логистического справочника, но не показываются в карточках самовывоза и не
требуют маршрутов задач.

Разговорные названия из pickup-чатов задаются отдельно в
`ORDER_FULFILLMENT_PICKUP_WAREHOUSE_ALIASES`. Они применяются только к
инвентаризации и строгому поступлению `chat8729`, но не участвуют в общем
сопоставлении адресов/РТУ.
Повторный разбор выполняет `scripts/reprocess_pickup_inventory.py`: dry-run
является режимом по умолчанию, а `--apply` создаёт новую подтверждённую ревизию
и помечает исходную ручную ревизию как superseded, не удаляя историю.

Для `chat727` v1 должен обрабатывать изображения:

- `params.FILE_ID` из сообщений;
- download через Bitrix Disk/file API;
- OCR через OpenAI Responses API по уже принятому в `pricing-service` подходу.

OCR должен возвращать JSON: номера заказов, статус доставки, сумму/оплату,
курьера/комментарий и confidence. Полный raw text/картинки не выводятся в
пользовательские ответы; наружу идет только redacted evidence.

Исторический backfill не входит в автоматический SLA v1: начинаем с новых
сообщений с надежными датами поступления и уведомления. Старые сделки
проверяются отдельно пакетами без SMS и без автоматического расформирования.
CLI `scripts/reconcile_historical_pickup_orders.py` по умолчанию только строит
четыре очереди. Применение требует свежий hash `approved-batch-id`, повторно
читает CRM, `1С` и последние состояния точек и ограничено 20 сделками.

# Фоновый Контроль Самовывоза

Основной сценарий не требует от сотрудников приложения, закреплённого меню или
запоминания команд. Бот работает фоновым контролёром и вмешивается только при
исключении:

1. В `chat733` склад привычным коротким сообщением указывает точку и список
   отправленных заказов.
2. В `chat8729` точка привычным коротким сообщением указывает ту же точку и
   список полученных заказов. Допустимый строгий ответ на вопрос бота:
   `Митино: 241500 241501 получили`.
3. Оба строгих факта сохраняются append-only в application DB молча: без
   карточки, SMS и изменения CRM.
4. Если через настраиваемые `24` часа после отправки нет более позднего факта
   получения, бот задаёт в `chat8729` один компактный вопрос на исходный список
   и точку, а не публикует карточку на каждый заказ.
5. Если через настраиваемые `48` часов подтверждения всё ещё нет, бот создаёт
   отдельную задачу по каждому оставшемуся заказу оператору точки с подключением
   старшего по настроенному маршруту.

Перед сохранением строгого факта обязательны уникальная открытая сделка
внутреннего самовывоза, однозначное совпадение точки сообщения с точкой сделки
и ранее известным направлением, а также read-only проверка `1С`: заказ найден,
собран и возврат не подтверждён. Автор сообщения не является доказательством
точки. Если источники называют разные точки, автоматическая фиксация запрещена.

ОТМЕНЕНО (2026-08-26) в части обязательного признака `Собран`: физически
подтверждённое поступление на точку не блокируется из-за запаздывающего признака
сборки в `1С`. Проверка доступности заказа и отсутствия подтверждённого возврата
сохраняется.

Перед фактической отправкой вопроса или созданием задачи worker повторяет live-
проверки CRM, `1С` и append-only событий. Позднее сообщение `получили`, закрытая
сделка, подтверждённая выдача или возврат в `1С` подавляют уже поставленное в
очередь действие. Собственные сообщения бота исключены из evidence parser и не
могут подтвердить получение.

Свободный или неоднозначный текст не меняет CRM. При неопределённой точке
допустима одна компактная карточка уточнения на исходное сообщение. Lost-order
UX остаётся только в `chat739`, inventory clarification — только в `chat8961`.
Технические `/pickup`, `/pickup_arrival` и подписанный `pickup_action` могут
оставаться административным fallback, но не являются обязательным интерфейсом
сотрудника и не требуют закреплённой карточки.

Внешние действия проходят только через durable outbox с idempotency key и
non-retry правилом после неоднозначного результата внешнего API. Флаги
`ORDER_FULFILLMENT_PICKUP_EVIDENCE_TRACKING_ENABLED` и
`ORDER_FULFILLMENT_PICKUP_MISSING_RECEIPT_ENABLED` по умолчанию выключены.
Первый флаг дополнительно требует отдельную явную границу
`ORDER_FULFILLMENT_PICKUP_EVIDENCE_CUTOVER_AT`; общая старая дата запуска бота
для нового контура не используется, поэтому накопленные сообщения не создают
неявный backfill и шквал просроченных вопросов.
Второй флаг перечитывается непосредственно перед каждым внешним действием и не
требует включения общего CRM-флага `ORDER_FULFILLMENT_BOT_APPLY_ENABLED`.

# Парсер Чатов

Парсер должен быть сначала детерминированным:

- извлекать номера заказов сайта, прежде всего 6-значные номера;
- учитывать строки списков, диапазоны и несколько заказов в одном сообщении;
- нормализовать адреса/точки самовывоза;
- классифицировать event type по словарю ключевых фраз;
- выставлять confidence и причину.

LLM можно использовать только как assist для ручной разметки и расширения
словарей, но не как единственный источник автоматического перевода сделки в
`WON` или `LOSE`.

Базовые события из чата `Сайт MASTER-MOBILE.RU`:

| Event type | Пример смысла | Confidence |
| --- | --- | --- |
| `pickup_moving_to_point` | заказ/РТУ перемещается в магазин | medium/strong |
| `pickup_arrived_at_point` | заказ на точке самовывоза | strong при явном тексте или совпадении с логистическим receipt |
| `pickup_unclaimed_reported` | заказ числится незабранным | medium |
| `pickup_client_received` | клиент забрал/выдали заказ | strong только при явном сообщении |
| `pickup_dismantling_started` | начат разбор/возврат | medium |
| `pickup_dismantled` | заказ разобран/возврат оформлен | strong только при подтверждении `1С` или явном регламентном сообщении |

Базовые события из курьерского чата Санкт-Петербурга:

| Event type | Пример смысла | Confidence |
| --- | --- | --- |
| `courier_spb_assigned` | заказ назначен курьеру | medium |
| `courier_spb_handed_to_courier` | пакет физически передан курьеру | strong при явной передаче |
| `courier_spb_delivered_payment_pending` | доставлено, но оплата не подтверждена | medium/strong, CRM stage только `IN_DELIVERY` |
| `courier_spb_delivered_paid` | доставлено и оплачено/оплата собрана курьером | strong, можно рекомендовать `WON` |
| `courier_spb_failed` | не доставлено, перенос/отказ | medium/strong |
| `courier_spb_returned` | пакет вернулся/нужен возврат | strong при явном возврате или подтверждении `1С` |

Отсутствие заказа в очередном списке незабранных не является фактом выдачи.
Такой сигнал может создать `manual_review`, но не должен закрывать сделку в
успех.

# Правила Самовывоза

## Готовность

`РТУ` и событие `Собран` означают:

- товар собран/готов;
- сделку можно перевести в `Готов к отгрузке`;
- для самовывоза и курьера оплата может произойти при получении, поэтому
  отсутствие оплаты не блокирует готовность.

`РТУ + F` не означает выдачу клиенту.

## Хранение на точке

Сделка переходит в `PICKUP_WAITING`, если есть сильный факт, что внутренний
самовывоз находится в магазине и ждет клиента. `PICKUP_STORAGE` оставляем для
внешних ПВЗ/постаматов/почтовых отделений:

- логистический сервис зафиксировал приемку РТУ/пакета на складе магазина;
- или чат `Сайт MASTER-MOBILE.RU` явно сообщает, что заказ пришел/лежит на
  конкретной точке;
- или другой согласованный источник дает тот же факт.

Строго распознанное сообщение о поступлении в `chat8729` с однозначно
определённой точкой является самостоятельным физическим подтверждением. Для
уникальной незакрытой сделки внутреннего самовывоза оно разрешает переход из
`EXECUTING`, `FINAL_INVOICE` или `PICKUP_TRANSIT` в `PICKUP_WAITING`, даже если
признак сборки в `1С` ещё не обновился. Сделки в финальных стадиях не
переоткрываются; несовпадение точки, недоступность `1С` или подтверждённый
возврат по-прежнему блокируют переход.
Для заказа в финальной стадии бот не публикует служебную карточку «Фиксация
поступления»: в смешанном списке такой заказ молча исключается, а остальные
незакрытые заказы продолжают проверяться одной группой.

`storage_started_at` берется из первого сильного события нахождения на точке и
никогда не сбрасывается событием `Не забран`. Автоматическое SMS готовности
отправляется после подтвержденного поступления; его подтверждение сохраняется в
`notification_confirmed_at`. Для SLA используется
`sla_started_at = max(storage_started_at, notification_confirmed_at)`, поэтому
клиентский срок не начинается до уведомления.

Через `72 часа` от `sla_started_at` без выдачи создается одна задача на звонок.
После звонка остается еще `24 часа`; на `96-м часу` заказ становится только
кандидатом на подтвержденное расформирование. Истечение времени само по себе не
переводит сделку ни в `DISMANTLING`, ни в `LOSE`.

Если во время звонка клиент просит сохранить заказ дольше, сотрудник
интернет-магазина указывает конкретную дату `hold_until` (`Удерживать до`).
Фиксированного автоматического продления нет. До этой даты SLA расформирования
приостановлен; в дату `hold_until` создается новая задача на связь/проверку, а не
автоматическое расформирование.

`hold_until` редактируется в поле карточки сделки. Бот не принимает дату
свободным текстом и только показывает действующее значение и учитывает его в
проверках. Каждое изменение поля зеркалируется в service DB отдельным событием
с предыдущим и новым значением.

Роли текущего процесса:

- звонок клиенту и установка `hold_until` — сотрудники интернет-магазина;
- физический разбор заказа — сотрудник точки самовывоза;
- возврат/расформирование в `1С` — сотрудник сайта с соответствующими правами;
- контроль просрочки и эскалация — старший точки.

Назначение задач задается конфигурацией по стабильному
`logistics_warehouse.external_id`: глобальные роли интернет-магазина и сотрудника
сайта дополняются сотрудником и старшим каждой точки. Если маршрут отсутствует
или пользователь Bitrix неактивен, задача не назначается случайному сотруднику:
случай остается без смены стадии и попадает в технический отчет.

включалось.

Для внутреннего самовывоза разрешен сильный составной сигнал без ожидания по
возрасту: есть проведенная `РТУ`, заказ присутствовал в подтвержденном состоянии
своей точки из `chat8961`, а в более позднем подтвержденном состоянии этой же
точки уже отсутствует. При этом заказ не должен присутствовать в более новом
остатке другой точки, а после сравниваемого состояния не должно быть нового
перемещения, повторного прибытия, возврата или другого противоречащего события.
Такая комбинация считается подтверждением выдачи и разрешает переход
`PICKUP_WAITING` → `WON`. Отсутствие ответа точки, неполный список или единичное
сообщение доказательством выдачи не являются.

Будущий логистический event `accepted_by_customer` может стать отдельным сильным
источником только после явного расширения правил. Сайт `F`, оплата или нулевой
долг без факта вручения сами по себе сделку не закрывают.

До появления такого доказательства заказ остается в `PICKUP_WAITING` или в
ручном разборе.

## Расформирование / Отмена

Сделка переходит в `DISMANTLING`, если:

- прошло не менее 96 часов от `sla_started_at` и сотрудник дважды
  подтвердил кнопку `На расформирование`;
- или есть конфликт, который требует возврата товара из лотка.

Оплата, долг или конфликт фактов блокируют автоматический переход и направляют
карточку на ручную проверку. Backend не пишет в `1С`; создаётся физическая задача
на расформирование. Сделка переходит в `LOSE` только после отдельного
подтверждённого возврата, если:

- на основании `РТУ` есть проведенный `Возврат от покупателя`;
- оплаты нет;
- нет более сильного факта выдачи клиенту.

В `Bitrix24` нужно фиксировать loss reason/комментарий:
`Расформирован: самовывоз не забран, возврат от покупателя на основании РТУ`.

# Правила Курьера Санкт-Петербурга

Курьерский чат СПб должен давать такой же evidence-layer, как чат самовывоза.

Правила:

- вызов курьера или назначение заказа не является фактом передачи;
- `courier_spb_handed_to_courier` переводит сделку в `IN_DELIVERY`;
- факт доставки без оплаты создает `courier_spb_delivered_payment_pending` и
  оставляет сделку не выше `IN_DELIVERY`;
- `courier_spb_delivered_paid` переводит сделку в `WON` только при
  подтверждении доставки и оплаты;
- `courier_spb_failed` не закрывает сделку, а создает `manual_review` или
  повторную доставку;
- `courier_spb_returned` с подтверждением `1С`/возврата и отсутствием оплаты
  переводит в `LOSE`.

Для MVP отдельную CRM-стадию `Курьер СПб` не вводим: визуально достаточно
`Передан в доставку`, а тип маршрута хранится в derived status/полях. Если
операционно понадобится отдельная доска курьеров, лучше сделать smart-process
или фильтр, а не дробить основную воронку сделок.

# Правила СДЭК / Почты

Для внешних перевозчиков остаются текущие правила:

- онлайн-оплата выбрана и не оплачена: `PREPAYMENT_INVOICE`;
- заказ собран и готов к накладной: `FINAL_INVOICE`;
- есть трек/статус передачи перевозчику: `IN_DELIVERY`;
- `вручен`/`получен`: `WON`;
- отмена/возврат: `LOSE`.

СДЭК и Почта не должны закрываться по `РТУ` без статуса доставки.

## Automation Ownership

Центр принятия решений находится на стороне `pricing-service`, а не в роботах
Bitrix24. Сервер собирает события из `1С`, сайта, Bitrix-чатов, OCR,
СДЭК/Почты и других источников, хранит историю, рассчитывает `derived_status`,
строит review/outbox CSV и только после проверки применяет изменения через REST.

Bitrix-роботы в этой модели остаются UX-слоем:

- уведомить ответственного;
- поставить дело или напоминание;
- создать задачу на проверку или разбор;
- показать timeline-комментарий с безопасным evidence.

Bitrix-роботы не должны самостоятельно решать те же stage transitions, которыми
управляет сервер. Иначе появятся конкурирующие правила, циклы и переходы без
единого audit trail.

## Bitrix outbox

Любое изменение CRM идет через outbox:

- `target_type = bitrix_deal`;
- `target_id = deal id`;
- `operation = update_stage | update_fields | timeline_comment | smart_process_upsert`;
- `idempotency_key`;
- `dry_run_payload`;
- `applied_at`;
- `error`.

Прямые массовые REST-изменения без предварительного CSV/dry-run запрещены.
Первый серверный outbox для пилота формируется в CSV через
`scripts/build_order_fulfillment_stage_outbox.py`: он включает только строки
`update_stage`, блокирует целевые стадии, которых еще нет в CRM, и не выполняет
REST-изменения.
Применение outbox выполняется отдельным скриптом
`scripts/apply_order_fulfillment_stage_outbox.py`: dry-run по умолчанию,
реальная запись только с `--apply`, перед `crm.deal.update` live-проверяются
номер заказа, текущая стадия и отсутствие финальной стадии.

## Регулярный Cron-Контур

`infra/cron/order_fulfillment_sync.py` — единая точка регулярного dry-run
контроля:

- `--mode quick`: каждые 30 минут строит review/outbox для ограниченной партии
  оперативных сделок вне `EXECUTING`, делает dry-run/apply stage apply и пишет
  лёгкий операционный мониторинг без широких запросов РТУ;
- `--mode nightly`: выполняет исторический scan `EXECUTING`, широкую сверку РТУ,
  состояний заказов и сигналов сборки; программно разрешён только в окне
  `00:00–06:00 Europe/Moscow`;
- `--mode chat`: каждый час загружает `chat733` и `chat727`, сохраняет сообщения
  и результаты парсинга без execution events из свободного текста, строит
  review/outbox по ранее подтверждённым событиям и делает dry-run stage apply
  (`ORDER_FULFILLMENT_SYNC_REVIEW_LIMIT`, по умолчанию `100`);
- `--mode daily`: утром формирует отчет неизвестных raw-доставок и сводку по
  стадиям интернет-заказов.

Shell-обвязка `infra/cron/order_fulfillment_sync.sh` по умолчанию не передает
`--apply`. Auto-apply включается только явным env
`ORDER_FULFILLMENT_SYNC_APPLY=true` после приемки нескольких дней dry-run.

## Постоянный reconciliation стадии EXECUTING — решение от 2026-08-26

`pricing-service` является единственным владельцем решений об автоматическом
изменении стадий интернет-заказов. Стадия `EXECUTING` / `Сборка / обеспечение`
проверяется ночным reconciliation по актуальным фактам `1С`, сайта, логистики и
чатов. Дневные оперативные проходы эту тяжёлую сверку не запускают.

Каждый проход сначала обрабатывает свежие сделки, затем продолжает историческую
очередь вращающимся курсором. Фиксированный лимит не должен приводить к повторной
проверке одних и тех же старейших сделок.

Строгие переходы:

- `Собран` без возврата -> `FINAL_INVOICE`; если с заказом связано несколько
  проведённых РТУ, сборка должна быть подтверждена для всех РТУ;
- ОТМЕНЕНО (2026-08-27): требование `Распечатан + Отсканирован` обязательно для
  всех связанных проведённых РТУ внутреннего самовывоза; частичная выдача теперь
  закрывает исходную продажу в `WON` по правилу ниже;
- `Распечатан + Отсканирован` хотя бы одной РТУ внутреннего самовывоза -> `WON`,
  если сделка уникальна и отсутствует актуальный противоречащий остаток;
- полный возврат без оплаты и факта выдачи -> `LOSE`;
- отмена до исполнения -> `LOSE`, только если сайт подтверждает `CANCELED=Y`,
  отсутствуют оплата, сборка и РТУ, а единственный связанный заказ `1С` не
  проведён и помечен на удаление; активный, проведённый или неоднозначно
  связанный заказ `1С` остаётся на ручной проверке;
- неоплаченная внешняя доставка -> `PREPAYMENT_INVOICE`.

Дубли сделок, частичная сборка, частичные возвраты без подтверждённой выдачи,
оплата вместе с возвратом, конфликт способа доставки и противоречащие события не
меняют стадию и попадают в ручную проверку.
Все переходы выполняются через durable outbox с idempotency key, live-readback до записи
и проверкой результата. Исторический хвост применяется пакетами до 20 сделок после
dry-run. Прямое принятие решений о стадиях в PHP выводится из использования после canary.

Историческое решение `1С`, отклонённое как `stale_evidence` из-за более позднего
execution event, запрещено безусловно воспроизводить или снабжать outbox задним
числом. Для сделки, оставшейся в `EXECUTING`, разрешено создать новое составное
решение только после повторного чтения live CRM, актуальных данных `1С`, текущего
остатка и фактически последнего execution event. Совместимыми считаются только:

- `Распечатан + Отсканирован` и более позднее сильное `pickup_client_received`
  -> `WON`;
- полная сборка без возврата и более позднее сильное `pickup_client_received`
  -> `WON`;
- полный неоплаченный возврат без выдачи и более позднее
  `pickup_dismantling_started` либо `pickup_unclaimed_reported` -> `LOSE`, если
  актуальный остаток отсутствует.

Любая другая комбинация, изменённое исходное сообщение, неуникальная сделка,
актуальный остаток, новое событие между readback и enqueue либо недостаточная
уверенность блокируют переход. Составное решение записывается новым append-only
event и durable outbox, применяется явно выбранными партиями не более 20 с
финальным readback. Оно всегда историческое и никогда не запускает клиентскую SMS.

Историческая очередь не должна оставаться постоянным ручным остатком. Все
исторические сделки разбираются до конечного обоснованного состояния пакетами
не более 20; перед применением каждого пакета выполняется повторный readback CRM
и учетных данных. Конфликтные случаи остаются без движения и выводятся отдельным
списком для ручного решения.

Для исторического заказа частичный возврат не является основанием для `LOSE`,
если после сопоставления строк реализации и возврата в `1С` остаётся
положительное количество реальных товарных позиций. Такой заказ считается
кандидатом `WON`: состоявшаяся продажа закрывает сделку успешно, а последующий
возврат отдельной товарной единицы учитывается как самостоятельная операция и
не отменяет факт продажи оставшейся единицы. Перед применением обязательны
свежий readback стадии и номера заказа в CRM, повторная сверка строк `1С`,
отсутствие более позднего полного
возврата и отсутствие противоречащего актуального остатка. Подтверждённые
кандидаты применяются пакетами не более 20; любой конфликт работает fail-closed.

Если до полного возврата товара и денег подтверждена фактическая выдача заказа
клиенту, историческая сделка закрывается в `WON`. Последующий возврат не отменяет
факт состоявшейся продажи и учитывается как отдельная операция. Для перехода
обязательны однозначное сильное событие выдачи, уникальная сделка, свежий
readback CRM и отсутствие актуального остатка или более нового противоречащего
события.

Для внутреннего самовывоза последовательность `проведённая РТУ -> кассовая
оплата после РТУ -> последующий клиентский возврат` является сильным
подтверждением фактической выдачи. Такая сделка закрывается в `WON`, а возврат
товара и денег учитывается отдельно и не отменяет успех исходной продажи. Это
правило применяется и к возвратам с причинами `Не понадобился`, `Не понравился`
либо с подтверждённым браком, если оплата получена до возврата. Оно не
применяется, если оплата создана только после возврата, связь оплаты с заказом
неоднозначна либо возврат имеет техническую причину вроде расхождения при
сборке; такой случай работает fail-closed и остаётся на проверке.

Для исторического внутреннего самовывоза выдача хотя бы одной из нескольких РТУ
является основанием для `WON`, если эта РТУ имеет согласованный сильный сигнал
выдачи, сделка уникальна и отсутствует актуальный противоречащий остаток.
Возврат либо невыдача остальных РТУ учитываются отдельно и не отменяют
состоявшуюся частичную продажу. Правило не распространяется на курьерские и
внешние доставки без подтверждённого вручения клиенту.

На этапе исторической очистки сначала корректируются стадии CRM. Оплаченный
заказ с полным возвратом товара, без подтверждённой выдачи клиенту и без
денежного возврата переводится в `DISMANTLING`: товарный контур уже закрыт,
финансовый ещё не завершён. Создание задач и отдельной очереди контроля возврата
денег отложено на следующий этап и не блокирует исправление стадии.

Исторический заказ с полным возвратом товарных строк переводится в `LOSE`
только при свежем подтверждении полного возврата всех РТУ и точного связанного
денежного возврата не меньше подтверждённой оплаты с допуском `0,05 ₽`.
Перед применением обязательны уникальная сделка в `EXECUTING`, отсутствие
текущего остатка, выдачи в `1С`, подтверждённого события вручения и ранее
применённого `WON`. Частичный денежный возврат, возврат с неоднозначной связью,
отсутствие выплаты или любое расхождение блокируют переход и остаются в ручной
очереди. Применение выполняется пакетами не более 20 через durable outbox и
финальный readback CRM.

Новые контуры закрыты мастер-флагом и отдельными флагами ingest,
reconciliation, применения стадий и исторического применения; все значения по
умолчанию `false`. `ORDER_FULFILLMENT_EXECUTION_CUTOVER_AT` отделяет новые
события от истории по времени учетного evidence, а не по месту сделки в текущей
пачке сканирования. Без заданного cutover любое событие считается историческим.
Курсор хранится во внешнем общем `.local`, чтобы выпуск нового immutable release
не начинал обход сначала.

Production cutover `2026-08-27T02:34:43+03:00`: для событий после этой границы
включены master, reconciliation, ingest и применение стадий. Историческое
применение оставлено выключенным; старые решения могут сохраняться и попадать в
отчёт, но не меняют CRM до отдельного утверждения исторического пакета.

Чат остается источником сообщений и evidence, но свободный текст самовывоза не
создаёт execution event и не меняет CRM. Подтверждённое событие самовывоза
создаётся только кнопкой нового бота. После включения
`ORDER_FULFILLMENT_BOT_ENABLED=true` legacy auto-apply блокируется для всех
`pickup_*` событий, даже если общий chat auto-apply был настроен; курьерский
контур сохраняет собственные строгие правила. Сообщения ботов, отчеты, цитаты,
пересланные и неоднозначные тексты не применяются автоматически.

Защита закрыта по умолчанию: `ORDER_FULFILLMENT_CHAT_AUTO_APPLY_ENABLED=false`
оставляет chat-проход в dry-run, даже если общий cron запущен с `--apply`.
Разрешенные авторы задаются раздельно для `chat733` и `chat727` через
`ORDER_FULFILLMENT_SITE_CHAT_APPLY_AUTHOR_IDS` и
`ORDER_FULFILLMENT_COURIER_CHAT_APPLY_AUTHOR_IDS`; пустой allowlist запрещает
любой chat auto-apply.

Legacy-переходы v2 до cutover бота (для `pickup_*` после cutover только dry-run):

- строгое `не забрали` для самовывоза из `PREPARATION`, `EXECUTING`,
  `FINAL_INVOICE` или `IN_DELIVERY` -> `PICKUP_WAITING`;
- строгое `выдан клиенту` только из `PICKUP_WAITING` -> `WON`;
- строгое `расформирован` только из `PICKUP_WAITING` -> `DISMANTLING`;
- сверенный courier OCR из `FINAL_INVOICE` -> `IN_DELIVERY`, а оплаченная
  доставка только из `IN_DELIVERY` -> `WON`.

Перед REST-записью outbox повторно сверяет live-номер заказа, live-стадию
и отсутствие финальной стадии.

Оперативный и ночной проходы пишут отдельные артефакты:

- `quick-stage-summary-*.csv`: счетчики интернет-заказов по рабочим стадиям;
- `quick-operational-monitoring-*.csv`: сигналы по `NEW`, `PREPARATION`,
  `DELIVERY_REVIEW`, просроченному ожиданию оплаты, ошибкам outbox/apply;
- `executing-rtu-without-assembled-*.csv`: только ночной проход; сделки в
  `EXECUTING`, где в `1С` есть проведенная `РТУ`, но нет события `Собран`.

Стадия `PICKUP_WAITING` также попадает в quick-проход. Quick-проход не закрывает
самовывоз в `WON` только по сайту `F`, оплате или отсутствию долга: эти сигналы
подтверждают расчеты, но не вручение. Он пишет сигнал
`самовывоз можно проверить на закрытие`; закрытие выполняется подтверждённой
кнопкой бота с live-проверкой `1С` либо будущим отдельно утверждённым сильным
событием вручения.

Если уведомления включены, новые операционные сигналы отправляются в Bitrix
в групповой диалог сайта `MASTER-MOBILE.RU` через
`ORDER_FULFILLMENT_NOTIFY_SITE_DIALOG_ID` (по умолчанию берется
`ORDER_FULFILLMENT_SITE_CHAT_DIALOG_ID`) и, если настроены, получателям
`ORDER_FULFILLMENT_NOTIFY_BUSINESS_USER_IDS` и
`ORDER_FULFILLMENT_NOTIFY_TECH_USER_IDS`; state-файл не дает спамить тем же
ключом сигнала повторно. Для отключения публикации в групповой диалог при
сохранении персональных уведомлений можно задать
`ORDER_FULFILLMENT_NOTIFY_SITE_DIALOG_ID=-`.

После production-cutover 2026-08-31 штатные quick- и chat-проходы выполняются
каждые 30 и 60 минут, но
запускаются с `ORDER_FULFILLMENT_NOTIFY_ENABLED=false` и не отправляют сообщения
в рабочий чат. Quick запускается в `:25/:55`, кроме часа ночной сверки;
`nightly` — в `01:25`, chat — в `:10`, а накопительная
сводка формируется отдельным лёгким запуском `mode=daily` ежедневно в
`11:00 Europe/Moscow`. Временно с 27.08.2026 дневная сводка также запускается с
`ORDER_FULFILLMENT_NOTIFY_ENABLED=false`: отчёты и уведомления по заказам не
отправляются в чат задачи №372 до завершения настройки стадий и переходов CRM.
Фоновая обработка и накопление диагностических данных продолжаются без
публикаций. Повторное включение требует отдельного решения после проверки
движения сделок. Запуски защищены общей блокировкой: дневной
проход ждёт завершения частого, а новый частый проход пропускается, если
предыдущий ещё идёт. Временный `HTTP 500` при чтении статистики стадий
повторяется; если Bitrix не ответил после повторов, сводка всё равно формируется
с пометкой о частичных данных. Для текущего процесса непроведенный документ
заказа в `1С` и отсутствие `РТУ` не исключают заказ из контроля: автоматически
загруженный неотмененный заказ сайта считается актуальным, а ранняя `РТУ` не
используется как признак подтверждения заказа.

При этом просроченный неоплаченный заказ без проведенной `РТУ` не считается
однозначным основанием для автоматического закрытия сделки и не публикуется как
операционный сигнал `требуется действие`. Он остается в техническом review до
появления подтвержденного учетного факта или решения менеджера.

Групповой диалог получает только понятные операционные сигналы: номер
заказа/сделки, бизнес-причину, ожидаемое действие и владельца. Внутренние пути к
CSV/JSON, технические коды (`manual_review`, `terminal_crm_stage`) и состояние
dry-run/apply в групповой чат не выводятся. Ручной разбор доставляется только
персональным business-получателям, технический разбор — только tech-получателям;
ежедневная сводка отправляется в групповой диалог сайта и не требует заполненного
списка персональных business-получателей;
в эту сводку входят свежесть пяти pickup-чатов и отдельного курьерского
`chat727`, подтверждённые и неоднозначные инвентаризации, реакции, заказы без
подтверждённой SMS, SLA 72/96, активные продления, потерянные заказы, ошибки
маршрутизации и состояние outbox;
пустые примеры без номера заказа и сделки не публикуются.

Отчет неизвестных доставок использует общий нормализатор:

- `СДЭК*` и `Почта России*` считаются внешним перевозчиком;
- `Курьер*`, `Доставка курьером*`, `Dostavista/Достависта`, `Такси` считаются
  курьерской доставкой;
- `Самовывоз*`, названия магазинов и центрального склада считаются внутренним
  самовывозом;
- пустые или нераспознанные raw-значения остаются в unknown/watch отчете.

# Bitrix24 Поля

Минимальные поля сделки:

- `derived_status`;
- `derived_status_at`;
- `derived_status_confidence`;
- `execution_evidence`;
- `pickup_point`;
- `storage_started_at`;
- `notification_confirmed_at`;
- `sla_started_at`;
- `hold_until`;
- `storage_deadline_at`;
- `delivered_at`;
- `cancelled_at`.

На первом этапе используются поля `UF_CRM_*` в сделке и service DB. Новый
smart-process не создаётся. Отдельная отметка
`UF_CRM_MM_PICKUP_READY_SMS_AT` (`SMS «Самовывоз готов к выдаче» отправлена`)
не связана с действующим полем `UF_CRM_MM_READY_TRACK_SMS_AT` и защищает только
SMS самовывоза от дублей.

Будущим владельцем SMS назначен Bitrix24. Робот может запускаться только после
успешного readback стадии `PICKUP_WAITING`; антидубль хранится в полях сделки по
идентификатору события приёмки, статусу и времени отправки. Production-флаг
`PICKUP_READY_SMS_ENABLED=false` остается выключенным до shadow-проверки и
отдельного разрешения. Плановый текст:

```text
Ваш заказ №{Номер заказа} готов к выдаче. Master Mobile
```

Адрес точки обязателен. При отсутствии однозначного контакта, телефона, адреса
или корректного заказа SMS не отправляется, а в timeline создаётся
предупреждение. Срок хранения — три дня от первого сильного события приёмки.

Новые функции закрыты по умолчанию независимыми флагами:

- `ORDER_FULFILLMENT_PICKUP_STAGE_APPLY_ENABLED=false` — стадии и поля сделки;
- `ORDER_FULFILLMENT_PICKUP_AUTO_ARRIVAL_ENABLED=false` — автоматическая оценка
  строгого поступления `chat8729`; сама по себе не обходит master/stage flags;
- `ORDER_FULFILLMENT_PICKUP_EVIDENCE_TRACKING_ENABLED=false` — молчаливая
  append-only фиксация строгих отправки/получения только в application DB;
  требует явно заданный `ORDER_FULFILLMENT_PICKUP_EVIDENCE_CUTOVER_AT`;
- `ORDER_FULFILLMENT_PICKUP_MISSING_RECEIPT_ENABLED=false` — групповые вопросы
  через 24 часа и адресные задачи через 48 часов; это отдельный внешний контур,
  который не включает изменения CRM/SMS;
- `ORDER_FULFILLMENT_BOT_SMS_ENABLED=false` — SMS;
- `ORDER_FULFILLMENT_PICKUP_SLA_ENABLED=false` — задачи 72/96 и продления;
- `ORDER_FULFILLMENT_PICKUP_INVENTORY_ENABLED=false` — карточки уточнения
  инвентаризации;
- `ORDER_FULFILLMENT_INVENTORY_WON_ENABLED=false` — автоматический `WON` по
  подтверждённому исчезновению, дополнительно ограниченный allowlist точек;
- `ORDER_FULFILLMENT_LOST_ORDERS_ENABLED=false` — карточки поиска потерянных
  заказов.

Allowlist точек, chat-алиасы и карта ответственных являются конфигурацией, а не
feature flags. Их заполнение не включает внешние действия; SLA остаётся
запрещён, пока health не подтверждает полную карту по всем 11 точкам и активность
пользователей не проверена read-only через Bitrix.

Общий `ORDER_FULFILLMENT_BOT_APPLY_ENABLED=false` имеет приоритет над CRM, SMS,
SLA, inventory/WON и lost-order действиями. Контур отсутствующего получения
намеренно управляется своим независимым флагом, чтобы не включать вместе с ним
CRM-контур. Отключение профильного флага останавливает и уже ожидающие внешнего
применения строки outbox; raw ingest и безопасные отчёты могут продолжаться.

# Invariants

- Сделку в `PREPAYMENT_INVOICE` не возвращать в `EXECUTING`, если сайт уже
  имеет статус `F`, а в `1С` есть проведенная `РТУ`. Такой случай направляется
  в `manual_review` до подтверждения выдачи или доставки.
- Не закрывать самовывоз в `WON` по факту `РТУ + F`.
- Не закрывать самовывоз в `WON` только по отсутствию в одном списке. Закрытие
  разрешено при проведенной `РТУ` и подтвержденном исчезновении между двумя
  состояниями одной точки из `chat8961`, если нет более нового остатка другой
  точки, перемещения, повторного прибытия или возврата.
- ОТМЕНЕНО (2026-08-23): `PAYED=N` в сочетании с отсутствием долга или полной
  оплатой больше не является достаточным основанием для `WON` без подтверждения
  вручения.
- Не закрывать курьерскую доставку в `WON` по назначению курьера или вызову
  машины.
- Не закрывать `Доставка курьером` в `WON` только по факту доставки, если заказ
  неоплачен.
- Не закрывать СДЭК/Почту в `WON` без статуса вручения/получения.
- Не переводить в `LOSE`, если есть подтвержденная оплата или сильный факт
  выдачи.
- Любой авто-переход должен иметь сохраненный evidence event.
- Все Bitrix-chat события дедуплицируются по `chat_id + message_id + order +
  event_type`.
- `1С` и сайт остаются source of truth по документам, оплатам и заказу.

# Errors / Edge Cases

- Сообщение содержит несколько заказов и одну фразу статуса: событие создается
  на каждый заказ, evidence сохраняет общий текст.
- В сообщении есть номер телефона/сумма/адрес: в Bitrix timeline выводить
  только минимальный evidence, raw хранить ограниченно.
- Один номер заказа найден в нескольких сделках: `manual_review`, без
  авто-перехода.
- Чат сообщает `выдан`, но в `1С` уже есть возврат: `manual_review`.
- Есть оплата, но чат сообщает расформирование: `manual_review`.
- Есть возврат на основании РТУ, но чат сообщает выдачу: `manual_review`, пока
  не решит ответственный.
- `1С` недоступна во время опасного действия: fail closed, `manual_review`, без
  изменения стадии.
- Несколько сделок на один номер, несовпадение точки/доставки, финальная стадия,
  истёкшая кнопка или нажатие неучастником: действие отклоняется.
- Bitrix REST недоступен или вернул неполный ответ: ingest job должен
  фиксировать ошибку, не делать выводы из отсутствия событий.
- Исторический backfill из Bitrix-чата не должен повторно применять уже
  обработанные события.

# Tests

Unit:

- regex/parser извлекает один и несколько номеров заказов;
- parser отличает `незабран`, `выдан`, `разобран`, `передан курьеру`,
  `доставлен`, `не дозвонились`;
- parser не считает отсутствие заказа в списке фактом выдачи;
- OCR-классификатор `chat727` отличает `доставлено`, `не доставлено`,
  `перенос`, `оплата получена`;
- state machine не закрывает неоплаченный курьерский заказ в `WON`;
- state machine не закрывает самовывоз по `РТУ + F`;
- state machine не закрывает самовывоз по сайту `F`, оплате или отсутствию долга
  без подтверждения вручения;
- state machine переводит `pickup_stored_at_point` в `PICKUP_WAITING`;
- state machine переводит `pickup_dismantled` в `LOSE` только при отсутствии
  оплаты и наличии возврата.

Integration:

- ingest Bitrix message -> parsed mentions -> execution events -> dry-run
  recommendation;
- duplicate message does not create duplicate event;
- conflicting evidence creates `manual_review`;
- Bitrix outbox builds update payload without direct side effects in dry-run.
- свободный текст создаёт только candidate и не создаёт execution event;
- HMAC token, TTL 24 часа, одноразовый nonce, повторный клик и проверка участника;
- опасные действия требуют второго подтверждения и fail closed при недоступной
  `1С`;
- исторические заказы не запускают бизнес-процесс, а количество новых SMS не
  ограничивается программным пилотным счётчиком;
- действующая отметка `UF_CRM_MM_READY_TRACK_SMS_AT` не меняется.
- два сотрудника не могут одновременно закрепить разные действия за одной
  карточкой, а `Ошибка / отмена` не обходит уже поставленное в очередь действие;
- print и scan разных РТУ не считаются выдачей; проведённый возврат на основании
  той же РТУ блокирует `Прибыл` и `Выдан`;
- зависшая SMS сверяется по marker без повторного запуска workflow;
- fallback `tasks.task.add -> task.item.add` разрешён только при доказанном
  отсутствии современного метода, а не при timeout/неоднозначной ошибке;
- callback принимает реальный динамический `COMMAND_ID` и отклоняет тело больше
  настроенного лимита.

Smoke:

- 10-20 живых заказов: самовывоз, курьер СПб, СДЭК, Почта;
- сверить stage recommendation с карточками сделок;
- проверить timeline comments на отсутствие секретов и лишних персональных
  данных.

  production-разрешения; исторические карточки не обрабатывать.

## Wave 4. SLA и операционные задачи

- Для новых заказов с надежными датами поступления и уведомления создавать одну
  задачу на звонок через 72 часа от `sla_started_at` и разрешать подтвержденное
  расформирование после 96 часов. Исторические заказы в этот SLA не включать.
- Для уже исполненного либо переданного заказа автоматизировать финальный `LOSE`
  только после отдельного подтверждения возврата. Отмена до исполнения следует
  строгому правилу `CANCELED=Y` и неактивного помеченного заказа `1С`,
  зафиксированному выше; запись в `1С` остаётся запрещена.
- Добавить ежедневный отчет по заказам на точках самовывоза и курьеру СПб.
