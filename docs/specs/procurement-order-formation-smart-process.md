# Приложение Bitrix24 «Формирование заказа»

Статус: production-интерфейс активен, автоматическое формирование внутренних
проектов заказов реализовано и включено в штатном cron с `2026-08-18`
(режим `persist_internal_drafts`); реальная запись заказов и свойств в 1С
выключена production-флагами.

Это главный технический источник по рабочей поверхности, API, правам и обмену
приложения. Канонический порядок дальнейших работ находится в
`docs/specs/assortment-status-contour-plan.md`.

Файл сохраняет старое имя только для совместимости ссылок. Рабочий интерфейс больше не использует смарт-процесс.

## Итоговая архитектура

- Единственная рабочая точка входа — OAuth-приложение Bitrix24 по маршруту `/bitrix/procurement-order-formation`.
- Разделы приложения: `Витрина`, `Помощник`, `Заказы`, `Свойства`, `История`.
- Смарт-процесс `1136`, старые стадии и тестовые карточки не участвуют в работе; они сохраняются скрытыми только для отката пилота.
- `pricing-service` хранит заказы, строки, версии, переходы, предложения свойств и журнал событий.
- 1С остаётся источником товарных фактов и получает только непроведённые черновики `ЗаказПоставщику` с `draft_only=true`.
- Товар связывается только по нормализованному `XML_ID = GUID номенклатуры 1С`.
- Розничная цена каталога не читается и не изменяется. Закупочная цена хранится только в строке заказа.
- `BitrixItemUrl` в пакете 1С необязателен для проектов OAuth-приложения без
  legacy-карточки; контроль подтверждения сохраняют обязательные
  `ConfirmationId`, `CalculationId` и `ApprovedBy`.

## OAuth и права

Приложение использует отдельную подписанную сессию со scope `procurement_order_formation`. Токен приложения этикеток не принимается.

- Просмотр, изменение заказа и отправка: Арсений `115204`, Омар `130757`, Эльдар `4241`.
- Жизненные переходы пилота: Омар или Эльдар.
- Ручные решения по статусу для папки `дисплеи`: Омар `130757`, замещающий — Эльдар `4241`. Прежнее правило «переход `ПРОДАЖА → Рабочий` подтверждает только Омар» отменено `2026-08-05`: переходы `Растим ↔ Поддерживаем` считаются по спросу и ручного подтверждения не требуют.
- Ручные свойства: Омар или Эльдар; самоутверждение запрещено.
- Закупочные цены доступны только пользователям приложения из указанного списка.

Именной список выше описывает текущие технические доступы. Бизнес-очередь общая:
любой сотрудник закупки из действующего списка доступа может открыть и обработать
проект, а история фиксирует фактического пользователя каждого действия.
Назначение проекта основному менеджеру по папке, постоянному заместителю или
резервной роли не требуется; таймер переключения также не используется.

**Решение `2026-08-19`:** в интерфейсе ответственный по проекту и строке
отображается обезличенно — `менеджер по закупке`. Личное имя из истории заказов
поставщику больше не подставляется, значение по умолчанию `Омар` в коде витрины
отменено. Фактического пользователя каждого действия по-прежнему фиксирует история.

**ОТМЕНЕНО (2026-08-10):** назначение основного исполнителя по товарной папке,
резервной закупочной роли и подключение резерва сразу при отсутствии либо через
один рабочий день. Причина: механизм избыточен для общей очереди, где проект
обрабатывает тот допущенный сотрудник, который открыл и взял его в работу.

## Витрина и жизненные переходы

Порядок карточек фиксирован и соответствует лестнице из
`docs/specs/assortment-lifecycle-policy.md`:
`Рассматриваем (fruit) → Заказали (newborn) → Завезли (new_item) → Пошли продажи
(sales_start) → Растим (sale) ↔ Поддерживаем (working)`.

Машинные коды не менялись; изменились только пользовательские названия и правила
переходов. Прежние названия `Плод / Новорожденный / Новинка / СП / ПРОДАЖА /
Рабочий` встречаются в исторических отчётах и означают те же коды.

**Решение `2026-08-19`:** на всех экранах приложения показывается действующее
название статуса, а прежнее остаётся рядом — на карточке витрины отдельной
мелкой строкой `раньше: <старое>`, в строках списков и выпадающих списках в
скобках (`Поддерживаем (Рабочий)`). Прежние названия хранятся в
`ASSORTMENT_STATUS_LEGACY_LABELS` рядом с действующими и служат только для
экрана. В данные это не попадает: `status_label`, выгрузки и значения свойства
в 1С остаются без скобок, а readback из учётной системы распознаёт оба набора
названий.

- Общее количество открывает все товары статуса.
- Бейдж `К переходу N` открывает очередь утверждения.
- Для `Рассматриваем / fruit` действует отдельное правило первого закупочного действия: документы `Заказ покупателя` не меняют жизненный статус, но могут автоматически открыть кейс первого `ЗаказПоставщику`; детальное правило зафиксировано в `reports/assortment_lifecycle/2026-07-11/display-fruit-order-formation-rule-2026-07-11.md`.
- Для сильного безопасного среза `Рассматриваем / fruit` система сама считает рекомендацию и
  готовит кейс. Допущенный сотрудник закупки подтверждает итоговое количество;
  только после этого формируется непроведённый черновик. Любой блокер или неизвестное
  значение до подтверждения переводит строку в `Review`.
- Для `Поддерживаем / working` используется `На пересмотр N`, маршрут `Поддерживаем → Review → решение`.
- `Добираем` — отдельная очередь дополнительной потребности, а не ступень лестницы: она может быть открыта поверх `Заказали` или `Завезли` и жизненный статус карточки не меняет. Legacy-код `newborn_need` новым карточкам не присваивается.
- При открытии очереди ничего не выбрано.
- `Выбрать готовые на странице` выбирает только актуальные строки без блокеров.
- Пакет ограничен `100` строками; команды `Утвердить всё` нет.
- Каждая строка фиксирует run id, хэш фактов, исходный и целевой статус, пользователя и результат.
- Возможные результаты: `approved`, `stale`, `blocked`, `conflict`, `failed`.

Жизненный статус, причина, дата, утвердивший и другие служебные поля статуса в
`УТ 10.3` не выгружаются: решение `2026-08-05`, запрет закреплён в коде обмена
(`PROHIBITED_LIFECYCLE_PROPERTY_NAMES`), такие строки не проходят валидацию.
Утверждение жизненного перехода фиксируется только внутри `pricing-service`.

Флаг `PROCUREMENT_ORDER_FORMATION_PROPERTY_APPLY_ENABLED=false` остаётся
выключенным и относится к прочим свойствам номенклатуры, не к жизненному статусу;
в выключенном режиме формируется только dry-run XML. Если пакет свойств
применяется, после результата 1С выполняется CommerceML-readback каталога по GUID.

## Заказы

Одна строка реестра — один будущий заказ поставщику, сгруппированный по поставщику, договору, валюте, складу, маршруту и партии.

Внутренний статус `draft` показывается пользователю как `Заказ на подтверждении`.
Слово `черновик` используется только для непроведённого документа, который уже
создан или передан на создание в 1С.

**Решение `2026-08-19`:** закупочная цена строки проекта всегда равна `1` в
валюте заказа. Цена из истории закупок вводила закупщика в заблуждение, поэтому
фактическую цену он проставляет вручную перед передачей черновика в 1С. До
ручного ввода сумма проекта равна количеству штук и коммерческого смысла не
несёт; блокер `purchase_price_missing` на такой строке не выставляется.

- Карточка заказа помещается в ширину окна Bitrix: таблица раскладывается по
  долям колонок, поэтому кнопка строки видна без горизонтального перетаскивания.
- Блок `Передача заблокирована` группирует блокеры по причине и показывает
  номера проблемных строк (`... — строки 13, 19, 22`). Блокеры приходят с
  префиксом `line_<номер>:`, и без разбора префикса разные причины выглядели
  одинаковой фразой `Требуется дополнительная проверка`.
- Количество и закупочная цена редактируются в строке, сумма пересчитывается сразу.
- PATCH принимает ожидаемые версии заказа и строки; устаревшая версия возвращает `409`.
- Любое изменение увеличивает версию и снимает прежнее подтверждение.
- Основная команда одна: `Проверил и создать черновик в 1С`.
- Серверного запуска создания черновика без действия допущенного пользователя нет.
- Режим dry-run/apply задаётся только серверным флагом; браузер не отправляет `apply`.
- Повторная отправка той же версии возвращает тот же `message_id` и не создаёт дубликат.
- После успешной передачи заказ доступен только для просмотра.
- Реестр выгружает все строки, соответствующие текущим фильтрам, в Excel по кнопке
  `Скачать Excel`; пагинация интерфейса выгрузку не ограничивает.
- Первые колонки выгрузки фиксированы: `Предмет`, `Категория`, `Группа`,
  `Номенклатура`, `Артикул`. Классификация и артикул читаются из актуальной
  витрины `assortment_lifecycle_classification` по коду номенклатуры; отсутствие
  классификации не блокирует скачивание и даёт пустые значения.

### Автоматическое формирование из расчёта дисплеев

Штатный `display_auto_order_sync.sh` после расчёта и адаптивного сравнения
формирует заказы через `tasks.build_procurement_order_formation_dry_run`.
Прямая запись результатов автозаказа в legacy-смарт-процесс не используется.

- Каталог Bitrix проверяется пакетно по нормализованным `XML_ID` номенклатуры 1С.
- Один заказ группирует строки по поставщику, договору, валюте, складу, маршруту
  и партии.
- По умолчанию cron создаёт только JSON/CSV dry-run. Запись в БД приложения
  включается отдельным флагом `DISPLAY_AUTO_ORDER_FORMATION_PERSIST_DB=true`.
- Наличие блокеров не отменяет создание внутреннего проекта: проект и все его
  строки сохраняются в БД приложения, а проблемные строки явно помечаются для
  проверки. Пользователь может открыть проект, исправить количество или
  исходные данные и исключить неподходящую строку.
- Передача конкретного проекта в 1С запрещена, пока в нём остаётся хотя бы один
  блокер. Таким образом, блокер ограничивает внешний результат, а не видимость
  расчёта в рабочем месте.
- Повтор одного расчёта обновляет тот же открытый пакет без дублей и снимает
  прежнее подтверждение при изменении строк.
- Новый расчёт помечает прежние открытые автоматические пакеты статусом
  `superseded`; они доступны по фильтру, но не входят в обычную сводку.
- Ежедневный расчёт создаёт или обновляет видимый внутренний проект независимо
  от календарного графика. График статуса, скорости и ценового профиля задаёт
  только `следующий срок проверки` и приоритет очереди, а не право проекта
  существовать в приложении.
- До подтверждения проекта новый расчёт выполняет построчный merge с обычным
  version/stale-контролем: нетронутые строки обновляются, новые строки
  добавляются, а вручную изменённые `final_quantity` и `purchase_price`
  конкретной строки не перезаписываются.
- Для защищённой строки новая рекомендация хранится отдельно; интерфейс
  показывает расхождение `решение человека ↔ новый расчёт`, а применение нового
  значения требует явного действия пользователя.
- Исчезнувшая по новому расчёту потребность не удаляется молча: строка остаётся
  видимой с пометкой `потребность исчезла` до решения закупщика.
- После подтверждения замораживается весь проект. Автопересчёт его не изменяет;
  последующая потребность создаёт отдельную ревизию заказа.
- Заказы со статусом передачи или подтверждённой передачей в 1С не изменяются.
  Для новой потребности создаётся отдельная ревизия заказа.
- События создания, обновления и замены пакета фиксируются в общей истории.

Штатный запуск сохраняет внутренние проекты с
`--persist-db --supersede-open-batches`, включая проекты со строками на
проверке. Сохранение в БД приложения не создаёт документы 1С; передача
непроведённого черновика требует устранения блокеров и отдельного действия
допущенного сотрудника закупки в интерфейсе.

**Реализовано `2026-08-10`:** штатный cron больше не передаёт
`--fail-on-blockers`, поэтому проблемные строки не отменяют сохранение дневных
проектов. Персональный default пользователя `130757` удалён: без явной настройки
проект попадает в общую очередь закупки.

**Реализовано `2026-08-10`:** ежедневная синхронизация выполняет построчный
merge открытого проекта по устойчивым измерениям заказа и товара. Ручные
`final_quantity` и `purchase_price` сохраняются в `payload.manual_overrides`,
новые расчётные значения — в `automatic_recommendation`, а отличия — в
`recommendation_discrepancy`. Исчезнувшая потребность остаётся видимой с
`need_status=disappeared`. Подтверждённый проект не изменяется; новый расчёт
создаёт связанную ревизию.

### Активные заказы покупателей в количестве

Для `sale (Растим / ПРОДАЖА)` и `working (Поддерживаем / Рабочий)` применяется:

```text
raw_need_qty = max(
    0,
    target_stock_qty
    + active_customer_order_qty
    - sellable_stock_qty
    - incoming_qty
)
```

`active_customer_order_qty` читается из положительного конечного остатка
проведённых и не удалённых `Заказов покупателей` по карточке. Заказы
контрагентов `Потребности <магазин>` включаются без фильтра по имени. Поля
`Зарезервировано` и `Под заказ` выводятся только справочно и не участвуют в
количестве. После формулы применяются MOQ, минимальная партия и округление
количества по правилам разделов ниже.

### Округление количества заказа — решение `2026-08-19`

Правило заменяет прежнюю лестницу округления целиком.

| Рассчитанное количество | Шаг округления | Условие по цене |
| --- | --- | --- |
| `1–49` шт | до `5` вверх | закупочная цена карточки не выше медианы своей ценовой группы |
| `50–500` шт | до `10` вверх | закупочная цена карточки не выше медианы своей ценовой группы |
| больше `500` шт | до `10` вверх | без условия |
| больше `1000` шт | до `50` вверх | без условия |
| больше `2000` шт | до `100` вверх | без условия |

- Округление выполняется только вверх.
- Границы `500`, `1000` и `2000` относятся к верхнему шагу: ровно `500` шт
  округляются по правилу «больше `500`», ровно `1000` — по правилу «больше
  `1000`», ровно `2000` — по правилу «больше `2000`». Практического расхождения
  на самих границах нет: `1000` кратно и `10`, и `50`, а `2000` кратно и `50`, и
  `100`, поэтому вверх округляется в то же число при любом прочтении.
- Если закупочная цена карточки выше медианы своей ценовой группы, количество не
  округляется вообще: в заказ идёт точное расчётное значение.
- Ценовая группа определяется свойствами карточки, а не папкой каталога, и
  состоит из двух частей: бренд плюс класс устройства. Бренд — реквизит
  совместимости бренда карточки (`brand_compatibility`: `Apple`, `Samsung`,
  `Xiaomi`). Класс — `планшет`, `часы` или `телефон`, определяется по названию
  карточки. Медиана считается по закупочным ценам карточек одной группы, а не по
  всем дисплеям. Цена карточки — последняя закупочная цена из строк заказов
  поставщику.
- Класс устройства распознаётся по названию: `планшет` — `iPad`, `Tab`, `Pad`,
  `MatePad`, `MediaPad`; `часы` — `Watch`, `Band`, `GT <цифра>`, `Forerunner`,
  `Fenix`; во всех прочих случаях `телефон`.
- Мультибрендовые дисплеи (`Дисплей для Tecno Spark 7 / Infinix Hot 10i`)
  относятся к группе первого бренда из списка совместимости — того же, что
  открывает название карточки. Реквизит `Бренд` у таких карточек может называть
  любой из совместимых брендов, поэтому сам по себе он группу не определяет.
- Если в ценовой группе меньше `10` карточек с ценой, медиана не считается:
  количество округляется до `10` вверх при любом значении и без условия по цене.
- Если у карточки бренд не заполнен и восстановить его из свойств нельзя, группа
  считается неопределённой и применяется то же правило малой группы — шаг `10`
  без условия по цене.
- Если у карточки нет закупочной цены, количество не округляется вообще: в заказ
  идёт точное расчётное значение. Округление разрешено только там, где проверено
  условие «цена не выше медианы»; без цены проверять нечего, а шаг округления
  вслепую раздул бы заказ по карточке, о которой ничего не известно. На
  `2026-08-19` таких строк в расчёте `0` из `415`.

**Решение `2026-08-19`:** количество, поднятое до минимальной представленности
`13` шт правилом «Маржинального потока», является финальным: округление из
таблицы выше поверх него не применяется. Порядок такой же, как у минимальной
партии дешёвых сегментов. Если целевой запас задала адаптивная потребность, а не
минимум, округление работает обычным порядком. Канон правила —
`docs/specs/assortment-lifecycle-policy.md`.

**ОТМЕНЕНО (2026-08-19):** база медианы «папка бренда каталога 1С»
(`Дисплеи для Apple iPhone` и аналогичные). Причина: папка — ручная раскладка,
и перекладывание карточки сотрудником меняет её ценовую группу без следа в
свойствах. База заменена на свойства карточки — предмет и бренд.

Проверка расхождений на `2026-08-19` (важно для чтения правила): фактических
ошибок раскладки в папках дисплеев не найдено. Все `78` карточек из `2677`, у
которых реквизит бренда не совпадает с брендом в имени папки, — мультибрендовые
дисплеи вида `Дисплей для Tecno Spark 7 / Infinix Hot 10i`: бренд из имени папки
присутствует в названии у `78` из `78`, и у `62` из них оба бренда есть в
названии, причём бренд папки стоит первым. То есть расходится не раскладка, а
выбор одного бренда из нескольких совместимых. Поэтому правило обязано задавать
детерминированный выбор бренда для мультибрендовых карточек — см. пункт про
группу бренда выше.

Проверка предмета на `2026-08-19`: `19` карточек из `2677` в папках дисплеев
имеют предмет, отличный от дисплея (`корпус`, `инструмент`, `аккумулятор`,
`держатель для смартфона`, `Дисплеи/сенсор/стекло`), при том что все `19`
называются `Дисплей для ...` и лежат в правильной папке. То есть ошибочен
реквизит, а не раскладка. Жёсткий отбор по `subject_1c = дисплей` выбросил бы эти
`19` карточек из расчёта, поэтому предмет применяется как мягкий признак: отбор
идёт по составу расчёта дисплеев, а расхождение предмета выводится сигналом на
проверку и не исключает карточку.

**РЕШЕНО (2026-08-19):** разделение по классу устройства внутри бренда
сохраняется. Класс определяется по названию карточки, а не по папке: `планшет`,
`часы`, `телефон`. Причина: дисплей планшета дороже дисплея телефона того же
бренда примерно в полтора раза (`Apple`: медиана `355` против `218,50`;
`Samsung`: `165` против `116`), и склейка классов разрешила бы округлять дорогие
планшетные позиции. Признак из названия точнее папки — находит `170` планшетов
против `86`, которые выделяет папка: `Huawei MediaPad`/`MatePad`, `Lenovo Tab`,
`Acer Iconia` лежат в общих папках бренда. Плата за разделение: групп становится
`36` вместо `24`, карточек в малых группах — `66` из `1642` вместо `45`, то есть
на `21` карточку больше округляется без ценовой проверки; при этом `31` карточка
перестаёт сравниваться с чужой медианой.

**ОТМЕНЕНО (2026-08-19):** прежняя лестница округления `больше 100 → до 10`,
`больше 1000 → до 50`, `больше 2000 → до 100` без условия по цене. Причина:
правило не различало дешёвые и дорогие карточки и раздувало закупку дорогих
позиций.

### Минимальная партия и предохранитель по излишку — решение `2026-08-19`

- Минимальная нормальная партия для дешёвых сегментов (`economy`, `mid_low`)
  сохраняется в прежнем виде: `20` шт для `super_fast`, `12` шт для `fast`,
  `10` шт для `normal`.
- Минимальная партия является финальным количеством: округление из раздела выше
  поверх неё не применяется. Поднятые до партии `12` шт остаются `12` шт.
- Предохранитель по излишку: если подъём до минимальной партии создаёт запас
  больше чем на `30` дней сверх целевого, строка уходит в ручную проверку.
  Порог `30` дней действует одинаково для всех классов скорости.
- Порог задаётся только в трёх правилах дешёвых сегментов (`economy`, `mid_low`
  для `super_fast`, `fast`, `normal`) — там, где есть подъём до минимальной
  партии. Дорогим сегментам (`mid_high`, `premium`) поле излишка не заводится:
  количество там не поднимают до партии, режим `ровно по потребности`, и излишку
  взяться неоткуда. Их защиту — точное количество плюс ручная проверка выше
  `p75` — это решение не меняет.
- Ценовые сегменты `economy / mid_low / mid_high / premium` считаются
  по-прежнему — квартилями по всем карточкам расчёта дисплеев, а не внутри
  группы бренда. Этим решением они не меняются.

**Исправление сигнала `2026-08-20`.** Сигнал
`price_batch_minimum_applied` означает только одно: исходная расчётная
потребность была меньше минимальной партии, и итог действительно поднят до этой
партии. Обычное округление вверх при уже достигнутом минимуме не считается
применением партии. После адаптивного пересчёта сигнал не наследуется с раннего
этапа, а снимается и вычисляется заново по финальным значениям
`recommended_order_qty_raw`, `recommended_order_qty` и
`price_batch_min_qty`. На данных `2026-08-20` прежний сигнал стоял на `117`
строках. Первичный аудит разделил их на `70` ложных (`raw >= minimum`) и `47`
предположительно фактических (`raw < minimum`). Строгая проверка финального
sync-ready уточнила результат: у `39` из этих `47` итог тоже ниже партии;
фактический подъём до минимума есть только у `8` строк. Регрессионные примеры:
`31 -> 35` при минимальной партии `10` — только округление, сигнала нет;
`160 -> 160` при партии `20` — количество не менялось, сигнала нет.

Отдельное найденное расхождение: adaptive/family overlay в части строк оставляет
итог ниже `price_batch_min_qty` (`1 -> 5` при партии `10`). Исправление сигнала
не меняет количество и не маскирует это расхождение; повторное применение
минимальной партии после всех overlay требует отдельного qty-diff и повторной
проверки предохранителя `30` дней.

Текст адаптивной рекомендации показывает изменение количества и горизонта как
два независимых факта. Формулировка вида «адаптивный расчёт увеличил заказ:
горизонт `105 -> 82` дней» не используется, потому что ошибочно связывает
направление количества с направлением горизонта.

**ОТМЕНЕНО (2026-08-19):** разные пороги излишка `7 / 14 / 21` день для
`super_fast / fast / normal`.

### `stockout_guard` — принято, код ожидает доработки

Решение от `2026-08-17` и формула находятся в
`docs/specs/assortment-lifecycle-policy.md`. Техническая поверхность должна:

- проверять сигнал для каждой карточки `sale / Растим (ПРОДАЖА)` и
  `working / Поддерживаем (Рабочий)` независимо от результата `order` или
  `do_not_order`;
- вычитать из продаваемого остатка только активные `Заказы покупателей`; поля
  1С `Зарезервировано` и `Под заказ` не использовать;
- не запускать `stockout_guard` для строки с действующим блокером заказа;
- при `order` сохранить рассчитанное количество и показать срочный риск с
  действиями по ускоренному маршруту, перемещению, локальной закупке или
  подтверждённой замене;
- при `do_not_order` создать внеплановую потребность или ручную задачу.

**ОТМЕНЕНО (2026-08-17):** проверять `stockout_guard` только после решения
`do_not_order`. До отдельной кодовой задачи действующая реализация остаётся
старой; эта документационная правка не разрешает deploy или изменение
production.

## Помощник формирования заказов

`Помощник` находится между автоматическим расчётом и реестром заказов. Расчёт
создаёт предварительно сгруппированные проекты в БД `pricing-service`, но не
подтверждает их и не передаёт в 1С. Закупщик проверяет строки в помощнике и
командой `Собрать проекты заказов` переводит полностью выбранные готовые проекты
в статус `approved`. Передача в 1С остаётся отдельным ручным действием в
разделе `Заказы`.

Рабочая таблица содержит исходное фото, потребность, поставщика, закупочную цену
и её изменение, рентабельность, процент брака и объём исторической базы, срок
поставки и решение по строке. Колонки `Что мешает` нет: блокировки показываются
через недоступность сборки и адресные сообщения.

**Решение `2026-08-19`:** счётчик быстрого фильтра обязан совпадать с числом
строк, которые этот фильтр показывает.

- `Можно собрать N` — строки готовых проектов без снятой потребности: именно они
  уйдут в сборку. Раньше фильтр показывал ещё и снятые строки того же проекта,
  поэтому на кнопке было `31`, а в таблице `67`.
- `Все N` считает все показанные строки, включая снятые новым расчётом: их видно
  намеренно (решение сохранено), поэтому счётчик берётся по списку, а не по
  активным строкам сервера.
- У каждого фильтра есть подсказка, объясняющая отбор; она же выводится строкой
  в панели таблицы.
- Название поставщика в строке — кнопка, открывающая правую панель с профилем
  поставщика и условиями по этой строке. Название переносится внутри своей
  колонки и не заходит на соседнюю.

Оригинальное фото обязательно для серверной сборки проекта. Миниатюра используется
только для быстрого просмотра; пакеты `Список + фото` и `Фото отдельно` содержат
URL исходного изображения без повторного сжатия.

Карточка и исходное фото разрешаются read-only через публичный каталог
`https://master-mobile.ru/catalog/?q=<артикул>`. Автоматически принимается только
единственное точное совпадение артикула с повторной проверкой на canonical-карточке;
сопоставление по названию запрещено. В `payload` строки сохраняются
`product_card_url`, `photos[0].thumbnail`, `photos[0].original` и
`photo_source=master_mobile_site`, а API отдельно отдаёт ссылку карточки и источник
фото. Backfill по умолчанию работает как dry-run, затрагивает только открытые строки
помощника и при apply создаёт rollback-manifest, повышает версии и пишет событие,
не меняя количество, цену, поставщика, статус, Bitrix24 или 1С.
Если строка содержит внутренний код 1С вида `РБ...`, публичный артикул определяется
только через точное соответствие `code_1c -> article` локального каталога; несколько
разных артикулов для одного кода считаются неоднозначностью и не применяются.
Повтор apply с тем же committed `--output-json` возвращает сохранённый результат без
обращения к БД и не может перезаписать rollback-manifest.

Правая панель использует версионируемый профиль по точному `supplier_ref` 1С.
Класс `A/B/C`, преимущества и внутренний комментарий вводятся согласующим вручную;
число заказов, сроки, история цен и подтверждённый брак обновляются read-only из
1С. Официальные условия оплаты относятся только к точному договору поставщика.
Если реквизит договора не заполнен, API возвращает `terms_status=missing`, а UI
показывает «Не заполнено в 1С» без использования клиентских кредитных полей.
При обогащении дополнительно подтверждаются точный `contract_ref` и его владелец
`supplier_ref`; реквизиты контроля клиентской задолженности не считаются условиями
поставщика и намеренно не читаются как отсрочка или кредитный лимит.

### Подписи сигналов расчёта — решение `2026-08-19`

- Каждый код сигнала расчёта обязан иметь понятную русскую подпись в интерфейсе.
  Неизвестный код больше не показывается закупщику как «Требуется дополнительная
  проверка»: эта фраза оставалась заглушкой и не объясняла причину.
- Одинаковые подписи в пределах строки схлопываются в одну; коды остаются в
  подсказке. Раньше строка печатала одну и ту же фразу три-пять раз подряд.
- Новый код сигнала расчёта считается незавершённой доработкой, пока для него не
  заведена подпись.
- Блокеры заказа приходят с префиксом `line_<номер>:`, а решение по статусу — как
  `classification_blocks_order:<статус>`. Интерфейс разбирает оба вида, собирает
  одинаковые причины в одну строку и перечисляет номера проблемных строк.
  Счётчик блокеров в реестре считает причины, а не строки, чтобы цифра сходилась
  с содержимым карточки.

### Проблемные строки в карточке заказа — решение `2026-08-20`

**Решение `2026-08-20`:** очередь внутри заказа сортируется по принципу
«проблемные строки сначала». В реестре заказов раздельно показываются количество
типов блокеров и количество затронутых строк. В строке доступны ссылка на
карточку товара, краткая конкретная причина проблемы, фактический процент брака,
рентабельность и объяснение применённого либо пропущенного округления.
Повторяющийся перечень общих сигналов скрывается. Причина семейного
перераспределения показывается только если количество SKU действительно изменено
относительно базового.

Семейный сигнал не выбирает аналог и не перераспределяет заказ автоматически.
Если закупщик решил вести другую карточку, интерфейс открывает ручное решение
`Кандидат на замену` с обязательным полем `Взамен ведём`. Поля количества заказа
и ручного минимума изменяются с шагом `1` штука.

**Дополнение `2026-08-20`:** hard blocker нельзя подтвердить в обход причины.
Помощник обязан назвать блокирующее условие, перечислить затронутые строки и
показать числовое основание: процент, объём истории, порог и известную партию.
Если числового evidence нет, строка получает технический блокер, остаётся
видимой, но не передаётся в 1С до нового расчёта либо явного исключения.

Вместо неактивного `Включить` помощник показывает `Разобрать N блокеров` и
открывает карточку заказа с проблемными строками в начале. Для hard blocker
разрешены только безопасные действия: исключить строку с обязательной причиной,
исключить с заполнением существующего `Взамен ведём` либо дождаться нового
расчёта. Автор, причина и выбранная замена сохраняются в журнале.

`accepted_matching_review` является предупреждением, а не блокером или
конфликтом заказа. Интерфейс объясняет, что нужно проверить рамку и качество, и
даёт сохраняемое действие `Сопоставление проверено`. Подтверждение действует
только для текущей версии реестра и текущего evidence; после их изменения
проверка требуется снова.

Ручные кандидаты очереди жизненного цикла не участвуют в массовом выборе. Для
них доступно отдельное решение `Перевести в Допродаём` либо `Оставить Рабочим`
с обязательной причиной; для `Допродаём` применяется действующее правило поля
`Взамен ведём` или отметки «замены нет».

**Дополнение по итогам UX-аудита `2026-08-20`:** причина блокировки и действие
разбора показываются один раз на проект. Счётчики разделяются на уникальные
причины и затронутые активные строки, например `1 причина · 2 проблемные
строки`. Внутри заказа сначала идут активные проблемные строки, затем остальные
активные, а исключённые строки по умолчанию свёрнуты и проблемными не считаются.

**Решение `2026-08-20` — гейт передачи по проблемным строкам.** Пока хотя бы
одна активная строка требует вмешательства закупщика, документ не передаётся в
`1С`: сервер отклоняет операцию, карточка отключает кнопку передачи и напоминает
разобрать проблемные строки с их номерами. Исключённые строки блокером не
считаются. Это правило уже реализовано общим `order_blockers`, поэтому отдельный
обход для комнаты разбора не вводится.

На ширине до `1100 px` таблицы заказа и lifecycle заменяются карточками. Форма
исключения открывается в доступном диалоге и не сжимается внутри колонки.
Показатели evidence подписываются по смыслу: возвраты партии не подменяются
общим браком поставщика, а отсутствие партии, рентабельности или подтверждённой
атрибуции показывается как `не определена`, `не рассчитана` или `данных нет`,
но не как `0%`.

**Финальный UX-cleanup `2026-08-20`:** исключённые строки свёрнуты по умолчанию
не только внутри заказа, но и в очереди помощника. Заблокированная передача
показывает рядом с основной кнопкой конкретное следующее действие, а проектное
предупреждение не повторяет построчные числовые evidence. Пользовательские
подписи не содержат raw-коды статусов, маршрутов, источников и уверенности.
Проценты форматируются по русской локали, а количество возвратов — с правильным
склонением во всех API- и UI-сообщениях.

### Выбор поставщика

**Решение `2026-08-21` — три последовательных этапа выбора поставщика.**

1. Если в карточке товара `1С` заполнен реквизит `Основной поставщик`, строка
   относится к этому поставщику.
2. Если реквизит пуст, применяется действующий алгоритм по истории поступлений
   за последние три года: учитываются поставщики, от которых приходил товар,
   средняя скорость их сборки и доступные данные о цене; кандидат выбирается по
   существующему историческому правилу без введения новой балльной формулы.
3. Если у карточки нет ни основного поставщика, ни пригодной истории, строка
   попадает в комнату разбора. Менеджер вручную выбирает поставщика в строке.

После ручного выбора строка сразу покидает комнату разбора. Она добавляется в
последний заказ этого поставщика в приложении, который ещё не вошёл в обмен с
`1С`; дата дневной партии сама по себе объединению не мешает. Если такого заказа
нет, создаётся новый. После распределения готовые заказы передаются в `1С`
действующим обменом.

Подтверждение записи выбранного поставщика обратно в карточку товара `1С` не
является условием выхода строки из комнаты разбора. Состояние
`pending_onec_write` остаётся информационной пометкой. Обратная запись реквизита
является отдельным контуром и не задерживает распределение текущей строки.

**Решение `2026-08-19`:** поставщик строки берётся из реквизита «основной
поставщик» карточки номенклатуры `1С` — он считается актуальным. История закупок
остаётся запасным источником и применяется только тогда, когда реквизит карточки
пуст. Двухступенчатый выбор ниже сохраняется как правило сравнения кандидатов и
не переопределяет основного поставщика карточки без явного решения закупщика.

**Уточнение и реализация `2026-08-20`:** один read-only снимок карточки
(`_Reference62._Fld851RRef`, справочник поставщиков `_Reference54`) переносится в
dry-run вместе с кодом и названием поставщика. Этот же снимок управляет и
количеством, и группировкой проекта заказа: adaptive lead-time сначала
фильтрует историю по `main_supplier_ref`. Если у заполненного основного
поставщика нет подходящей истории, используется базовый срок строки; выбирать
срок другого поставщика запрещено. История без фильтра применяется только при
подтверждённо пустом реквизите. Недоступный readback 1С считается отдельным
fail-closed состоянием, а не пустой карточкой.

Перед финальной группировкой проекта выполняется свежий readback карточки `1С`.
Он имеет приоритет над снимком раннего этапа расчёта: если поставщика изменили в
`1С` вручную после расчёта, приложение не возвращает старое значение из CSV.

**Третий сценарий — поставщик не определён (`2026-08-20`).** Карточки без
`Основного поставщика` и без пригодной истории закупок не исчезают: они
собираются в один проект `поставщик не определён`. Это комната разбора, а не
будущий документ `1С`; на заказе и каждой строке сохраняется блокер отсутствия
поставщика.

**Решение `2026-08-20`: выбор поставщика в приложении разрешён.** Закупщик
назначает поставщика прямо в строке комнаты разбора. Перед сохранением и перед
разнесением приложение повторно читает карточку номенклатуры: при расхождении
побеждает значение `1С`, ручная правка не перетирается. Пока сторона `1С` не
подтвердила реквизит, строка получает неблокирующую пометку «выбран, в карточке
ещё не записан». Локальный выбор хранится в payload строки с состоянием
`pending_onec_write`.

Прямая запись в SQL `1С` запрещена. Будущая запись реквизита выполняется только
файловым обменом свойств номенклатуры. Приём ссылочного реквизита на стороне
`УТ 10.3` и снятие production-флага записи — отдельная задача контура `1С`; в
текущую реализацию не входят.

**Комната разбора (`2026-08-20`, уточнено `2026-08-21`).** Действие `Разнести по поставщикам` сначала
показывает будущие проекты, номера строк и сообщает, какие строки останутся
неразобранными. После подтверждения разобранные строки переходят в открытый
проект выбранного поставщика, ещё не вошедший в обмен с `1С`, либо создают новый;
неразобранные остаются в комнате. Если комната опустела, её проект закрывается
состоянием `superseded`. Само разнесение ничего не отправляет в `1С`.

**Склад приёмки (`2026-08-20`).** Он всегда берётся из политики складов:
`РБ0000010` — `Сдэк Склад`, роль `central_transfer_stock`. История заказов
остаётся только запасным источником для legacy/direct-вызовов и не может
оставить склад пустым в штатном контуре. Попытка передать через CLI другой код
склада отклоняется.

По решению владельца от `2026-08-10` кандидаты второго исторического этапа
сравниваются в два внутренних шага.

1. **Жёсткая допустимость (`eligibility`).** Кандидат участвует в сравнении,
   только если поставщик активен, есть подходящие договор и валюта, актуальная
   закупочная цена, подтверждена возможность заказа и заполнены обязательные для
   этого товара документы и реквизиты.
2. **Прозрачная лестница (`scoring`).** Допустимые кандидаты проходят критерии
   последовательно, без суммирования неподтверждённых весов:
   1. поставщик успевает поставить товар до прогнозного дефицита;
   2. отсутствует жёсткий блокер качества;
   3. сравнивается полная известная стоимость: закупочная цена плюс известные
      расходы доставки;
   4. близкой считается разница полной известной стоимости не более `3%`
      (`supplier_cost_tie_pct=3`); внутри этого коридора выигрывает более
      быстрый и стабильный поставщик, а при разнице `>3%` — кандидат с меньшей
      полной стоимостью из тех, кто успевает до дефицита;
   5. затем учитываются MOQ/кратность, условия оплаты и история исполнения.

Выбранный поставщик и пройденные ступени показываются закупщику. Ничья,
недостаток данных или отсутствие кандидата, успевающего до дефицита, не отменяют
ежедневный расчёт и не скрывают внутренний проект: интерфейс показывает 2–3
лучших доступных кандидата, проект получает состояние `поставщик требует
подтверждения` и не передаётся в 1С до явного решения закупщика.

Фиксированная балльная формула не используется. В будущем weighted score можно
считать только в теневом режиме и сравнивать с решениями закупщика до отдельного
утверждения. Порог близкой полной стоимости утверждён на уровне `3%`. Текущая
реализация умеет использовать кандидата и историю lead time, но полной лестницы
по всем перечисленным факторам и порога `supplier_cost_tie_pct` не выполняет;
правило остаётся требованием следующей кодовой задачи.

Метрики строки считаются за 180 дней. Рентабельность равна
`(чистая выручка − себестоимость) / себестоимость × 100`; при нулевой
себестоимости значение пустое и сопровождается причиной. Изменение цены берётся
по двум последним проведённым заказам одинаковых `поставщик + SKU + валюта`.
Срок разделён на сборку у поставщика, логистику и общий срок, с уровнем источника
`sku|display_group` и уверенностью; legacy `delivery_days` остаётся в контракте,
но UI его не использует. Если последние закупки есть только в другой валюте,
процент не рассчитывается: API возвращает `price_change_status=currency_mismatch`,
ожидаемую и доступные валюты, а UI показывает эту причину без ложного блокера.

Брак товара считается только по возвратам с причиной брак/качество/дефект.
`supplier_defect_pct` появляется только при доказанной связи с поставкой или
партией конкретного поставщика; иначе UI показывает отдельный брак товара с
пометкой «поставщик не подтверждён». База `<30` — `weak`, `30–99` — `warning`,
`>=100` — `reliable`.

По решению владельца от `2026-08-10` действуют два жёстких блокера качества:

1. `supplier_defect_attribution=supplier_exact`, подтверждённый брак выбранного
   поставщика `>10%` и база не менее `100` проданных единиц.
2. Аварийный сигнал партии: не менее `5` подтверждённых дефектов и одновременно
   не менее `40%` от продаж за применимое окно.

Брак товара без точной связи с выбранным поставщиком не обнуляет
`final_quantity` автоматически, но показывается как предупреждение и требует
явного решения закупщика: подтвердить продолжение, сменить поставщика или
исключить строку. Для точного поставщика база `<30` остаётся информационной,
база `30–99` даёт предупреждение и ручную проверку, но также не обнуляет
количество. Отсутствие данных означает `unknown`, а не `0%`.

Точный поставщицкий блокер `>10%` на базе `≥100` уже реализован. Аварийный
сигнал `≥5` и `≥40%` реализован в dry-run только для карточек основного прогона
и ещё не охватывает ранние статусы с окна от первой продажи. Явное событие
подтверждения закупщиком предупреждения при неизвестной атрибуции или слабой
базе также не реализовано; до этих доработок UI не должен обещать полный
workflow двухуровневой защиты.

### Уверенность расчёта

По решению владельца от `2026-08-10` единый порог `80/85/90` не используется.
Поле `confidence_category` принимает объяснимую категорию по худшему
существенному фактору:

- `red` — есть хотя бы один hard blocker; внутренний проект сохраняется и виден,
  но передача в 1С запрещена;
- `yellow` — hard blocker отсутствует, но есть слабая история, неизвестный или
  другой некритичный фактор; количество не обнуляется, проект не скрывается,
  перед 1С требуется явное решение закупщика;
- `green` — обязательные данные свежие и полные, поставщик определён,
  предупреждений и блокеров нет.

API и интерфейс должны отдавать не только категорию, но и список
`confidence_reasons`; один хороший фактор не может арифметически компенсировать
hard blocker. Numeric score `0–100` в будущем допускается только как shadow-
показатель для сравнения с решениями закупщика и не управляет созданием проекта
или передачей в 1С без отдельного утверждения.

Сейчас в коде есть отдельные признаки и `lead_time_confidence`, но общей
`confidence_category` с полным списком причин и событием подтверждения жёлтой
категории нет. Это остаётся кодовой задачей.

### Лимиты суммы и количества на текущем этапе не применяются

По решению владельца от `2026-08-10` приложение показывает полную рассчитанную
потребность и её стоимость. Сумма проекта и количество строки сами по себе не
являются hard blocker, не создают `confidence_category=yellow`, не обрезают и
не обнуляют рекомендацию. Бюджетный контроль откладывается до утверждения
бюджетной модели.

**ОТМЕНЕНО (2026-08-10):** предыдущее решение считать необычную сумму или
количество относительно профиля товара и истории заказов мягким лимитом,
переводящим проект в `yellow`. Проверка переписки восстановила прямое решение
владельца от `2026-07-19`: «на сегодня без лимита»; бюджетный рычаг планировался
только после решения вопросов бюджета.

В действующей policy глобальный потолок количества уже снят:
`max_order_qty=null`, поэтому dry-run показывает полную рассчитанную
потребность. Профильные `yellow`-сигналы по сумме и количеству реализовывать не
требуется до отдельного решения после утверждения бюджетной модели.

### Очередь свойств и правило второго сотрудника

**Решение `2026-08-19`:** запрет самоутверждения виден до нажатия кнопки. Очередь
свойств отдаёт по каждому предложению `can_approve`, `can_reject` и
`self_proposed`; автору и не допущенному сотруднику кнопка `Принять` показывается
неактивной с объяснением. Раньше правило срабатывало только на сервере, и
пользователь получал ответ `classification proposal cannot be self-approved` на
английском без подсказки, что делать. Исключение прежнее: `Допродаём` назначает
один человек (решение `2026-08-18`).

Тексты ошибок сервера переводятся в одном словаре
(`ui/src/utils/procurementErrorMessages.ts`) и используются во всех экранах
приложения, а статусы предложений показываются по-русски.

## Ручные свойства

Доступные статусы: `Поддерживаем` (`working`), `Матричный`, `Под заказ`, `Кандидат на замену`, `Выводим` (`nonliquid`), `Не закупать`, `Допродаём` (`pension`). Решением от `2026-08-18` `Допродаём` включён в рабочий список: правила статуса — в политике жизненного цикла.

- Причина обязательна.
- При ручном минимуме обязательна дата пересмотра.
- `Не закупать`, `Кандидат на замену`, `Выводим`, `Допродаём` блокируют строку.

## Безопасный запуск

По умолчанию оба флага записи выключены:

```env
PROCUREMENT_ORDER_FORMATION_PROPERTY_APPLY_ENABLED=false
PROCUREMENT_ORDER_FORMATION_ONEC_APPLY_ENABLED=false
```

Решением владельца от `2026-08-10` ежедневный автоматический расчёт и создание
сгруппированных по поставщикам внутренних `draft` являются штатной работой
приложения, а не отдельным риск-гейтом. Предварительное совпадение количества с
решением человека для создания таких проектов не требуется. Закупщик открывает
проект в приложении, проверяет и при необходимости исправляет количество.

Внутренний `draft` не является заказом поставщику. Передача в 1С выполняется
только отдельным ручным действием пользователя в приложении и создаёт только
непроведённый `ЗаказПоставщику`; автоматическая передача и проведение запрещены.
До появления документа в 1С smart-process не создаётся и в формировании заказа
не участвует. Возможный smart-process после фактического заказа относится к
отдельному контуру оплаты, логистики и приёмки.

Требование `transmit_order()` к пользовательской сессии и запись пользователя
как согласовавшего являются обязательным контрольным шлюзом. Backend не должен
создавать черновик `ЗаказПоставщику` в 1С без подтверждения количества
допущенным сотрудником закупки; это не запрещает внутренний автоматический `draft` в БД
`pricing-service`. Даже после подтверждения в 1С передаётся только `draft_only`.

Порядок пилота:

1. Применить миграции и развернуть backend/UI.
2. Настроить отдельные OAuth-параметры приложения и LEFT_MENU placement.
3. Провести `3–5` рабочих дней dry-run без записи свойств и заказов в 1С.
4. Применить одно тестовое свойство и проверить readback по CommerceML.
5. После подтверждения количества допущенным сотрудником закупки создать один непроведённый
   тестовый `ЗаказПоставщику`.
6. Не включать автоматическое проведение документов.

# Source of Truth

- Публичные маршруты находятся под `/api/procurement-order-formation`.

- Файловый обмен с 1С использует версионированные XML payload/result и

# Rollout

Два P0-разрыва исправлены и проверены локальными регрессиями. Следующий отдельный
операционный шаг — развернуть изменение и подтвердить ежедневное сохранение
внутренних проектов в production без дополнительного гейта совпадения количества
с решением человека. Текущая реализация не выполняет deploy и не меняет внешние
флаги production, Bitrix24 или 1С.

**ОТМЕНЕНО (2026-08-10) для включения только внутренних проектов:** обязательные
XML round-trip с 1С и отдельное бизнес-решение после live dry-run. Эти требования
сохраняются для реальной передачи в 1С. До отдельного rollout-решения
`PROCUREMENT_ORDER_FORMATION_ONEC_APPLY_ENABLED=false`; автоматическое проведение
документа запрещено.

Первый реальный тест 1С выполняется по следующему протоколу:

1. Внутренний автозаказ успешно отрабатывает три рабочих дня подряд после
   исправления двух P0-разрывов; проверены ежедневное обновление, построчная
   защита ручных правок и создание ревизий после подтверждения.
2. Допущенный сотрудник закупки выбирает один небольшой проект без блокеров и вручную сверяет
   поставщика, договор, склад, валюту, номенклатуру, количество и закупочную
   цену.
3. Проект передаётся одной ручной командой; в 1С должен появиться только
   непроведённый `ЗаказПоставщику`.
4. В 1С выполняется readback перечисленных реквизитов. Повторная команда для той
   же версии не должна создать второй документ или новый `message_id`.
5. До отдельного решения обычная ручная передача остальных проектов остаётся
   выключенной. Автоматическая передача и автоматическое проведение запрещены.

Эта фиксация определяет будущий протокол приёмки, но сама по себе не разрешает
текущему документационному изменению переключать флаги или отправлять данные в
1С.
