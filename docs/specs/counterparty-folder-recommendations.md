# Назначение

Контур выявляет контрагентов с открытой дебиторкой, у которых папка в
`Справочник.Контрагенты.Родитель` не совпадает с папкой подразделения, создавшего
старейший просроченный долг. V1 не меняет 1С: сервис только строит рекомендации и
выгружает dry-run отчет для ручной сверки с финансами и руководителями розницы.

Дополнительно контур хранит ежедневные read-only снимки текущих папок
контрагентов в `pricing-service` и показывает фактические изменения папок между
двумя снимками. Это не определяет пользователя, который поменял папку в 1С, но
сужает окно разбора до суток.

# Scope / Out of Scope

Входит:
- расчет статусов `move_recommended`, `ok`, `no_overdue`, `needs_review`;
- выбор источника долга по read-only ведомостной логике 1С: РТУ, оплаты,
  возвраты, урегулирования и общий остаток контрагента;
- проверка просрочки по текущей глубине кредита;
- чтение текущей папки контрагента и папки подразделения из 1С;
- ежедневный read-only снимок папок контрагентов в БД `pricing-service`;
- daily diff папок между текущим и предыдущим снимком;
- management API и CSV wrapper для ежедневной выгрузки.

Не входит:
- автоматическое изменение `Контрагент.Родитель` в 1С;
- определение пользователя, который вручную поменял папку в 1С;
- Bitrix/Telegram доставка без отдельного acceptance и включения root orchestration.
- новый канал записи в 1С: будущие команды бота должны использовать существующий
  файловый обмен `UT103_EXCHANGE_ROOT` из `docs/specs/ut103-bot-command-file-exchange.md`.

  взаиморасчётов `_AccumRgT7009 + _AccumRg7002`: после последнего устойчивого

  оставшийся долг. Полностью погашенные документы исключаются; частично
  погашенный остается с прежней датой и остатком. Непрерывный read-only баланс,
  контроль суммы и защита неполной истории сохраняются. Общий кеш и счетчик
  возраста используют решение `2026-09-10` из
  `docs/specs/receivables-smart-process-workflow.md`. Автоперенос папок в 1С
  этим изменением не разрешается.
- Внутридневные отрицательные строки перепроведения не считаются закрытием долга,
  если итог того же дня снова положительный. Это не позволяет свежей РТУ
  перепроведения подменить более ранний фактический источник.
- Прямые ПКО/урегулирования и локальная ведомостная эвристика остаются
  диагностическим enrichment, но не переопределяют подтверждённый непрерывным
  полным регистром источник и не создают готовую рекомендацию сами по себе.
- Если сумма выбранных открытых РТУ отличается от текущего долга более чем на
  `0,01 ₽`, документ и папка не назначаются, строка попадает в `data_quality`.
- Если подтверждённые открытые РТУ относятся к разным папкам, рекомендация
  очищается, а строка попадает в `business_review`.

- Строки без заполненного срока оплаты больше не переводятся массово в
  `needs_review`; для отчета применяется read-only срок `7 дней` от даты
  исходного документа.
- Ежедневные списки `move_recommended` и `needs_review` не включают мелкие долги
  ниже `500 ₽`; summary показывает, сколько строк скрыто этим порогом.
- Готовые `move_recommended` временно выключены: отчет показывает ручную
  диагностику открытых реализаций по ведомостной логике 1С, но не дает
  инструкцию на перенос до приемки.
- Источник долга больше не берется напрямую из
  `receivable_balance_snapshot.origin_document_ref`: отчет строит ведомостную
  ленту по контрагенту, закрывает РТУ оплатами/возвратами/урегулированиями и
  выбирает открытые реализации по правилам сверки Максима.
- Закрытые по ведомостной логике или структуре 1С реализации не показываются как
  долгообразующие; если открытые реализации не найдены, строка остается
  диагностикой с русской причиной.
- В рекомендации к переносу не попадают сотрудники, оптовый контур, `Выдача без
  оплаты`, группа `Поставщики Китай`, совпадающие папки, межпапочные СПБ-кейсы и
  строки из папки `08. Сайт`, где нужно проверить оплату через заказ/карту сайта.
- Bitrix-preview показывает открытые документы по ведомостной логике 1С,
  ответственного РТУ, конечный остаток ведомости и правило выбора источника, а
  технические причины заменяет на русские пояснения.
- CSV и Bitrix-preview показывают код клиента из карточки контрагента 1С, чтобы
  контрагента можно было быстрее найти в 1С.
- Wrapper формирует CSV и XLSX; при настроенной отдельной папке Bitrix Disk XLSX
  прикрепляется к задаче 756.
- Для embedded рабочего места дебиторки отчет может быть сохранен в локальный
  кеш `receivable_folder_recommendation_cache`; вкладка `Контроль папок` сначала
  читает кеш и только при его отсутствии уходит в live fallback.
- Спорные бизнес-эквиваленты папок нормализуются только по whitelist-алиасам:
  `Сайт` = `Онлайн-магазин`, `Теплый Стан` = `04.Теплый Стан`. Для Теплого
  Стана тем же бизнес-разделом считаются `Радиорынок «Электромир»` и
  `Теплый стан Радиорынок "Электромир" пав. 652`. Алиасы используются для
  отображения и сравнения, но не меняют refs и raw-названия из 1С.

# Acceptance Criteria

- Долг без `planned_payment_date`, `credit_depth_days` и `due_date` считается
  просроченным по `origin_document_date + 7 дней`, если документ старше этого
  срока.
- Долг младше или ровно `7 дней` не попадает в ежедневные рекомендации; строка
  может попасть в список только на 8-й день и позже.
- Долг меньше `500 ₽` не попадает в `move_recommended` или `needs_review`.
- Если `credit_depth_days > 0`, расчетный fallback `7 дней` не подменяет
  исходную глубину кредита.
- Исключения по сотрудникам, опту, `Выдача без оплаты`, совпадающей папке,
  СПБ-в-СПБ и сайт-долгам не попадают в `move_recommended`.
- Без подтверждения структуры документа в 1С готовых рекомендаций к переносу нет:
  несовпадение папок попадает в ручную диагностику с русским пояснением.
- Если полный регистр показывает устойчивое закрытие долга на конец дня,
  реализации до этой даты не показываются как источник текущего долга.
- Если ПКО закрывает одну РТУ рядом в ведомости с допуском `±50 ₽`, РТУ считается
  оплаченной.
- Если ПКО закрывает несколько соседних РТУ, отчет суммирует до `7` РТУ
  вверх/вниз с допуском `±100 ₽`.
- Если оплаты идут без привязки к РТУ, отчет выбирает открытые документы
  bottom-up только при отсутствии подтверждённых структурой открытых РТУ и
  только внутри незакрытого сегмента ведомости: снизу вверх суммирует РТУ до
  превышения общего долга. Такой результат остается диагностическим fallback.
- Подтверждённые структурой открытые РТУ сортируются от старых к новым; папка и
  ответственный берутся из фактически выбранной первой открытой РТУ.
- Расхождение суммы открытых документов и текущего долга допускается только в
  пределах `0,01 ₽` включительно; большее расхождение не создаёт рекомендацию.
- Контрагенты из группы `Поставщики Китай` не попадают в ежедневный
  `needs_review`.
- Контрагент `РБ028196` (`Маклаб СПБ ПРОСВЕТ`) не попадает в ежедневный
  `needs_review`.
- В Bitrix-комментарии нет технического кода
  `folder_mismatch_payment_term_missing`; номер и дата накладной видны в preview.
- В Bitrix-комментарии и CSV/XLSX есть код клиента из 1С, ответственный РТУ,
  конечный остаток ведомости, сегмент ведомости и правило выбора источника.

# Source of Truth

`1С` остается системой учета для контрагентов, подразделений, папок и документов
долга. `pricing-service` использует локальную витрину дебиторки
`receivable_balance_snapshot` для суммы открытого остатка, но источник долга для
отчета выбирает заново по ведомостной логике на read-only событиях 1С.

# Data Flow

1. `pricing-service` берет строки `receivable_balance_snapshot` за дату отчета с
   положительной открытой дебиторкой.
2. Для каждого контрагента читает из 1С текущую папку:
   `_Reference54._ParentIDRRef`.
3. По каждому контрагенту собирает read-only ведомостную ленту из
   `receivable_ledger_event`: реализации, оплаты, возвраты, урегулирования и
   корректировки до конца даты отчета.
4. Для кандидатов дополнительно читает read-only структуру:
   `_Document203._Fld4939_RTRef/_Fld4939_RRRef -> _Document132`, движения
   `_AccumRg7550`, прямые приходники `_Document196` и урегулирования
   `_Document201` по основанию реализации или заказа.
5. Ведомостная логика закрывает РТУ прямыми ПКО, возвратами, пачками соседних
   РТУ под один ПКО. Для кандидатов заранее запрашивается структура 1С.
6. Если структура подтверждает открытые РТУ, именно они становятся источником
   долга и сортируются от старых к новым. Bottom-up применяется только при
   отсутствии подтверждённых открытых РТУ и не считается готовой рекомендацией.
7. Для выбранной открытой реализации читает подразделение, ответственного РТУ и
   legacy-автора для отладки:
   `_Document203._Fld4937RRef -> _Reference68`.
   Ответственный РТУ читается из `_Document203._Fld4950RRef -> _Reference69`.
   Legacy-автор читается из `_Document203._Fld4942RRef -> _Reference54`, но не
   выводится в человекочитаемый отчет.
8. Ведомостная логика считает `statement_balance_after` после каждой строки и
   выбирает открытые РТУ только внутри сегмента после последней безопасной точки,
   где конечный остаток находится в диапазоне `0..100 ₽`. Если ПКО рядом
   относится к следующей РТУ, такая строка не считается безопасным закрытием
   предыдущего сегмента.
9. Рекомендуемую папку берет из `Справочник.Подразделения.ОсиГруппа`:
   `_Reference68._Fld8927RRef -> _Reference54`.
10. Сравнивает текущую и рекомендуемую папку. Перед сравнением применяет только
   утвержденные alias-группы бизнес-эквивалентов; fuzzy-сопоставления без явного
   whitelist не используются.
11. Возвращает статус и человекочитаемые display-названия папок/подразделений.
12. Если открытый долг есть, папка не совпадает, но срок оплаты не рассчитан
   (`planned_payment_date`, `credit_depth_days`, `due_date` отсутствуют), отчет
   использует read-only fallback `7 дней` от даты выбранной открытой реализации. Это
   только расчет внутри отчета: 1С не меняется.
13. Для ежедневных списков отчет скрывает строки ниже `500 ₽` и строки без
   эффективной просрочки после срока оплаты.
14. Отдельный snapshot flow читает из 1С все активные элементы справочника
   контрагентов (`_Marked = 0`, `_Folder = 1`) и сохраняет текущую папку за дату.
15. Diff flow сравнивает текущий снимок с предыдущим сохраненным снимком. Если
   контрагент есть в открытой дебиторке за дату отчета, строка дополнительно
   получает сумму долга, документ долга и рекомендуемую папку.
16. Root orchestration может забрать отчет через API и доставить его в канал
   управления; dedupe ключ доставки: `date + status + report_revision + task_id`.

# API / Data Contracts

Endpoint:

```http
GET /api/management/counterparty-folder-recommendations?date=YYYY-MM-DD
```

Параметры:
- `date` - дата снапшота дебиторки;
- `status` - необязательный фильтр: `move_recommended`, `ok`, `no_overdue`,
  `needs_review`;
- `limit` - необязательное ограничение количества строк.
- `queue` - `actionable`, `business_review`, `data_quality`, `excluded` или
  `all`; по умолчанию `all`, фильтрация выполняется до `limit`.

Ответ:
- `as_of`, `freshness_status`, `source_status`;
- `report_revision` - короткий hash состава выгрузки;
- `summary` - счетчики строк и суммы;
- `payload[]` - контрагент, текущая папка, рекомендуемая папка, display-названия
  папок/подразделений после whitelist-нормализации, подразделение долга, сумма,
  основной открытый документ `debt_document_*`, ответственный РТУ
  `debt_document_responsible_*`, legacy-документ витрины `origin_document_*`,
  список `open_debt_documents`, конечный остаток `statement_balance_after`,
  границы сегмента `statement_segment_*`, правило выбора источника, просрочка,
  статус и причина ручной проверки.
- `exclusion_reason`, `business_review_reason`, `queue`, `signal_key` и
  `action_required` отделяют исключения, бизнес-решения и проблемы качества.
- дополнительные поля структуры: статус проверки, остаток по структуре,
  связанный заказ и закрывающие документы.

Embedded endpoint рабочего места:

```http
GET /api/receivables/workplace/folder-recommendations?date=YYYY-MM-DD
```

Этот endpoint использует тот же расчет и тот же контур доступа. Штатный путь для
Bitrix UI - чтение сохраненного full-cache отчета за дату с последующей
фильтрацией по доступным подразделениям пользователя. Если кеша за дату нет,
endpoint использует старый live fallback с ограниченным preview кандидатов и
возвращает `source_status=fallback_live`, чтобы UI и диагностика видели
нештатный режим.

Кеш пересчитывается вручную или из daily orchestration. Штатный daily path -
`infra/cron/receivable_ledger_sync.sh`: после успешного
`tasks.rebuild_receivable_read_models` он запускает
`tasks.rebuild_receivable_workplace_cache` для той же даты и сохраняет полный
отчет `Контроль папок`. Если кеш-пересчет не прошел, основной импорт дебиторки
не блокируется по умолчанию; строгий режим включается через
`RECEIVABLE_WORKPLACE_CACHE_REQUIRED=1`.

```bash
python tasks/rebuild_receivable_workplace_cache.py --date YYYY-MM-DD
```

CSV wrapper:

```bash
python infra/cron/counterparty_folder_recommendations_from_a.py \
  --date YYYY-MM-DD --status move_recommended
```

По умолчанию wrapper экспортирует CSV и XLSX-артефакты и state. С `--dry-run`
он ничего не пишет. При наличии
`COUNTERPARTY_FOLDER_RECOMMENDATIONS_B24_DISK_FOLDER_ID` и Bitrix task id XLSX
загружается в отдельную папку Bitrix Disk и прикрепляется к задаче.

Endpoint для read-only снимка папок:

```http
POST /api/management/counterparty-folder-snapshots/sync?date=YYYY-MM-DD
```

Ответ:
- `summary.fetched_count` - сколько активных контрагентов прочитано из 1С;
- `summary.inserted_count`, `updated_count`, `deleted_count` - что изменилось в
  локальном снимке за дату.

Endpoint для изменений папок:

```http
GET /api/management/counterparty-folder-changes?date=YYYY-MM-DD
```

Параметры:
- `date` - дата текущего снимка;
- `previous_date` - необязательная дата для сравнения; если не указана, берется
  ближайший сохраненный снимок до `date`;
- `limit` - необязательное ограничение количества строк.

Ответ:
- `as_of`, `previous_as_of`, `freshness_status`, `source_status`;
- `report_revision` - короткий hash состава изменений;
- `summary` - количество изменений, размер текущего и предыдущего снимка,
  количество и сумма строк с открытой дебиторкой;
- `payload[]` - контрагент, код клиента, старая папка, новая папка, дата обнаружения и, если
  есть открытая дебиторка, сумма долга, документ долга и рекомендуемая папка.

# Invariants

- V1 не выполняет запись в 1С.
- Если позже появится запись в 1С, она идет только через общий файловый обмен
  `UT103_EXCHANGE_ROOT/to_1c/new -> UT103_EXCHANGE_ROOT/from_1c/new`, без прямого
  SQL и без отдельной новой папки под этот контур.
- Если долг не просрочен после открытого документа или расчетного срока оплаты,
  возвращается `no_overdue`. Если папки отличаются и исходный срок оплаты пустой,
  строка может сохранить `review_reason=folder_mismatch_payment_term_missing` как
  пояснение, но не продвигается в `needs_review` только из-за пустого срока.
- Долги ниже `500 ₽` подавляются из ежедневных списков и учитываются в
  `summary.below_min_balance_count`.
- Папки сотрудников, оптовый контур и контрагенты с маркером `Выдача без оплаты`
  не попадают в рекомендации к переносу.
- Межпапочные СПБ-кейсы не попадают в рекомендации к переносу; при просрочке они
  идут в ручную диагностику с причиной `spb_cross_folder_manual_review`.
- Whitelist-алиасы папок применяются только для сравнения и отображения.
  Исходные refs и raw-названия из 1С сохраняются в ответе и кеше без изменения.
- Для Теплого Стана canonical display — `04.Теплый Стан`; `Радиорынок
  «Электромир»`, `МСК-025 Радиорынок Электромир` и `Теплый стан Радиорынок
  "Электромир" пав. 652` считаются эквивалентными только через whitelist.
- Если текущая папка контрагента `08. Сайт`, а витрина дебиторки указывает
  подразделение магазина, строка не становится рекомендацией к переносу и не
  попадает в ежедневный `needs_review`; причина сохраняется как
  `origin_document_needs_order_payment_check`, пока ledger/order-chain и история
  документа не подтверждают фактический источник долга надежно.
- Если просроченных долгов несколько, источник строится по ведомостной логике в
  незакрытом сегменте после последней безопасной точки конечного остатка, а не по
  одному legacy `origin_document_ref` из витрины.
- В диагностическом rollout даже подтвержденный структурой открытый остаток не
  превращается в `move_recommended`; строка остается в `needs_review` до сверки с
  Максимом/Тимуром.
- `exclusion_reason` не перезаписывается диагностикой суммы или свежести.
- `РБ034645` и строки, где текущая либо рекомендованная папка нормализуется как
  `Поставщики`, всегда относятся к `excluded`.
- Открытые РТУ из разных папок не дают предполагаемую папку и относятся к
  `business_review`.
- Если непрерывный остаток с `2025-01-01` не сходится с текущим долгом более чем
  на `0,01 ₽`, не найден последний устойчивый неположительный день или суммы РТУ
  после него не покрывают долг, документы и папка не назначаются, строка
  относится к `data_quality`.
- Контрольные источники: `РБ008670` начинается с РТУ 2025 года без подмены
  документами 2026 года; `РБ028014` — `РБГУ0106586`, Лещенко Мария, Проспект
  Просвещения; `РБ008206` — `РБГУ0132302`, открытый остаток `90 ₽`;
  `РБ006368` — `РБГУ0198680`, папка `01. Горбушкин Двор`.
- Если нет документа, подразделения, папки подразделения или текущей папки
  контрагента, строка уходит в `needs_review`.
- Daily diff не создает изменений в первый день снимка, когда еще нет
  предыдущего снимка для сравнения.

# Errors / Edge Cases

- Нет `ONEC_DATABASE_URL` или 1С недоступна: API отвечает `503`.
- Неверный `status`: API отвечает `422` на уровне FastAPI validation.
- Нет снапшота за дату: `source_status=empty`, `freshness_status=missing`.
- Документ долга не найден в `_Document203`: `needs_review`,
  `review_reason=origin_document_not_found`.

# Tests

- Unit/integration тесты расчета статусов на sqlite-имитации 1С.
- API smoke тест с management bearer token.
- Проверка фильтра `status=move_recommended`.
- Проверка read-only fallback `7 дней` для долга без срока оплаты и с
  несовпадающими папками.
- Проверка структуры документа: открытая реализация, закрытая приходником
  реализация через заказ, отсутствие однозначных движений.
- Проверка непрерывного канонического остатка, расхождения суммы более
  `0,01 ₽`, частичного и полного погашения старейшего документа и перехода
  к следующему документу после полного закрытия. Прежняя проверка удержания
  старого источника независимо от оплат отменена решением `2026-09-10`.
- Проверка порога `500 ₽` и строгого правила `старше 7 дней`.
- Проверка исключений из рекомендаций: сотрудники, опт, `Выдача без оплаты`,
  совпадающая папка, `РБ028196`, сайт-долги и межпапочные СПБ-кейсы.
- Проверка XLSX wrapper: файл создается рядом с CSV, содержит фильтруемую шапку,
  а при настроенной папке Bitrix Disk прикрепляется к задаче без дублей.
- Проверка daily diff: первый день без ложных изменений, вчера `06. Гранд Юг`,
  сегодня `08. Сайт` дает одну строку изменения.
- Rollout acceptance: первые топ-20 рекомендаций вручную сверить с
  Максимом/Тимуром и 2-3 дня запускать dry-run без изменений в 1С.

# Rollout

1. Развернуть API и CSV wrapper в `pricing-service`.
2. Запускать локальный dry-run после сборки витрины дебиторки.
3. Сверить первые отчеты с бизнесом.
4. Две автоматические публикации задачи 756 в 10:30/10:35 отключены постоянно;
   диагностика остается во вкладке `Контроль папок`, ежедневный rebuild кеша
   сохраняется.
5. Восстановление публикаций допускается только отдельным решением пользователя.
6. Автоперенос в 1С рассматривать отдельным этапом после подтверждения качества.
7. Любые будущие команды на изменение глубины кредита, лимита или папки
   контрагента оформлять через `onec_commands.v1` в существующем
   `UT103_EXCHANGE_ROOT`, сначала только в `dry_run`.
