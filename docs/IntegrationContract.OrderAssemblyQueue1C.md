# Integration Contract: CRM -> очередь сборки заказов 1С

## 1. Назначение и владельцы факта

Контракт предоставляет рабочему месту ТЗП единую очередь заказов, которым CRM
разрешила сборку.

- Bitrix24 — источник допуска, срочности и срока: в очередь входит только стадия
  `EXECUTING` (`Сборка / обеспечение`).
- `ЗаказПокупателя` в УТ 10.3 — источник построчного и итогового факта сборки.
- `pricing-service` — fail-closed адаптер, сортировка и технический снимок ответа.
- РТУ не является основанием для включения в очередь и не создаётся при завершении
  сборки. Она появляется только по отдельному физическому факту выдачи или передачи.

## 2. HTTP API

```http
GET /api/order-fulfillment/assembly-queue?format=xml&limit=500
Authorization: Bearer <internal-token>
Accept: application/xml
```

Параметры:

| Параметр | Значение |
| --- | --- |
| `format` | Только `xml`, по умолчанию `xml` |
| `limit` | `1..500`, по умолчанию `500`; превышение фактического числа строк даёт `503`, а не усечённую очередь |

Токен backend хранится в `ORDER_FULFILLMENT_INTERNAL_API_TOKEN`. В УТ 10.3 URL
и тот же токен читаются из `MM_ORDER_ASSEMBLY_QUEUE_URL` и
`MM_ORDER_ASSEMBLY_QUEUE_TOKEN`; секреты в конфигурацию не встраиваются.

## 3. Успешный XML

Ответ `200 application/xml`:

```xml
<?xml version="1.0" encoding="utf-8"?>
<assembly_queue generated_at="2026-08-31T10:00:00Z"
                last_success_at="2026-08-31T10:00:00Z"
                stale="false" count="1" truncated="false">
  <order>
    <order_number>218011</order_number>
    <deal_id>11</deal_id>
    <crm_stage>EXECUTING</crm_stage>
    <stage_entered_at>2026-08-31T07:00:00Z</stage_entered_at>
    <delivery_method>Самовывоз</delivery_method>
    <payment_status>Оплачен</payment_status>
    <assembly_due_at>2026-08-31T09:00:00Z</assembly_due_at>
    <urgent>true</urgent>
    <urgent_reason>Клиент выезжает</urgent_reason>
    <urgent_until>2026-08-31T12:00:00Z</urgent_until>
    <synced_at>2026-08-31T10:00:00Z</synced_at>
    <evidence_id>64-символьный-sha256</evidence_id>
  </order>
</assembly_queue>
```

Обязательные поля для допуска в 1С: непустой `order_number`, стадия
`EXECUTING`, непустой `evidence_id`. Для одного номера заказа 1С должна получить
ровно одну сделку; ноль или дубликат блокируют действие над заказом.

`evidence_id` — SHA-256 нормализованного CRM payload. Это идентификатор
технического доказательства, а не бизнес-статус и не ключ идемпотентности сборки.

## 4. Порядок очереди

Backend сортирует строки одинаково при каждом запросе:

1. действующая срочность;
2. срок сборки `assembly_due_at`, пустой срок — в конец;
3. время входа в `EXECUTING` (`stage_entered_at`, FIFO);
4. номер заказа;
5. ID сделки.

Срочность действует только при одновременном наличии `urgent = true`, непустой
причины и `urgent_until >= now`. Просроченный или необоснованный флаг не повышает
приоритет. `stage_entered_at` берётся из `MOVED_TIME`; если CRM его не вернула,
фиксируется время первого успешного наблюдения и не сдвигается следующими sync.

В ТЗП поверх CRM-порядка сначала показывается операционная группа 1С:
`Готов к сборке`, `Недостаток товара`, `Ошибка данных`. Внутри группы сохраняется
срочность, срок и FIFO.

## 5. Fail-closed ошибки

При любой недостоверности ответ имеет статус `503 application/xml` и не содержит
строк прежней очереди:

```xml
<assembly_queue_error code="bitrix_unavailable"
                      last_success_at="2026-08-31T09:55:00Z"
                      stale="true" />
```

Коды: `bitrix_not_configured`, `bitrix_unavailable`,
`bitrix_invalid_payload`, `assembly_queue_limit_exceeded`.

Последний успешный снимок остаётся в БД только для диагностики. Его запрещено
показывать ТЗП или использовать для взятия/завершения заказа. Клиент 1С также
отбрасывает ответы с `stale != false`, `truncated != false`, неизвестным корнем
или неполной строкой и очищает локальную таблицу результата.

## 6. Хранение и миграция

Технические таблицы:

- `order_assembly_queue_item` — последний успешный нормализованный снимок;
- `order_assembly_queue_sync_state` — время успеха/ошибки, код ошибки и число строк.

Схема вводится миграцией
`alembic/versions/a4c5e6f70819_add_order_assembly_queue.py`. Снимок не становится
вторым source of truth: каждый API-запрос сначала читает CRM, а при сбое отвечает
`503`.

## 7. Исходящее событие сборки и повторы CRM

`pricing-service` является владельцем очереди доставки подтверждённых событий
сборки в CRM.

Сервис получает событие из 1С либо восстанавливает его read-only reconciler-ом,
проверяет `СтатусИсполнения`, `КодСлужбыДоставки` и уникальный идентификатор
события, после чего создаёт идемпотентную outbox-запись.

Повторная обработка выполняется в `pricing-service`. Недоступность CRM не
отменяет статус сборки в 1С. После исчерпания повторов событие переходит в
`manual_review` и отображается в мониторе расхождений.

Прямой вызов `1С -> CRM` сохраняется только как переходная совместимость. После
приёмки backend-outbox единственным штатным писателем стадии CRM становится
`pricing-service`, чтобы исключить двойные переходы и дубли доставки.

### 7.1. Приём события из 1С

```http
POST /api/order-fulfillment/assembly-events
Authorization: Bearer <internal-token>
Content-Type: application/x-www-form-urlencoded
```

Обязательные поля: `event_key`, `order`, `status=assembled`,
`assembly_source=customer_order`, `assembly_ref`, `assembled_at`,
`execution_status`, `delivery_code`. Дополнительно передаются `payment_mode` и
`onec_order_number`.

Backend принимает только `execution_status=05/06`. Для `MM_COURIER` разрешён
только статус `06`; режим `payment_mode=by_agreement` означает согласованную
оплату при получении и сам по себе не переводит заказ в ручной разбор. Проверки
отмены заказа и адреса доставки остаются обязательными.

УТ 10.3 читает URL этого endpoint из `MM_ORDER_ASSEMBLY_EVENT_URL`, а Bearer
token — из `MM_ORDER_ASSEMBLY_QUEUE_TOKEN`. Значения остаются во внешнем
окружении и не встраиваются в конфигурацию.

Успешный первый приём возвращает `accepted=true`, `duplicate=false`, ID и статус
outbox-записи. Повтор того же `event_key` с тем же payload возвращает ту же
запись с `duplicate=true`. Тот же ключ с другим payload даёт `409`, нарушение
контракта — `422`.

Outbox хранится в `order_assembly_crm_outbox`, создаваемой миграцией
`d7e8f9012345_add_order_assembly_crm_outbox.py`. Неуспешная доставка получает
экспоненциальную задержку; после предельного числа попыток — статус
`manual_review`. Reconciler восстанавливает пропущенные события из 1С read-only,
но фильтр `05/06` применяется только к событию `assembled`: существующий контур
фактической выдачи `issued` не сужается.

## 8. Приёмка

- endpoint возвращает только `EXECUTING` и сортирует срочность/срок/FIFO;
- fallback времени входа устойчив между синхронизациями;
- `503`, overflow и некорректный payload не публикуют частичную или старую очередь;
- УТ 10.3 не разрешает действия без свежего полного XML;
- событие `Собран` формируется по `ЗаказПокупателя`, а reconciler отправляет
  `assembly_source=customer_order`;
- повтор одного события не создаёт вторую outbox-запись, сбой CRM переводит
  событие в `retry`, затем в `manual_review`;
- `MM_COURIER + 06 + by_agreement` допускает неоплаченный заказ к стадии
  готовности только при пройденных проверках отмены и адреса;
- создание РТУ остаётся отдельным физическим действием.

## Ограниченный тестовый запуск №46 — 14.09.2026

`app.api.order_assembly_readonly:create_app` монтирует только существующий
`GET /api/order-fulfillment/assembly-queue` с его проверкой Bearer token.
Команды событий сборки, изменения сделок, оплаты и отправления отсутствуют.
Сервис очереди использует `ReadOnlyAssemblyClient`: разрешён исключительно
`crm.deal.list` с фильтром `=STAGE_ID: EXECUTING`. HTTP POST внутри Bitrix REST
для этого метода является чтением, а не созданием/изменением сделки.

Запуск требует `ENVIRONMENT=test` и отдельной SQLite
`/opt/MM/.local/task46-test-assembly/queue.sqlite`; production PostgreSQL
не допускается. Схему двух таблиц очереди нужно подготовить отдельным шагом;
entrypoint не создаёт таблицы и не запускает фоновые миграции.

Источник задаётся явно после согласования: `MM_TASK46_CRM_SOURCE=test` для
отдельного тестового портала либо `production_readonly` для согласованного
чтения `crm.master-mobile.ru`. Боевой адрес нельзя объявить тестовым; значение
из случайно загруженного `.env` само по себе не разрешает запуск. Webhook и
токен остаются только в закрытом окружении. Выбор источника пока открыт.
